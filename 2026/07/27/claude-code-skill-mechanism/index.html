Claude Code Skill 机制深度解析

CLAUDE.md 解决了”让 AI 记住项目规范”的问题。但现实中的开发任务远不止遵守规范：你需要 AI 按照特定流程部署应用、用固定模板生成代码、遵循团队专属的审查清单。这些多步骤的结构化工作流，靠一个 CLAUDE.md 是撑不住的。

Skill 就是为这个场景设计的。

Skill 不是什么

一个常见的误解是把 Skill 当成一个 Markdown 文件。实际上 Skill 是一个完整的目录结构，可以包含核心指引文件、参考资料、可执行脚本和输出模板。系统不会一次性注入所有资源，而是让 AI 根据任务进度按需读取。

my-skill/
  SKILL.md          # 必需，核心指引
  reference.md      # 可选，详细参考文档
  scripts/          # 可选，工具脚本
    validate.py
    deploy.sh
  templates/        # 可选，输出模板
    api-endpoint.ts

官方明确指出，充分利用目录结构的 Skill 能发挥最大效能。把所有内容塞进一个文件是最常见的错误用法。

SKILL.md 的格式

核心文件由 YAML frontmatter 和 Markdown 正文组成：

---
description: 根据团队规范生成 REST API 端点。当用户要求创建新 API、添加接口、编写端点时触发。
allowed-tools:
  - Bash
  - Read
  - Write
---

# API 端点生成器

## 步骤
1. 确认接口路径和 HTTP 方法
2. 生成路由文件，遵循 src/api/ 下的现有命名模式
3. 运行 scripts/validate.py 检查接口规范合规性
4. 如果验证失败，修复后重新验证

## 坑点清单
- 所有端点必须包含 request id 中间件
- 错误响应统一使用 ApiError 类，不要自定义错误格式
- 数据库查询必须通过 repository 层，禁止在 controller 中直接操作

frontmatter 中的几个关键字段：

description。这是 Skill 能否被正确触发的决定性因素。后面会详细展开。

allowed-tools。预授权特定工具，免除每次调用的确认弹窗。对于需要频繁执行命令的 Skill 来说，这个配置直接影响使用体验。

disable-model-invocation。设为 true 后禁止 AI 自动触发，只允许用户通过斜杠命令手动调用。适合敏感操作，比如生产环境部署。

context。配置为 fork 模式时，Skill 会在隔离的上下文中运行，不污染主对话历史。适合探索性任务或规划类工作。

触发机制：渐进式披露

这是 Skill 系统中设计最精巧的部分，也是最容易被忽视的部分。

AI 并不会在启动时全量读取所有 Skill。系统采用的是渐进式披露：初始阶段只加载每个 Skill 的名称和 description。只有当用户输入与某个 description 匹配时，对应的 SKILL.md 正文才会被懒加载。附属的参考文件和脚本则需要 AI 根据根目录自行探索。

这里有一个硬性的字符预算限制。源码分析显示，系统为 description 列表分配的上下文预算很低，单条 description 存在 250 个字符的截断阈值，超出部分会被直接替换为省略号。如果安装的 Skill 过多，系统甚至会降级为只显示名称，连 description 都不展示。

这意味着 description 的前几十个字符直接决定了 Skill 的触发率。它应该被设计为面向模型的触发规则，而非面向人类的功能摘要。

好的 description：根据团队规范生成 REST API 端点。当用户要求创建新 API、添加接口、编写端点时触发。

差的 description：这是一个帮助你编写高质量 API 代码的工具，包含了我们团队的最佳实践和规范。

前者包含了明确的触发关键词，后者全是模糊的形容词。

内容编写原则

SKILL.md 的正文应该提供 AI 无法自行推断的增量信息。

高价值内容包括：特定环境的隐蔽规则、字段映射关系、容易踩的坑、团队独有的约定。比如”这个项目的 user_id 字段在数据库中是 bigint，但 API 层返回的是 string，转换逻辑在 src/utils/id.ts 中”。

低价值内容包括：AI 已经知道的通用知识、显而易见的操作步骤。比如”先阅读需求，然后编写代码，最后测试”。

官方建议提供充足信息但保留执行自由度。不要把 AI 限制在死板的流程轨道上，否则它在遇到未覆盖的情况时会失去应变能力。”做 A，然后做 B，然后做 C”不如”确保 A、B、C 都完成，顺序根据实际情况决定”。

控制在 500 行以内。超过这个长度，把详细参考资料拆分到独立文件中，让 AI 按需读取。

九大 Skill 类型

Anthropic 内部数百个 Skill 被归纳为九种核心类型：

  1. API 参考。对接特定 API 时的用法指南和常见陷阱。
  2. 产品验证。让 AI 自主验收工作成果，检查输出是否符合产品要求。
  3. 数据查询。封装数据库查询或日志检索的标准流程。
  4. 流程自动化。CI/CD 流程、批量操作等重复性工作。
  5. 代码脚手架。按团队模板生成项目骨架或模块代码。
  6. 质量审查。代码审查清单、安全检查项。
  7. 部署。标准化的部署流程和回滚方案。
  8. 排障手册。常见故障的诊断和修复流程。
  9. 基础设施运维。服务器管理、监控配置等运维操作。

其中，产品验证类被认为投资回报率最高。它赋予 AI 自主验收的能力，让 AI 在完成工作后自行检查输出是否达标。这相当于给 AI 装了一个内置的 QA 环节，显著减少人工复查的工作量。

高阶特性

记忆与持久化

Skill 可以通过专属环境变量获取持久化数据目录，用于保存日志、配置或中间状态。这些数据在 Skill 版本更新时不会被清除，支持跨会话的状态保持。典型用途是首次使用引导和渐进式配置积累。

脚本编排

将底层函数库预置在 scripts 目录中，让 AI 专注于逻辑组合而非重复编写基础代码。比如一个部署 Skill 可以在 scripts/ 中提供 check_health.sh、rollback.sh 等脚本，AI 只需要根据当前状态决定调用顺序。

动态上下文

SKILL.md 支持通过特定语法执行 Shell 命令，命令输出会替换文档中的占位符。这意味着 Skill 可以在加载时获取实时数据，比如当前的 Git 分支、环境变量或配置文件内容。

临时钩子

Skill 可以在配置中声明仅在激活期间生效的安全拦截或文件修改限制，会话结束后自动失效。这兼顾了安全性和开发体验，不需要为偶尔使用的 Skill 配置全局规则。

子代理执行

通过 context fork 配置，Skill 可以将任务委派给专门的子代理。子代理拥有独立的上下文窗口，完成后只将结果返回主会话。这对探索性任务和规划类工作特别有用，避免了大量中间过程污染主对话历史。

团队共享与管理

Skill 的作用域由存储位置决定：

  • ~/.claude/skills/ 下为个人级别，跨项目生效
  • 项目根目录 .claude/skills/ 下为团队级别，纳入版本控制
  • 子目录中的 Skill 支持 Monorepo 场景，处理对应目录文件时自动激活

初期可以直接将 Skill 放入代码仓库。规模化后建议建立内部插件市场，按需安装。Anthropic 内部采用类似开源社区的自然演化模式，通过沙盒测试和口碑传播来决定是否纳入正式市场。

Skill 之间的依赖不需要复杂的原生管理机制。如果一个 Skill 需要调用另一个 Skill，直接在文档中用自然语言声明即可，AI 会自行处理调用链。

使用度量与优化

通过工具调用前的钩子记录 Skill 使用日志，可以识别两类问题：

高频使用的优质 Skill。验证了设计方向，可以进一步打磨和扩展。

触发不足的问题 Skill。通常不是 Skill 本身没用，而是 description 编写不当导致 AI 未能识别。这是最常见的 Skill 失效原因。优化 description 中的关键词覆盖，通常就能解决大部分问题。

数据闭环是持续优化的基础。没有使用数据，就无法区分”Skill 写得不好”和”Skill 根本没被触发”这两种完全不同的失败模式。

小结

Skill 是 Claude Code 从”通用助手”进化为”专业工程师”的关键机制。它的设计哲学可以概括为三点：

分层加载。不用的不加载，用到的才注入，控制上下文成本。

增量信息。只写 AI 不知道的，不重复常识。

验证闭环。最有价值的 Skill 是让 AI 自己检查自己的工作。

好的 Skill 始于简单的经验记录，在解决边界问题的过程中逐步完善。不需要一开始就设计完美的系统，先把你反复纠正 AI 的那些问题沉淀下来，就是一个合格的 Skill。
