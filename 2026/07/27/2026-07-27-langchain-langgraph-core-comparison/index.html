LangChain 与 LangGraph 核心对比总结

LangChain LangGraph Deep Agents
发布日期:   2026-07-27

基于多轮对话深度讨论的精华整理，聚焦三个核心主题：框架区别、记忆机制、错误处理。

一、LangChain 与 LangGraph 的区别

1.1 核心设计哲学

LangChain LangGraph
编排方式 Chain（链式） / Agent（黑盒） Graph（图：节点 + 边）
抽象程度 高（开箱即用） 低（需要自己组装）
学习曲线 低 高
灵活性 受限于预定义组件 几乎无限
适合场景 简单线性工作流 复杂条件逻辑、反馈循环、多 Agent 协作

1.2 组件层级关系

LangChain：Chain > Agent > Tool

Chain（唯一的容器，最大的编排单元）
├── 步骤1: LLM 调用
├── 步骤2: Tool 调用（预定义的）
├── 步骤3: Agent（Agent 是 Chain 的一个步骤）
│   ├── 推理
│   ├── 动态选 Tool
│   └── 执行 Tool
├── 步骤4: LLM 调用
└── 步骤5: 输出

LangGraph：Graph > Node + Edge（没有 Agent 对象）

Graph（唯一的容器）
├── Node: "reasoning"（推理节点）
├── Node: "tool_execute"（工具执行节点）
├── Edge: reasoning → tool_execute（条件边：选了哪个工具？）
├── Edge: tool_execute → reasoning（循环边）
└── Edge: reasoning → END（条件边：可以结束了？）

关键区别：LangGraph 把 Agent 行为拆成了 推理节点 + 工具节点 + 循环边 的组合，不再是一个独立的黑盒对象。

1.3 代码层面的差异

# LangChain：Agent 是一个对象，内部循环不可见
agent = create_agent(model="gpt-4o", tools=[search, calculate])
result = agent.invoke({"messages": [user_msg]})

# LangGraph：Agent = 节点 + 边的拓扑结构
builder = StateGraph(AgentState)
builder.add_node("reasoning", reasoning_node)
builder.add_node("tools", tool_node)
builder.add_edge(START, "reasoning")
builder.add_conditional_edges("reasoning", tools_condition, {
    "tools": "tools",
    END: END,
})
builder.add_edge("tools", "reasoning")  # 这一行就是循环！
graph = builder.compile()
result = graph.invoke(...)

1.4 适用场景

场景 推荐框架
简单的 LLM 对话 LangChain
单步工具调用（查天气、搜文档） LangChain
需要记忆的聊天机器人 都可以（LangChain 更简单）
多步骤 + 条件分支工作流 LangGraph
带反馈循环（LLM 输出→检查→重试） LangGraph
多 Agent 协作 LangGraph
需要人工审批节点 LangGraph
需要从失败点恢复（而非从头重试） LangGraph

二、记忆机制

2.1 LangChain 的 Memory：外部附加组件

核心逻辑：Memory 是挂在 Chain 外面的独立对象。每轮对话执行 save_context() 存、load_memory_variables() 取，本质是把历史拼进 Prompt。

八种 Memory 类型

类型 存储方式 Prompt 长度 适用场景
ConversationBufferMemory 存全部原文 无限增长 短对话（<10轮）
ConversationBufferWindowMemory(k=K) 只保留最近 K 轮 固定 只需最近上下文
ConversationSummaryMemory LLM 自动生成摘要 固定，很短 超长对话，细节不重要
ConversationSummaryBufferMemory 近期原文 + 远期摘要 固定，可配置 长对话，兼顾远近
ConversationTokenBufferMemory 按 Token 数量截断 固定，精确 需精确控制 Token 预算
VectorStoreRetrieverMemory 向量语义检索 只取最相关 海量历史，精准回忆
自定义 Memory 完全自由 完全自定义 特殊存储/过滤需求
RunnableWithMessageHistory 任意后端 看实现 LangChain 1.0 推荐方式

存取流程（以 ConversationBufferMemory 为例）

每一轮对话：

① load_memory_variables()
   → self.buffer → get_buffer_string(messages)
   → 返回 {"history": "Human: xxx\nAI: xxx\n..."}

② 拼进 Prompt（{history} 占位符被替换）

③ LLM 生成回复

④ save_context(inputs={"input": "..."}, outputs={"output": "..."})
   → HumanMessage(input) → append 到 chat_memory.messages
   → AIMessage(output) → append 到 chat_memory.messages

内部数据结构：

# BaseChatMemory.save_context() 的实现：
self.chat_memory.messages.append(HumanMessage(inputs["input"]))
self.chat_memory.messages.append(AIMessage(outputs["output"]))

# chat_memory 就是 ChatMessageHistory
# ChatMessageHistory 就是 messages: list[BaseMessage] 的容器

持久化：get_session_history

默认的 Memory 类都存在进程内存（一个 Python 变量），进程重启就丢失。要持久化，需要用 RunnableWithMessageHistory + 自己写 get_session_history：

# 自己实现的读写函数，LangChain 自动调用
def get_session_history(session_id: str) -> ChatMessageHistory:
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,       # ← 你决定存在哪（内存/Redis/PostgreSQL/文件）
    input_messages_key="input",
    history_messages_key="history",
)

重要区分：

  • **create_agent 创建的 Agent 不需要 get_session_history**，因为 Agent 底层是 LangGraph 图，用 checkpointer 管理记忆
  • **普通 Chain 需要 get_session_history**，因为 Chain 没有内置的状态管理

2.2 LangGraph 的记忆：State + Checkpointer

核心逻辑：State 本身就是记忆。没有单独的 Memory 对象。加一个 checkpointer 就自动实现持久化。

class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]  # 对话历史
    user_name: str          # 任意字段都是"记忆"
    task_progress: str      # 任意字段都是"记忆"

checkpointer = MemorySaver()  # 或 SqliteSaver、PostgresSaver
graph = builder.compile(checkpointer=checkpointer)

# 同一个 thread_id → 自动恢复上次的 State，无需手动读写
config = {"configurable": {"thread_id": "user-001"}}
graph.invoke({"messages": [msg]}, config=config)
LangChain Memory LangGraph State + Checkpointer
本质 拼进 Prompt 的历史字符串 图的原生数据结构，节点间自动流转
存储内容 只有对话历史 对话历史 + 任务进度 + 用户偏好 + 任意字段
持久化 手动实现 get_session_history 加 checkpointer 自动完成
隔离方式 自己设计 session_id 逻辑 thread_id 天然隔离
触发时机 每轮对话结束 每个 superstep（节点）结束

2.3 LangChain Memory 的内部实现解析

继承链

BaseMemory                    ← 抽象基类，定义接口
  └─ BaseChatMemory           ← 实现 save_context（存）
       └─ ConversationBufferMemory ← 实现 load_memory_variables（取）+ buffer 格式化

BaseMemory —— 定义接口

最底层的抽象，只声明了记忆必须具有的能力：

load_memory_variables()  → 取出历史
save_context()           → 存入这一轮对话

BaseChatMemory —— 实现存

class BaseChatMemory(BaseMemory):
    def __init__(self):
        self.chat_memory = ChatMessageHistory()  # 核心：就是那个 messages 列表容器
        self.input_key = "input"                 # 从 inputs 字典取用户消息的 key
        self.output_key = "output"               # 从 outputs 字典取 AI 回复的 key

    def save_context(self, inputs, outputs):
        # ① 从字典取出用户消息 → HumanMessage
        human_message = HumanMessage(content=inputs[self.input_key])
        # ② 从字典取出 AI 回复 → AIMessage
        ai_message = AIMessage(content=outputs[self.output_key])
        # ③ 追加到内存列表
        self.chat_memory.messages.append(human_message)
        self.chat_memory.messages.append(ai_message)

ChatMessageHistory 的本质就是一个 messages 列表 + add_user_message / add_ai_message 便捷方法。

ConversationBufferMemory —— 实现取和格式化

class ConversationBufferMemory(BaseChatMemory):
    human_prefix: str = "Human"
    ai_prefix: str = "AI"
    memory_key: str = "history"   # 返回时用的 key 名

    @property
    def buffer(self):
        if self.return_messages:
            # 模式1：返回原始消息对象列表
            return self.chat_memory.messages
        else:
            # 模式2（默认）：格式化成字符串
            return "Human: 我叫张三\nAI: 你好！\n..."

    def load_memory_variables(self, inputs):
        # 返回 {"history": <buffer内容>}，这个字典合并进 Prompt 变量
        return {self.memory_key: self.buffer}

完整存取流程（以两轮对话为例）

第1轮：chain.predict(input="我叫张三")

① load_memory_variables:
   messages = []  → buffer 为空 → 返回 {"history": ""}

② 构建 Prompt:
   "...{history}...Human: {input}..."
   → "...Human: 我叫张三..."  (history 位置是空的)

③ LLM 生成回复: "你好张三！"

④ save_context({"input": "我叫张三"}, {"output": "你好张三！"}):
   → self.chat_memory.messages.append(HumanMessage("我叫张三"))
   → self.chat_memory.messages.append(AIMessage("你好张三！"))
   此时 messages = [HumanMessage("我叫张三"), AIMessage("你好张三！")]


第2轮：chain.predict(input="我刚才说我叫什么？")

① load_memory_variables:
   messages = [HumanMessage("我叫张三"), AIMessage("你好张三！")]
   → get_buffer_string → "Human: 我叫张三\nAI: 你好张三！"
   → 返回 {"history": "Human: 我叫张三\nAI: 你好张三！"}

② 构建 Prompt:
   "Human: 我叫张三\nAI: 你好张三！\nHuman: 我刚才说我叫什么？"

③ LLM 看到历史 → 回答: "你叫张三！"

④ save_context → messages 再追加 2 条 → 现在共 4 条

关键总结：整个记忆机制就是一个 messages 列表，每轮对话追加两条（Human + AI），取的时候格式化成字符串拼进 Prompt。所有 Memory 类型的区别只是格式化 / 裁剪 / 压缩这个列表的方式不同。

三、Checkpoint 持久化机制（LangGraph 记忆的底层实现）

3.1 持久化了什么？

整个 State（TypedDict 里定义的所有字段）：

checkpoint = {
    "channel_values": {           # ← 核心！State 全部字段的快照
        "messages":     [HumanMessage, AIMessage, ...],
        "step_count":   3,
        "user_name":    "张三",
        "任意自定义字段":  "任意值"
    },
    "channel_versions": {...},    # 版本号，用于增量更新
    "versions_seen":    {...},    # 每个节点看到的版本，用于失败恢复
}

3.2 怎么持久化的？

每个节点（superstep）执行完毕后，LangGraph 自动调用 checkpointer.put() 存快照：

graph.invoke(input, config={"thread_id": "user-1"})
  │
  ├── greet 执行完毕 → checkpointer.put(config, checkpoint)  ← 自动！
  ├── remember_name 执行完毕 → checkpointer.put(config, checkpoint)  ← 自动！
  └── farewell 执行完毕 → checkpointer.put(config, checkpoint)  ← 自动！

开发者不需要手动调用任何 save 方法。

3.3 什么时候加载？

**每次 graph.invoke() 时，根据 config 里的 thread_id 自动调用 checkpointer.get()**：

graph.invoke(input, config={"thread_id": "user-1"})
  ↓
checkpointer.get(config)  ← 根据 thread_id 查上次的 checkpoint
  ↓
  ├─ 第一次调用 → 返回 None → 用 input 做初始 State
  └─ 第 N 次调用 → 返回上次存的完整 State → 以历史 State 为起点继续执行

3.4 关键特性

  • 同一个 thread_id = 同一个会话 = 自动拼接历史
  • 不同 thread_id = 完全隔离的记忆空间
  • 失败恢复：节点失败 → 从最后一个成功的 checkpoint 恢复，不从头执行

四、错误处理机制

4.1 LangChain：Middleware 声明式配置

通过 Middleware 配置重试策略，只能选择框架提供的选项：

from langchain.agents.middleware import (
    ModelRetryMiddleware,
    ModelFallbackMiddleware,
    ToolRetryMiddleware,
)

agent = create_agent(
    model="gpt-4o",
    tools=[...],
    middleware=[
        ModelRetryMiddleware(max_retries=3, backoff_factor=2.0),
        ModelFallbackMiddleware("gpt-3.5-turbo"),  # 主模型挂了切备用
        ToolRetryMiddleware(
            max_retries=2,
            tools=["api_tool"],
            retry_on=(ConnectionError, TimeoutError),
            on_failure="continue",  # 选项：continue / raise / error
        ),
    ],
)

特点：

  • 简单，声明式配置
  • 你只能选：重试几次、退避策略、失败后继续还是崩溃
  • 无法根据错误类型做不同处理
  • 无法在重试前执行额外逻辑（如发告警、记日志）

4.2 LangGraph：错误处理是一个图节点

错误处理作为图中的一个独立节点，可以写任意逻辑：

def error_handler(state):
    """独立的错误处理节点——可以写任意复杂逻辑"""
    if state["error_count"] >= state["max_retries"]:
        # 超过重试次数 → 走 fallback
        return {"messages": [AIMessage(content="服务不可用，使用已有知识回答")]}
    
    if "TimeoutError" in state["last_error"]:
        # 超时 → 切换到备用 API
        return {"use_backup_api": True}
    
    if "AuthError" in state["last_error"]:
        # 鉴权失败 → 通知运维，暂停执行
        send_alert("API 鉴权失败！")
        # 可以用 interrupt() 暂停等待人工处理
    
    # 还可以：记日志、发告警、切换策略...
    return {}

# 错误处理作为独立节点接入图
builder.add_node("error_decision", error_handler)

# 决定重试还是放弃
builder.add_conditional_edges("error_decision", after_error_handling, {
    "reasoning": "reasoning",   # 重试
    "__end__": END,             # 放弃
})

图结构可视化：

              ┌──────────┐
     ┌───────→│reasoning │←──────────────┐
     │        └────┬─────┘               │
     │             │                     │
     │             ↓                     │
     │      ┌────────────┐              │
     │      │ execute_tool│              │
     │      └──┬────┬────┘              │
     │         │    │                   │
     │       成功  失败                  │
     │         │    │                   │
     │         │    ↓                   │
     │         │ ┌──────────────┐       │
     │         │ │错误处理节点    │ ← 独立 │
     │         │ │              │       │
     │         │ │· 分类错误类型  │       │
     │         │ │· 切换备用工具  │       │
     │         │ │· 发送告警     │       │
     │         │ │· 人工审批介入  │       │
     │         │ └──┬────┬──────┘       │
     │         │    │    │              │
     │         │  重试  放弃             │
     └─────────┼────┼────│──────────────┘
               │    ↓
               └──→ END

4.3 错误处理对比总结

LangChain Middleware LangGraph Error Node
自由度 配置：重试次数、退避、失败行为 任意 Python 逻辑
错误分类 只能按异常类型过滤 可以在节点里做任何判断
人工介入 ❌ 不支持 interrupt() 暂停等人处理
Fallback 工具 ❌ 不支持 ✅ 可以切换到备用工具
失败恢复 只能从头重来 Checkpoint 让图从失败处继续
告警/日志 ❌ 不支持 ✅ 任意逻辑

五、一句话总结

LangChain = 给你封装好的"家电"，调开关和旋钮，开箱即用但改不了内部。

LangGraph = 给你"零件"，决定怎么组装，多写代码但完全可控。

记忆：LangChain 靠外部 Memory 对象拼 Prompt；LangGraph 靠 State 本身 + Checkpointer 自动持久化。

错误处理：LangChain 靠 Middleware 配置重试；LangGraph 靠独立的错误处理节点，拥有无限定制的自由。

六、LangGraph State 类型详解

6.1 State 的本质

State 是图中所有节点共享的数据容器。每个节点接收 State、返回局部更新，LangGraph 根据规则将更新合并回 State。State 同时承担”记忆”和”节点间通信”两个职责。

6.2 三种 Schema 定义方式

方式 访问方式 校验能力 推荐程度
TypedDict state["key"] 无运行时校验，字段错误抛 KeyError 官方推荐，最轻量
dataclass state.key 无运行时校验，字段错误抛 TypeError 适合需要属性访问的场景
Pydantic BaseModel state.key 有完整校验，字段错误抛 ValidationError 需要严格校验时使用 
# 方式一：TypedDict（官方推荐）
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    step_count: int
    user_name: str

# 方式二：dataclass
from dataclasses import dataclass

@dataclass
class AgentState:
    messages: Annotated[list[BaseMessage], add_messages]
    step_count: int = 0
    user_name: str = ""

# 方式三：Pydantic BaseModel
from pydantic import BaseModel

class AgentState(BaseModel):
    messages: Annotated[list[BaseMessage], add_messages] = []
    step_count: int = 0
    user_name: str = ""

6.3 Reducer 机制

问题：多个节点都往 messages 字段写数据，是覆盖还是追加？

答案：由 Reducer 决定。

from typing import Annotated
from operator import add

class State(TypedDict):
    # 有 Reducer：新值与旧值合并（这里是列表拼接）
    messages: Annotated[list[str], add]

    # 无 Reducer：新值直接覆盖旧值（默认行为）
    current_step: str

Annotated[type, reducer] 语法解析：

  • Annotated 是 Python 类型标注的扩展，第一个参数是类型，第二个参数是元数据
  • LangGraph 读取第二个参数作为该字段的 Reducer 函数
  • Reducer 函数签名：(old_value, new_value) -> merged_value

add_messages —— 最常用的内置 Reducer：

from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

add_messages 不是简单的列表拼接，它会：

  1. 按 id 去重：如果新消息的 id 与已有消息相同，则更新而非追加
  2. 自动为无 id 的消息生成 uuid
  3. 支持将 tuple ("ai", "content") 自动转换为 AIMessage 对象

6.4 节点返回值与 State 更新规则

def my_node(state: AgentState):
    # 节点只返回"局部更新"，不需要返回完整 State
    return {"step_count": state["step_count"] + 1}  # 只更新这一个字段

规则：

  • 节点返回 dict → LangGraph 逐字段应用 Reducer 合并到 State
  • 未返回的字段 → 保持不变
  • 返回了 State 中未定义的字段 → 静默忽略（不报错）

七、补充概念

7.1 DAG vs 有环图

LangChain（DAG）：
  A → B → C → D（单向流动，不回头）

LangGraph（有环图）：
  A → B → C → A（C 可以回到 A，形成循环）

为什么这很重要：Agent 的核心行为就是”推理 → 行动 → 观察 → 再推理”的循环。DAG 无法表达这个模式，所以 LangChain 的 AgentExecutor 只能在 Chain 内部用 while 循环硬编码。LangGraph 把循环提升为一等公民（一条边就能表达），使得循环中的每个节点都可独立观测、测试和替换。

7.2 interrupt() 人工介入机制

LangGraph 支持在图中设置”暂停点”，等待人工审批后继续执行：

from langgraph.types import interrupt

def approval_node(state):
    """需要人工审批的节点"""
    # 执行到这里时，图暂停，State 被 Checkpointer 保存
    human_decision = interrupt({
        "question": "是否允许执行删除操作？",
        "context": state["pending_action"],
    })
    # 人工回复后，从这里继续执行
    if human_decision == "approve":
        return {"approved": True}
    return {"approved": False}

工作流程：

  1. 图执行到 interrupt() → 暂停 → State 自动持久化到 Checkpointer
  2. 外部系统（UI/CLI）收到中断通知，展示给人工
  3. 人工做出决策，调用 graph.invoke(Command(resume="approve"), config)
  4. 图从暂停点恢复执行，interrupt() 返回人工的决策值

这是 LangChain 完全不具备的能力。LangChain 的 Middleware 没有暂停-恢复语义。

7.3 Command 对象（控制流跳转）

LangGraph 的 Command 允许节点同时更新 State 和指定下一个节点：

from langgraph.types import Command

def router_node(state):
    if state["need_tool"]:
        # 更新 State 并跳转到 tool 节点
        return Command(update={"routed": True}, goto="tool_execute")
    return Command(goto=END)

相比条件边（add_conditional_edges），Command 把”数据更新”和”路由决策”合并到一个返回值中，适合动态路由场景。

八、LangChain 公司新框架：Deep Agents

8.1 定位

Deep Agents 是 LangChain Inc 推出的企业级 Agent 运行框架（Agent Harness）。它不是 LangGraph 的替代品，而是建在 LangChain + LangGraph 之上的更高层封装。

三者关系：

Deep Agents（成品构建器：规划、子代理、记忆、权限一站式）
    ↓ 构建于
LangGraph（图运行引擎：状态管理、检查点、循环、中断）
    ↓ 使用
LangChain（组件库：模型接入、工具、RAG、Prompt）

8.2 核心特性

  • 内置规划：自带 write_todos 工具，Agent 先列待办再逐项推进
  • 子代理隔离：通过 task 创建子 Agent，拥有独立上下文和工具集，主 Agent 只拿最终结果
  • 文件系统能力：读写、局部编辑、通配搜索；大输出落盘避免撑满上下文
  • 自动摘要：旧对话自动压缩，保持上下文窗口可控
  • 权限与审批：内置人工审批点和命令沙箱
  • 原生 LangGraph 支持：底层复用 LangGraph 的 Checkpointer 和状态管理

8.3 与 LangGraph 的选择标准

场景 选择
需要完全自定义图拓扑、节点逻辑 LangGraph
需要快速搭建一个功能完整的 Agent 产品 Deep Agents
需要子代理协作、长任务拆解、文件处理 Deep Agents
需要精确控制每一步的状态转移 LangGraph
原型验证、简单工具调用 LangChain
