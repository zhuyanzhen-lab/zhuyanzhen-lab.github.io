Claude Code 记忆机制深度解析

LLM 本质上是无状态的。每次对话结束，上下文清空，一切归零。这意味着你上一轮花了 20 分钟教 AI 理解的项目架构、编码规范、调试经验，下一轮全部丢失。

Claude Code 通过一套分层的记忆系统解决了这个问题。这套系统的核心思路很直接：把需要记住的东西写成 Markdown 文件，每次启动时注入到上下文中。没有向量数据库，没有 RAG，没有复杂的记忆检索算法，就是纯文本文件的读取和拼接。

双轨记忆模型

Claude Code 的记忆分为两条轨道：

人工配置轨道。开发者手动维护的 CLAUDE.md 文件和 rules 规则库。内容是项目架构、编码规范、常用命令等确定性知识。每次会话启动时完整注入上下文。

AI 自主学习轨道。Auto Memory 机制。AI 在交互过程中自动记录调试经验、用户偏好纠正、踩过的坑。启动时只加载摘要索引，具体内容按需检索。

两者的关系是：你定基调，AI 补细节。

CLAUDE.md：人工记忆的核心载体

CLAUDE.md 是 Claude Code 记忆系统中最基础也最重要的文件。它的定位是”每次会话都应该知道的事实”。

四级层级体系

CLAUDE.md 不只是一个文件，而是一个从宏观到微观的四级体系。系统会沿目录树向上搜集并合并所有找到的文件，后加载的覆盖先加载的：

企业级。存放在操作系统级别的受保护目录，如 macOS 的 /Library/Application Support/ClaudeCode/CLAUDE.md。用于公司层面的合规要求，个人无法绕过。

用户级。位于 ~/.claude/CLAUDE.md，跨所有项目生效。适合存放个人编码偏好，比如”始终使用 TypeScript strict 模式””注释用中文”。

项目级。放在工程根目录的 CLAUDE.md 或 .claude/CLAUDE.md，纳入版本控制。这是团队共享的项目规范，包括技术栈说明、架构约定、构建命令等。

本地覆盖。带 .local 后缀的同级文件，如 CLAUDE.local.md。专用于本地调试，排除在 Git 提交之外。

还有一个容易忽略的机制：子目录级。项目子目录中也可以放 CLAUDE.md，但不会在启动时全量加载。只有当 AI 访问该目录的代码时，才按需加载对应的配置。这个设计有效控制了 token 消耗。

编写原则

控制在 200 行以内。这是官方建议。文件越长，模型的遵从度越低，注意力越容易分散。

使用祈使句，提供具体信息。”使用 pnpm 而非 npm””Python 版本为 3.12””数据库连接字符串从 .env 读取”比”注意使用正确的包管理器”有效得多。

规则要可验证。”代码要有良好的错误处理”是模糊的，”所有 API 端点必须包含 try-catch 且返回标准化错误格式”是可验证的。模糊规则等于没有规则。

用 @ 语法引用外部文档。如果某个规范太长不适合直接写入 CLAUDE.md，可以用 @docs/api-convention.md 引用。但注意这是全文注入，不会节省上下文空间。

初始化方式

在项目根目录执行 /init 命令，AI 会分析当前目录结构并自动生成 CLAUDE.md 骨架。生成后建议手动审查和调整，不要完全依赖自动生成。

.claude/rules/：模块化规则库

当项目规模增大，单一 CLAUDE.md 无法承载所有规范时，可以将规则分散到 .claude/rules/ 目录中。

这个目录的核心特性是条件触发。通过 YAML frontmatter 中的 paths 字段定义匹配模式，规则只在 AI 操作相关文件时才被激活：

---
paths:
  - "src/api/**/*.ts"
---
# API 开发规范
- 端点必须包含输入验证
- 错误响应统一使用 ApiError 类
- 所有公开接口需要 JSDoc 注释

这比全部塞进 CLAUDE.md 的优势在于：不相关的规则不会占用上下文窗口。一个有 200 个文件的大型项目可能有 20 个规则文件，但每次对话实际加载的可能只有 2 到 3 个。

Auto Memory：AI 的自主笔记本

Auto Memory 是 Claude Code 在交互过程中自动积累的经验记录。它不需要人工维护，AI 会自己判断哪些信息值得记住。

存储位置

数据存储在 ~/.claude/projects/<project-hash>/memory/ 下，按 Git 仓库路径推导出专属目录。这意味着同一个代码库的不同分支和工作树共享同一份记忆。

加载机制

核心文件 MEMORY.md 充当索引，每次会话启动时加载前 200 行或 25KB。如果记忆内容超出这个范围，系统会按主题拆分，详细笔记静默存储，待特定场景下被模型主动检索。

典型记录内容

  • 调试过程中发现的坑和解决方案
  • 用户反复纠正的偏好，比如”不要用 any 类型””错误日志要包含 request id”
  • 项目特有的构建陷阱
  • 某次修复的关键步骤

管理方式

Auto Memory 默认启用，纯本地存储，不同步到云端或 Git。用户可以通过 /memory 命令查看、编辑、删除记忆条目，也可以通过环境变量 CLAUDE_CODE_DISABLE_MEMORY 全局禁用。

保存机制：什么值得记住

Auto Memory 不是什么都记。系统遵循一条核心原则：只保存无法从项目当前状态推导出的信息。代码里能 grep 到的、git 历史能查到的、标准工具能获取的，一律不存。

具体保存的信息分为四类：

  • 用户偏好：编码风格、工具选择（如 pnpm 而非 npm）、格式化习惯。
  • 行为纠正：用户对 AI 的纠正反馈，如”不要用 any 类型””错误日志要包含 request id”。系统同时记录正面验证和负面纠正，避免 Agent 因只记错误而变得过度保守。
  • 项目上下文：构建陷阱、部署经验、团队约定等无法从代码中直接推断的背景知识。
  • 外部引用：文档链接、架构决策记录等指针性信息。

保存动作在每轮用户交互之后由一个后台提取 Agent 静默执行。该 Agent 的权限被严格限制：只允许读操作和写入 memory 目录，不允许修改源代码或访问网络。写入顺序是先写主题文件到磁盘，再更新 MEMORY.md 索引，保证数据一致性。

检索机制：两条互补路径

MEMORY.md 索引在每次会话启动时注入上下文，但索引只是指针，每条记录约 150 字符，只存位置和摘要，不存完整内容。当模型需要具体知识时，有两条检索路径：

路径一：模型主动拉取。 模型根据索引中的摘要判断相关性，使用标准的文件读取工具加载对应主题文件。这是”拉”模式，由模型自主决定读什么。

路径二：Sonnet Bypass 自动注入。 这是一个更精巧的机制。对每一条用户 prompt，系统用一个轻量模型（Sonnet 级别）扫描 memory 目录下最多 200 个主题文件的 frontmatter（前 30 行），做字面关键词匹配，选出最相关的最多 5 个文件，将其完整内容作为 relevant_memories 注入上下文。这不是语义搜索，是纯关键词匹配。最近已经注入过的文件会被跳过，避免重复。

这种两阶段过滤的设计（廉价关键词扫描 frontmatter → 注入 top 匹配文件的完整内容）在成本和效果之间取得了平衡。没有向量数据库，没有 embedding 计算，就是对 Markdown 文件的文本匹配。

时间衰减。 检索时系统会标注记忆的时间新鲜度。超过 1 天的记忆会附加”可能已过时”的警告。超过 30 天的记忆被标记为需要谨慎对待，模型被指示先对照实际代码验证再行动。

记忆的完整生命周期

将保存和检索串联起来，一次完整会话中记忆的闭环如下：

会话启动
  → 加载 CLAUDE.md 层级 + MEMORY.md 索引（前 200 行）
  → 用户发送 prompt
  → Sonnet Bypass 扫描主题文件 frontmatter，注入 top 5 匹配
  → 模型处理 prompt + 注入的记忆 + 上下文
  → 后台提取 Agent 审查本轮交互
  → 发现不可推导信息？
     是 → 写主题文件 → 更新 MEMORY.md 索引
     否 → 跳过
  → Token 用量接近上限（~92%）？
     是 → 触发上下文压缩（见下文）
  → 会话结束
  → 满足 24h + 5 会话条件？
     是 → 触发 AutoDream 整合

会话启动时的记忆加载流程

一次新会话启动时，记忆加载的完整流程如下：

  1. 读取企业级 CLAUDE.md，如果存在
  2. 读取用户级 ~/.claude/CLAUDE.md
  3. 从当前目录向上遍历，合并所有项目级 CLAUDE.md 和 CLAUDE.local.md
  4. 加载 .claude/rules/ 中无条件触发的规则
  5. 读取 Auto Memory 的 MEMORY.md 索引文件
  6. 将以上内容拼接注入 system prompt

子目录的 CLAUDE.md 和带 paths 条件的 rules 文件在这一步不加载，等 AI 实际访问相关代码时再按需注入。

AutoDream：记忆的后台整合

记忆在每次会话中持续追加，时间久了必然出现重复、过时、矛盾的内容。AutoDream 是 Claude Code 的自动整合机制，类比人类的 REM 睡眠，在后台完成记忆的清理和合并。

触发条件

AutoDream 通过五层门控决定是否触发：

  1. 环境检查：确认 AutoDream 功能已启用，且不在远程模式或守护进程模式下。
  2. 时间门控：距上次整合超过 24 小时（通过锁文件的 mtime 判断，不需要额外存储时间戳）。
  3. 扫描节流：两次扫描之间至少有 10 分钟冷却期，防止快速无效的扫描循环。
  4. 会话门控：距上次整合至少产生了 5 个新会话（通过扫描 JSONL 会话记录文件计数）。
  5. 文件锁：获取进程级互斥锁，防止多个 Claude Code 实例同时整合。

这些阈值不是硬编码的，由远程 Feature Flag 控制，可以动态调整。

四阶段整合算法

AutoDream 由一个受限子 Agent 执行，该 Agent 无权修改源代码，也无网络访问权限。整合分四个阶段：

阶段一：Orient。 读取 MEMORY.md 索引，映射当前记忆目录的完整结构。

阶段二：Gather。 在本地 JSONL 会话记录中做定向 grep 搜索，提取用户纠正、显式保存请求、关键决策等新信号。不全文读取会话记录，只用窄搜索控制成本。

阶段三：Consolidate。 合并重叠条目。将相对日期（”昨天””上周”）转换为绝对日期（”2026-07-20”），防止时间逻辑错乱。解决不同文件之间的矛盾信息。删除已被当前代码推翻的过时事实。

阶段四：Prune and Index。 重建 MEMORY.md 索引，强制控制在 200 行或 25KB 以内。删除指向已删主题文件的死链接，压缩冗长的摘要描述。

崩溃恢复

整合过程使用锁文件 memory/.consolidate-lock 保护。锁文件存储当前进程 PID，文件的 mtime 同时充当”上次整合时间”的时间戳。如果整合过程中进程崩溃，锁在 1 小时后自动过期。如果整合失败，系统回滚锁文件的 mtime，使其看起来整合从未发生，下次会话会重新尝试。

上下文压缩的五层管线

长对话中 token 用量会逼近上下文窗口上限。当使用率达到约 92% 时，Claude Code 触发一个五层压缩管线：

第一层：预算裁剪。 截断过长的文件读取结果，保留前 N 行，剩余内容留在 JSONL 原始记录中备查。

第二层：工具输出裁剪。 优先丢弃体积大的工具输出结果。

第三层：MicroCompact。 针对 Prompt Cache 优化，优先压缩后部内容以保护缓存前缀不被破坏。

第四层：上下文折叠。 创建只读投影，不修改底层 JSONL 存储。

第五层：AutoCompact。 对完整对话做 LLM 摘要，将对话历史压缩到原始体积的约 10%。

压缩后，根目录的 CLAUDE.md 和 MEMORY.md 索引会从磁盘重新注入，具备抗压缩能力。子目录的 CLAUDE.md、带 paths 条件的 rules、未使用的技能描述和完整工具输出在压缩中丢失。用户可以通过 /compact focus on XXX 指令显式指定需要保留的内容。

记忆失效的场景与应对

规则被忽略

常见原因有三个：文件不在有效路径上、指令过于模糊、不同文件之间存在冲突规则。排查方法是用 /memory 命令确认文件是否被加载。

如果某条规则必须被严格执行，不应依赖 CLAUDE.md，而应使用 Hooks 机制。Hooks 可以在工具调用前后执行脚本，实现硬性拦截。比如禁止执行某些命令、自动格式化代码等。Hooks 是确定性的代码执行，不存在”模型可能不遵守”的问题。

上下文压缩导致遗忘

长对话中，Claude Code 会执行上下文压缩以节省 token。压缩后的行为：

  • 根目录的 CLAUDE.md 和 rules 会自动重新加载，具备抗压缩能力
  • 子目录的配置需要等 AI 再次访问该目录才能重新激活
  • Auto Memory 的索引会保留，但详细笔记需要重新检索

这意味着核心规则应该放在根目录，而非子目录。

对照：mem0 的数据库记忆方案

Claude Code 选择了文件加文本注入的朴素路线。另一个值得关注的方案是 mem0，一个开源的 AI 记忆层，GitHub 51000+ star，代表了完全不同的设计哲学。

存储策略

mem0 的记忆存储分为三个环节：提取、向量化、图谱化。

提取环节。 当一轮对话结束后，mem0 用一次 LLM 调用从对话上下文中提取结构化事实。输入由两部分拼接：异步维护的对话摘要，以及最近 N 条消息的滑动窗口。LLM 被提示为”个人信息整理器”，按习惯、计划、专业信息、偏好等维度提取具体细节，输出为 JSON 格式的 facts 数组。例如，从对话”我最近在用 pnpm，之前的 npm 太慢了”中提取出 ["用户使用 pnpm 作为包管理器", "用户认为 npm 速度慢"]。每轮对话的提取成本约 7000 token。

向量化存储。 每条提取出的自然语言事实被送入 embedding 模型（默认 OpenAI text-embedding-3-small，也支持 Qwen、AWS Bedrock 等）生成稠密向量，写入向量数据库。支持的向量数据库包括 Qdrant（托管服务默认）、Pinecone、Milvus、pgvector、FAISS 等。每条记忆附带时间戳、用户 ID、会话 ID 等元数据。

图谱存储。 V3 之前，mem0 集成外部图谱数据库（Neo4j、Memgraph、Kuzu、Amazon Neptune）存储实体关系。V3 版本（2026 年发布）废弃了外部图谱驱动，改为内置实体链接：用二级向量集合存储实体嵌入，通过向量相似度发现交叉引用关系，不再需要独立的图谱基础设施。图谱的构建分两步：实体提取器识别对话中的关键元素和类别，关系生成器构建语义三元组（如”用户 → 偏好 → pnpm”）。启用图谱后每轮对话的提取成本翻倍，约 14000 token。

作用域。 mem0 支持四级记忆作用域：User Memory 跨所有会话持久化用户偏好；Session Memory 限定在单次会话内；Agent Memory 存储 Agent 级别的状态和学习到的事实；Run Memory 限定在单次执行中。多用户场景下通过 user_id 隔离，天然支持群聊记忆。

检索策略

mem0 的检索是一个多信号并行评分、融合排序的管线。V3 版本的具体流程：

第一步：查询编码。 用户的当前 prompt 被送入 embedding 模型生成稠密查询向量。

第二步：三路并行检索。

  • 语义相似度路径：查询向量与存储的事实向量计算余弦距离，返回 top-K 最相似的自然语言事实。这是稠密检索，擅长捕捉语义层面的关联。
  • BM25 路径：对查询做稀疏词法匹配，基于 TF-IDF 变体对记忆库做关键词检索。擅长精确匹配专有名词、技术术语等向量容易丢失的细节。
  • 实体匹配路径：从查询中提取实体，遍历实体向量集合找到关联的实体和关系三元组。擅长回答”用户的 X 是什么”这类结构化查询。

第三步：时间权重提升（Temporal Boosting）。 每条候选记忆根据时间新鲜度加权。近期记忆的得分被提升，久远记忆的得分被衰减。mem0 支持配置记忆衰减策略，包括 TTL 过期机制和不可变标记（immutability flags）。标记为不可变的记忆不参与衰减。

第四步：融合排序。 三路得分与时间权重合并，生成最终排序。可选的 explain 参数暴露每条记忆的评分细项，供调试使用。

第五步：Reranking（可选）。 托管平台提供内置 reranker 模型做精排。自部署版本可配置自定义 reranker。

与 Claude Code 的 Sonnet Bypass 对比：Claude Code 只扫描 frontmatter 做字面关键词匹配，mem0 的三路融合检索覆盖面更广，但也意味着每次检索需要多次向量查询和 LLM 调用，延迟和成本更高。

冲突解决

mem0 的冲突解决经历了从”写入时裁决”到”检索时推理”的范式转变。

V1/V2：写入时四操作模型。 新事实被提取后，系统用一次 LLM 调用将其与已有记忆逐条比较，通过 tool call 选择四种操作之一：

操作 语义 示例
ADD 新建记忆 首次记录”用户使用 pnpm”
UPDATE 修改已有记忆，保留原始 ID，替换为信息量更大的版本 “用户使用 pnpm” → “用户使用 pnpm 9.x，要求 monorepo 工作区”
DELETE 删除被推翻的事实 用户明确说”我不用 pnpm 了” → 删除 pnpm 相关记忆
NOOP 事实已被覆盖，无需操作 重复记录”用户使用 pnpm”

这个模型的问题在于：每次写入都需要 LLM 评估新事实与所有相关记忆的关系，成本高且评估不稳定。如果 LLM 误判为 NOOP，有价值的信息会丢失；如果误判为 UPDATE，可能破坏仍有价值的旧记忆。

V3：ADD-only 追加策略。 V3 放弃了写入时的 UPDATE 和 DELETE 操作。所有提取出的事实一律追加，不与已有记忆做比较。冲突在检索时通过时间推理动态解决：当多条记忆在语义上相似但在事实上矛盾时（如”用户偏好浅色模式”和”用户偏好深色模式”），检索管线根据时间戳和上下文相关性返回最匹配当前查询的版本。

这个设计的动机是：记忆的价值取决于使用时刻的上下文，而非写入时刻的判断。一条看似过时的记忆在特定场景下可能仍然有用。写入时删除它是不可逆的损失，而检索时忽略它只是暂时的过滤。

图谱冲突处理。 图谱中的矛盾关系不会被删除，而是被 LLM 标记为 invalid。例如”用户 → 偏好 → 浅色模式”被标记为 [invalidated]，但它仍然存在于图谱中。这样做的目的是保留时间上下文：系统可以追溯偏好的变化历史，而不是只看到最新状态。

记忆衰减与过期。 V3 引入了可配置的记忆衰减。每条记忆可以设置 TTL（生存时间），超过 TTL 的记忆在检索时被降权但不删除。标记为不可变的记忆（如”用户的生日”）不受衰减影响。这种设计让系统在保持记忆完整性的同时，自然地将注意力集中在近期信息上。

Claude Code 的冲突解决相比之下简单得多：AutoDream 的 Consolidate 阶段由模型自主判断合并和删除，没有显式的操作分类，也没有图谱级别的关系追踪。本质上完全依赖模型的理解力。

核心取舍

维度 Claude Code（文件方案） mem0（数据库方案）
存储 纯 Markdown 文件 向量数据库 + 实体链接
检索 关键词匹配 frontmatter 语义 + BM25 + 实体融合检索
基础设施 零（一个文本文件即可） 需要向量数据库、embedding 模型、提取 LLM
人类可读性 完全可读、可 diff、可 Git 版本控制 向量不可读，需要工具辅助
自动提取 后台 Agent 提取，质量依赖模型能力 管线化提取，结构化程度更高
可扩展性 文件线性增长，大规模时消耗上下文 token 向量搜索可高效扩展到百万级记忆
token 效率 整个文件注入上下文 只返回相关片段，节省 90%+ token
多用户支持 单用户设计 内置 user/session/agent 多级作用域
时间感知 手动写入日期 + 检索时新鲜度标注 内置时间戳、衰减、过期、temporal boosting

两者的根本取舍是能力 vs 简洁。mem0 在自动提取、可扩展检索、时间推理上有明显优势，适合多用户、高频交互、大规模记忆的生产环境。Claude Code 的文件方案在可调试性、确定性、零基础设施依赖上有不可替代的价值，适合单用户开发场景。

一个有趣的趋势是：mem0 V3 转向 ADD-only 追加策略，在哲学上更接近文件系统的 append-only 日志；而 Claude Code 的 AutoDream 整合机制，本质上也引入了结构化的记忆维护流程。两个方案在向对方靠近。

设计思路的启示

Claude Code 的记忆系统没有使用向量数据库或语义检索，而是选择了最朴素的方案：Markdown 文件加文本注入。这个选择背后有几个考量：

可调试性。所有记忆都是纯文本文件，开发者可以直接查看、编辑、版本控制。不存在黑盒。

确定性。文件在不在、内容是什么、加载了什么，都是确定的。不像向量检索那样存在相关性排序的不确定性。

可控性。四级层级体系加上条件触发，开发者可以精确控制什么信息在什么时候被加载。

成本可控。按需加载和路径限制避免了上下文窗口被无关规则占满的问题。

但 AutoDream 和 mem0 的存在也揭示了文件方案的局限。当记忆规模增长到数百条，200 行的索引和关键词匹配会逐渐力不从心。AutoDream 通过定期整合延缓了这个问题，但没有根本解决。mem0 的向量检索和时间推理则展示了数据库方案在规模化和精度上的优势。

对于构建 AI Agent 系统，选择哪种方案取决于场景。单用户开发工具，Claude Code 的文件方案足够好，零基础设施、完全透明。多用户生产系统，mem0 这类结构化记忆层是更合适的选择。两种方案正在相互借鉴：文件方案在引入自动整合，数据库方案在引入追加语义。记忆系统的演进方向，可能是两者的融合。
