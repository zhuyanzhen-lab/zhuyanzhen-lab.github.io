Claude Code 记忆机制深度解析

LLM 本质上是无状态的。每次对话结束，上下文清空，一切归零。这意味着你上一轮花了 20 分钟教 AI 理解的项目架构、编码规范、调试经验，下一轮全部丢失。

Claude Code 通过一套分层的记忆系统解决了这个问题。这套系统的核心思路很直接：把需要记住的东西写成 Markdown 文件，每次启动时注入到上下文中。没有向量数据库，没有 RAG，没有复杂的记忆检索算法，就是纯文本文件的读取和拼接。

双轨记忆模型

Claude Code 的记忆分为两条轨道：

人工配置轨道。开发者手动维护的 CLAUDE.md 文件和 rules 规则库。内容是项目架构、编码规范、常用命令等确定性知识。每次会话启动时完整注入上下文。

AI 自主学习轨道。Auto Memory 机制。AI 在交互过程中自动记录调试经验、用户偏好纠正、踩过的坑。启动时只加载摘要索引，具体内容按需检索。

两者的关系是：你定基调，AI 补细节。

CLAUDE.md：人工记忆的核心载体

CLAUDE.md 是 Claude Code 记忆系统中最基础也最重要的文件。它的定位是”每次会话都应该知道的事实”。

四级层级体系

CLAUDE.md 不只是一个文件，而是一个从宏观到微观的四级体系。系统会沿目录树向上搜集并合并所有找到的文件，后加载的覆盖先加载的：

企业级。存放在操作系统级别的受保护目录，如 macOS 的 /Library/Application Support/ClaudeCode/CLAUDE.md。用于公司层面的合规要求，个人无法绕过。

用户级。位于 ~/.claude/CLAUDE.md，跨所有项目生效。适合存放个人编码偏好，比如”始终使用 TypeScript strict 模式””注释用中文”。

项目级。放在工程根目录的 CLAUDE.md 或 .claude/CLAUDE.md，纳入版本控制。这是团队共享的项目规范，包括技术栈说明、架构约定、构建命令等。

本地覆盖。带 .local 后缀的同级文件，如 CLAUDE.local.md。专用于本地调试，排除在 Git 提交之外。

还有一个容易忽略的机制：子目录级。项目子目录中也可以放 CLAUDE.md，但不会在启动时全量加载。只有当 AI 访问该目录的代码时，才按需加载对应的配置。这个设计有效控制了 token 消耗。

编写原则

控制在 200 行以内。这是官方建议。文件越长，模型的遵从度越低，注意力越容易分散。

使用祈使句，提供具体信息。”使用 pnpm 而非 npm””Python 版本为 3.12””数据库连接字符串从 .env 读取”比”注意使用正确的包管理器”有效得多。

规则要可验证。”代码要有良好的错误处理”是模糊的，”所有 API 端点必须包含 try-catch 且返回标准化错误格式”是可验证的。模糊规则等于没有规则。

用 @ 语法引用外部文档。如果某个规范太长不适合直接写入 CLAUDE.md，可以用 @docs/api-convention.md 引用。但注意这是全文注入，不会节省上下文空间。

初始化方式

在项目根目录执行 /init 命令，AI 会分析当前目录结构并自动生成 CLAUDE.md 骨架。生成后建议手动审查和调整，不要完全依赖自动生成。

.claude/rules/：模块化规则库

当项目规模增大，单一 CLAUDE.md 无法承载所有规范时，可以将规则分散到 .claude/rules/ 目录中。

这个目录的核心特性是条件触发。通过 YAML frontmatter 中的 paths 字段定义匹配模式，规则只在 AI 操作相关文件时才被激活：

---
paths:
  - "src/api/**/*.ts"
---
# API 开发规范
- 端点必须包含输入验证
- 错误响应统一使用 ApiError 类
- 所有公开接口需要 JSDoc 注释

这比全部塞进 CLAUDE.md 的优势在于：不相关的规则不会占用上下文窗口。一个有 200 个文件的大型项目可能有 20 个规则文件，但每次对话实际加载的可能只有 2 到 3 个。

Auto Memory：AI 的自主笔记本

Auto Memory 是 Claude Code 在交互过程中自动积累的经验记录。它不需要人工维护，AI 会自己判断哪些信息值得记住。

存储位置

数据存储在 ~/.claude/projects/<project-hash>/memory/ 下，按 Git 仓库路径推导出专属目录。这意味着同一个代码库的不同分支和工作树共享同一份记忆。

加载机制

核心文件 MEMORY.md 充当索引，每次会话启动时加载前 200 行或 25KB。如果记忆内容超出这个范围，系统会按主题拆分，详细笔记静默存储，待特定场景下被模型主动检索。

典型记录内容

  • 调试过程中发现的坑和解决方案
  • 用户反复纠正的偏好，比如”不要用 any 类型””错误日志要包含 request id”
  • 项目特有的构建陷阱
  • 某次修复的关键步骤

管理方式

Auto Memory 默认启用，纯本地存储，不同步到云端或 Git。用户可以通过 /memory 命令查看、编辑、删除记忆条目，也可以通过环境变量 CLAUDE_CODE_DISABLE_MEMORY 全局禁用。

会话启动时的记忆加载流程

一次新会话启动时，记忆加载的完整流程如下：

  1. 读取企业级 CLAUDE.md，如果存在
  2. 读取用户级 ~/.claude/CLAUDE.md
  3. 从当前目录向上遍历，合并所有项目级 CLAUDE.md 和 CLAUDE.local.md
  4. 加载 .claude/rules/ 中无条件触发的规则
  5. 读取 Auto Memory 的 MEMORY.md 索引文件
  6. 将以上内容拼接注入 system prompt

子目录的 CLAUDE.md 和带 paths 条件的 rules 文件在这一步不加载，等 AI 实际访问相关代码时再按需注入。

记忆失效的场景与应对

规则被忽略

常见原因有三个：文件不在有效路径上、指令过于模糊、不同文件之间存在冲突规则。排查方法是用 /memory 命令确认文件是否被加载。

如果某条规则必须被严格执行，不应依赖 CLAUDE.md，而应使用 Hooks 机制。Hooks 可以在工具调用前后执行脚本，实现硬性拦截。比如禁止执行某些命令、自动格式化代码等。Hooks 是确定性的代码执行，不存在”模型可能不遵守”的问题。

上下文压缩导致遗忘

长对话中，Claude Code 会执行上下文压缩以节省 token。压缩后的行为：

  • 根目录的 CLAUDE.md 和 rules 会自动重新加载，具备抗压缩能力
  • 子目录的配置需要等 AI 再次访问该目录才能重新激活
  • Auto Memory 的索引会保留，但详细笔记需要重新检索

这意味着核心规则应该放在根目录，而非子目录。

设计思路的启示

Claude Code 的记忆系统没有使用向量数据库或语义检索，而是选择了最朴素的方案：Markdown 文件加文本注入。这个选择背后有几个考量：

可调试性。所有记忆都是纯文本文件，开发者可以直接查看、编辑、版本控制。不存在黑盒。

确定性。文件在不在、内容是什么、加载了什么，都是确定的。不像向量检索那样存在相关性排序的不确定性。

可控性。四级层级体系加上条件触发，开发者可以精确控制什么信息在什么时候被加载。

成本可控。按需加载和路径限制避免了上下文窗口被无关规则占满的问题。

这套方案对于构建其他 AI Agent 系统也有参考价值。记忆不一定要用复杂的检索系统，简单的文件加载在大多数场景下就足够了。关键在于分层设计和按需加载的策略。
