Demystifying Evals for AI Agents 学习笔记

AI Agent 评测 Anthropic
发布日期:   2026-07-24

Demystifying Evals for AI Agents 学习笔记

原文：Demystifying evals for AI agents — Anthropic Engineering Blog

这篇来自 Anthropic 工程团队的文章，系统性地讲解了如何为 AI Agent 构建有效的评测体系。对于正在做 Agent 开发或者想把 Agent 从 Demo 推向生产的人来说，这篇文章几乎是必读材料。以下是我的学习笔记。

为什么 Agent 评测这么难

传统的 LLM 评测相对简单：给一个 prompt，看一个 response，打个分就行了。但 Agent 不一样——它会跨多轮对话、调用工具、修改外部状态，整个执行过程是一个动态链条。这意味着：

  • 同一个输入可能产生不同的执行路径
  • 中间步骤的正确性同样重要（不仅仅是最终结果）
  • 系统行为受到模型、prompt、工具链、环境状态的共同影响

文章指出，很多团队在早期靠直觉和手动检查来评估 Agent，这在原型阶段还行，但一旦要规模化部署就会”盲飞”——用户报告问题时根本不知道是 regression 还是 random noise。

核心术语速查

文章先统一了一套术语体系，理解这些概念是后续讨论的基础：

术语 含义
Task 一个具体的测试用例，包含输入和成功标准
Trial 一次执行尝试
Grader 评估性能的逻辑（可以是代码、模型或人类）
Transcript 完整的交互记录，包括推理过程和工具调用
Outcome 最终的环境状态（不是 Agent 说了什么，而是实际做了什么）
Evaluation harness 执行测试的基础设施
Agent harness 让模型能够行动的脚手架（工具调用、上下文管理等）
Evaluation suite 一组针对特定行为的测试集合

这里有一个我觉得很重要的区分：Transcript 和 Outcome 是不同的。一个 Agent 可能最终达成了正确结果但中间过程一塌糊涂，也可能中间步骤很优雅但最终失败了。好的评测应该同时关注这两者。

三种 Grader 类型

这是文章的一个核心框架。评测 Agent 的打分方式主要有三种，各有优劣：

1. 代码打分（Code-based）

用正则表达式、lint 检查、单元测试等确定性逻辑来判定。优点是快、无偏见、可重复；缺点是无法处理主观性判断。

适用场景：代码正确性验证、格式检查、工具调用参数验证。

2. 模型打分（Model-based）

用另一个 LLM 作为裁判，配合评分 rubric 来打分。擅长处理主观任务（比如”回复是否友好”），但需要确保裁判模型和人类判断的一致性。

关键技巧：给 LLM 裁判一个 “I don’t know” 选项，避免它在不确定的时候胡编评分。

3. 人类打分（Human）

请领域专家或众包工人来评判。信号质量最高，但又贵又慢。

实际建议：三种方式组合使用。代码打分处理确定性检查，模型打分处理主观判断，人类打分做定期校准。

Capability Test vs. Regression Test

这个分类很实用：

  • Capability Test（能力测试）：衡量系统能做什么。初始通过率很低（比如 20%），随着迭代逐步提升。适合用来驱动开发方向。
  • Regression Test（回归测试）：确保已经能做的事情不会退化。目标通过率接近 100%。

一个重要实践：当某个 capability test 的通过率稳定在高位时，就应该把它迁移到 regression suite 中。这样 regression suite 会随着产品成熟不断壮大，形成越来越厚的安全网。

不同场景的评测策略

文章针对几种典型的 Agent 场景给出了具体建议：

编程类 Agent

使用确定性单元测试作为主要 grader（比如 SWE-bench 的做法）。但不仅要看最终代码是否通过测试，还要看交互轨迹——Agent 是优雅地解决了问题，还是暴力试错碰巧通过？

推荐组合：单元测试 + 静态分析 + LLM 评分（代码质量）。

对话类 Agent

需要多维度打分：状态变更是否正确、对话轮数是否合理、语气是否得当。通常用另一个 LLM 模拟用户角色。

推荐组合：状态验证 + 轮数限制检查 + 语气评分。

研究类 Agent

质量高度主观。需要评估内容的 groundedness（是否有据可依）、fact coverage（信息覆盖度）和 source authority（来源权威性）。LLM 裁判需要频繁和人类做校准。

计算机操作类 Agent

Agent 通过 GUI 与系统交互。评测时需要在 DOM 提取（token 密集但精确）和截图（慢但高效）之间找平衡。

处理非确定性：pass@k 和 pass^k

Agent 的输出天然是非确定性的。同一个任务跑 10 次可能得到 7 次成功 3 次失败。文章引入了两个关键指标：

  • pass@k：k 次尝试中至少成功一次的概率。适合”只要有一次对就行”的场景（比如代码生成）。
  • pass^k：k 次尝试全部成功的概率。适合面向用户的场景——用户不会容忍”偶尔失败”。

这两个指标的差异非常重要。一个 Agent 的 pass@10 可能是 95%，但 pass^10 可能只有 30%。前者告诉你”它有能力做到”，后者告诉你”它在实际使用中靠不靠谱”。

面向用户的系统应该关注 pass^k，而不是 pass@k。

从零到一的实施路线图

这是文章最实用的部分，给出了 8 个递进步骤：

Step 0：立刻开始。 不要追求完美，先用一小批真实失败案例建起初始测试集。

Step 1：自动化已有检查。 把手动 QA 流程、Bug 报告转化为自动测试。

Step 2：设计清晰的任务。 每个 task 应该有明确的输入和已知的正确输出。模糊的任务会产生噪音指标。提供参考答案（reference solution）来证明这个任务确实可解。

Step 3：构建平衡的数据集。 不仅测试”应该使用工具”的场景，还要测试”不应该使用工具”的场景，避免单向优化。

Step 4：隔离测试环境。 防止共享状态导致测试结果互相干扰或产生关联失败。

Step 5：设计灵活的 Grader。 评估最终结果而非固定路径。允许部分得分。给 LLM 裁判 “unknown” 选项来避免幻觉评分。

Step 6：阅读执行轨迹。 不要只看分数。检查失败案例是真正的 Agent 错误还是 Grader 的 bug。

Step 7：关注饱和。 当某个测试集通过率稳定在 100%，它就不再驱动改进了——需要更难的任务。

Step 8：长期维护。 把评测当作标准的单元测试来维护，鼓励跨团队贡献测试用例。

瑞士奶酪模型：多层防护

文章最后推荐了一个整体性的质量保障框架——瑞士奶酪模型（Swiss Cheese Model）。每一层都有洞，但多层叠在一起就能覆盖大多数问题：

  1. 自动化测试：快速迭代，发布前的基本保障
  2. 生产监控：真实世界的 ground truth
  3. A/B 测试：衡量实际用户指标
  4. 用户反馈：捕获意想不到的边界情况
  5. 手动轨迹审查：建立开发者对系统的直觉
  6. 系统性人类研究：评估主观、复杂的领域

没有任何单一方法能覆盖所有问题，但这个组合能形成足够的安全网。

个人总结

这篇文章最大的价值在于它提供了一个从理念到落地的完整框架。不是告诉你”评测很重要”就结束了，而是给了你具体的术语、方法、指标和实施步骤。

几个我觉得值得记住的要点：

  1. 评测不是上线前才做的事，而是从第一天就该开始的实践（eval-driven development）
  2. 区分 Transcript 和 Outcome——过程正确但结果错误，和过程混乱但结果正确，需要不同的修复策略
  3. pass^k 比 pass@k 更能反映真实可靠性——用户不会因为你”偶尔能做到”就满意
  4. Grader 本身也会出 bug——一定要定期 review 评测逻辑，而不只是看分数
  5. 基础设施（Harbor、Braintrust、LangSmith 等）是手段，核心投资应该在高质量的 Task 和 Grader 上
