SQL 注入原理与防御指南

SQL注入
发布日期:   2026-08-03

SQL 注入是 Web 安全中最经典也最持久的漏洞类型之一。理解它的本质，不需要大量工具记忆，核心在于理解一条原则：当用户输入被当作 SQL 指令执行时，注入就发生了。

注入原理

根本原因

SQL 注入的根源是数据与指令的边界混淆。

在正常的 SQL 执行流程中，应用程序将用户输入拼接到 SQL 语句中，数据库引擎解析这条语句并执行。问题在于，数据库引擎在解析时无法区分”开发者写的固定指令”和”用户提供的数据”。当用户输入中包含 SQL 语法字符（如单引号 '、分号 ;、注释符 --）时，这些字符会改变原始 SQL 语句的逻辑结构。

以一个典型的登录查询为例：

SELECT * FROM users WHERE username='[input]' AND password='[input]'

正常情况下，用户输入 admin 作为用户名，拼接后：

SELECT * FROM users WHERE username='admin' AND password='[input]'

如果攻击者输入 ' OR '1'='1 作为用户名，拼接后变成：

SELECT * FROM users WHERE username='' OR '1'='1' AND password='[input]'

'1'='1' 恒为真，OR 条件使整个 WHERE 子句永远成立，查询返回所有用户记录。攻击者绕过了认证。

注入的本质

从更抽象的层面看，SQL 注入是一种注入攻击（Injection Attack）的特例。所有注入攻击的共同特征是：外部输入未经充分处理就被嵌入到目标语言的执行上下文中。SQL 注入的目标语言是 SQL，类似的还有命令注入（目标是 Shell）、XSS（目标是浏览器 JS 引擎）、SSTI（目标是模板引擎）。

理解这一点很重要，因为防御思路是通用的：在数据进入执行上下文之前，消除其作为指令的能力。

常见注入方法

联合查询注入（UNION 注入）

适用条件：页面有回显，且原始查询的列数可知。

原理：利用 UNION SELECT 将恶意查询结果附加到原始查询结果中，直接在页面上显示。

步骤：

  1. 确定列数。使用 ORDER BY n 逐步增大 n，直到报错，前一个成功的 n 即为列数。或者使用 UNION SELECT NULL,NULL,... 逐个试探。

  2. 确定回显位置。在 UNION SELECT 的各列中填入不同的可识别值（如 1,2,3），观察页面显示哪些值，这些位置就是可控的回显点。

  3. 提取数据。在回显点替换为目标查询，如 version()、database()、GROUP_CONCAT(table_name) 等。

?id=1 UNION SELECT 1,username,password,4 FROM users--

布尔盲注

适用条件：页面无直接数据回显，但能区分查询结果为真或为假时的不同页面状态（如正常显示 vs “记录不存在”）。

原理：逐位猜测目标数据。每次注入一个布尔条件，根据页面响应判断条件是否成立。

?id=1 AND SUBSTRING((SELECT password FROM users LIMIT 1),1,1)='a'

如果页面正常，说明密码第一位是 a；如果页面异常，继续尝试 b、c… 对每一位重复此过程。

效率优化：使用二分法将每位字符的猜测次数从最多 128 次降到 7 次。

?id=1 AND ASCII(SUBSTRING((SELECT password FROM users LIMIT 1),1,1))>64

时间盲注

适用条件：页面既无数据回显，也无法通过布尔条件区分真假（所有响应页面完全相同）。

原理：利用条件语句控制数据库的延迟响应。通过 SLEEP() 或类似函数，根据响应时间推断数据。

?id=1 AND IF(ASCII(SUBSTRING(database(),1,1))>100, SLEEP(3), 0)

如果页面响应延迟 3 秒，说明条件成立（数据库名首字符 ASCII 大于 100）。

时间盲注是效率最低的注入方式，通常需要借助自动化工具（如 sqlmap）批量执行。

报错注入

适用条件：页面不显示查询结果，但会显示数据库的错误信息。

原理：构造使数据库引擎报错的表达式，错误信息中携带目标数据。

MySQL 常用方法：

?id=1 AND EXTRACTVALUE(1, CONCAT(0x7e, (SELECT database()), 0x7e))

EXTRACTVALUE 的第二个参数期望是合法的 XML 路径，传入非 XML 格式的数据会触发错误，错误信息中包含拼接的 database() 结果。

其他函数：UPDATEXML()、FLOOR() + GROUP BY + COUNT() 利用主键重复报错。

堆叠注入

适用条件：数据库引擎和 API 支持执行多条 SQL 语句（用分号分隔）。

原理：在原始查询后追加新的 SQL 语句，执行任意操作（增删改查、创建用户、写文件等）。

?id=1; DROP TABLE users--

MySQL 的 mysqli_multi_query() 支持堆叠，但 PDO + MySQL 默认不支持。SQL Server 和 PostgreSQL 默认支持。堆叠注入的危害远大于数据泄露，攻击者可以执行任何数据库操作。

二次注入

适用条件：用户输入被存储到数据库，后续被取出拼接成新的 SQL 语句。

原理：第一次输入时，恶意数据被原样存储（转义处理使其安全入库）。第二次取出使用时，数据被再次拼接到 SQL 语句中，此时没有经过转义，触发注入。

典型场景：用户注册时用户名为 admin'-- （带尾随空格），系统存储了这个值。后续修改密码时，查询使用 WHERE username='[从数据库取出的用户名]'，此时 admin'-- 导致条件变为 WHERE username='admin'，修改的是 admin 账户的密码。

二次注入比反射型注入更隐蔽，因为恶意数据在存储阶段不会触发任何异常。

防御方法

参数化查询（预编译语句）

这是防御 SQL 注入最根本、最有效的方法。

原理：参数化查询将 SQL 语句的结构定义与数据传递分离。应用程序先将 SQL 模板（带占位符）发送给数据库引擎，引擎解析并编译这条语句的结构。之后，应用程序再发送参数值，引擎将其作为纯数据处理，不会重新解析语句结构。

// Java JDBC 示例
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement stmt = conn.prepareStatement(sql);
stmt.setString(1, username);
stmt.setString(2, password);
ResultSet rs = stmt.executeQuery();

# Python DB-API 示例
cursor.execute(
    "SELECT * FROM users WHERE username = %s AND password = %s",
    (username, password)
)

无论用户输入什么内容，? 或 %s 占位符位置的值始终被当作数据处理，不可能改变 SQL 语句的逻辑结构。这是从协议层面消除了注入的可能性。

输入验证

作为参数化查询的补充，不单独作为防御手段。

白名单验证：对已知合法输入定义精确规则。如用户 ID 只允许纯数字，邮箱必须符合 RFC 格式。

黑名单过滤：移除或转义特定字符（如单引号、分号）。不推荐作为主要防御，因为黑名单难以穷举所有变体（编码绕过、Unicode 混淆等）。

转义处理：对特殊字符添加转义符（如 ' → \'）。MySQL 的 mysql_real_escape_string() 就是这种方式。但转义容易遗漏，且与字符集配置相关，存在绕过风险。

最小权限原则

限制数据库账户的权限范围。

应用程序使用的数据库账户不应拥有 DBA 权限。只授予必要的 SELECT、INSERT、UPDATE、DELETE 权限，禁止 FILE、SUPER、GRANT 等高权限。这样即使发生注入，攻击者的操作范围也受到限制。

为每个应用或模块使用独立的数据库账户，避免一个账户访问所有表。

WAF（Web 应用防火墙）

在网络层对 HTTP 请求进行规则匹配，拦截包含注入特征的请求。

WAF 可以作为纵深防御的一层，但不应作为唯一防线。绕过 WAF 的技术很多：编码变换（URL 编码、Unicode、Hex）、分块传输（Chunked Transfer）、注释混淆、大小写混合等。

ORM 框架

使用 ORM（如 SQLAlchemy、Hibernate、ActiveRecord）操作数据库，ORM 内部默认使用参数化查询，从框架层面避免拼接 SQL。

注意：ORM 不是万能的。如果开发者在 ORM 中使用了原生 SQL 拼接（如 SQLAlchemy 的 text() 或 execute(raw_sql)），同样会产生注入风险。

防御优先级

按有效性排序：

  1. 参数化查询。从协议层面消除注入，是唯一的根本解决方案。
  2. ORM 框架。封装了参数化查询，降低开发者犯错概率。
  3. 最小权限。限制注入成功后的影响范围。
  4. 输入验证。减少攻击面，作为辅助手段。
  5. WAF。网络层过滤，作为最后一道防线。

核心原则只有一条：确保用户输入永远不被当作 SQL 指令执行。参数化查询是唯一从结构上保证这一点的方法，其他手段都是补充或兜底。
