HTTP 请求响应全景：从协议结构看 Web 攻击的本质

安全 Web安全 HTTP
发布日期:   2026-08-07

引言：为什么要从协议层理解攻击

XSS、CSRF、文件上传是 Web 安全中最常见的三类漏洞。表面上看它们各不相同——XSS 是脚本注入，CSRF 是请求伪造，文件上传是恶意文件写入。但如果回到 HTTP 协议层面，会发现它们攻击的是同一条通信链路的不同环节。

一条完整的 Web 交互包含两部分：客户端发给服务端的请求（Request），和服务端返回给客户端的响应（Response）。请求中有方法、URL、请求头、请求体；响应中有状态码、响应头、响应体。每一部分都可能成为攻击面。

本文先完整拆解请求和响应的每一个组成部分，然后将 XSS、CSRF、文件上传三种攻击映射到这条链路上，最后分析它们之间的关联和各自的防御侧重。

一、HTTP 请求的完整结构

一个 HTTP 请求由四部分组成：请求行、请求头、请求体、以及底层 TCP/TLS 连接。攻击面分布在这四层的每一个字段中。

1.1 请求行

POST /api/transfer HTTP/1.1
│      │            │
│      │            └── 协议版本
│      └── URL 路径（含查询参数）
└── HTTP 方法

方法（Method）： GET、POST、PUT、DELETE 等。方法决定了服务端如何处理这个请求，也决定了攻击者能做什么。

GET 请求的参数在 URL 中，可以被 <img src>、<link href>、<a href> 等标签直接触发。这就是 GET 型 CSRF 的基础——攻击者不需要 JS，一个 HTML 标签就能发出请求。

POST 请求的参数在请求体中，需要 <form> 表单或 JS 才能构造。这提高了 CSRF 的攻击门槛，但并没有根本阻止。

URL 路径和查询参数： https://bank.com/search?q=<script>alert(1)</script>

URL 中的查询参数（?q=xxx）是反射型 XSS 最常见的注入点。服务端从 URL 中取出参数值，未经转义拼入 HTML 响应，浏览器解析时执行注入的脚本。

URL 路径本身也可能成为注入点。$_SERVER['PHP_SELF'] 包含当前 URL 路径，如果直接用于 form action 属性，路径部分可被注入：访问 /page.php/<script>alert(1)</script>，PHP_SELF 的值为 /page.php/<script>alert(1)</script>。

1.2 请求头

请求头是键值对，每行一个 Key: Value。以下是与安全直接相关的关键请求头：

Host： 指定目标主机。虚拟主机环境下，一个 IP 服务多个域名，服务端根据 Host 头决定路由。Host 头注入可能导致密码重置链接指向攻击者的服务器。

Content-Type： 告诉服务端请求体的格式。

Content-Type: application/x-www-form-urlencoded   ← 表单默认
Content-Type: multipart/form-data; boundary=xxx    ← 文件上传
Content-Type: application/json                      ← API 常用
Content-Type: text/plain                            ← 纯文本

文件上传攻击的入口就是 multipart/form-data。请求体按 boundary 分割为多个部分，每个部分有自己的 Content-Disposition（含文件名）和 Content-Type。这两个字段完全由客户端控制，服务端不能信任——这是文件上传安全问题的根源。

CSRF 攻击中，Content-Type 也是一道天然屏障。HTML 表单只能发送 application/x-www-form-urlencoded、multipart/form-data、text/plain 三种类型。如果服务端只接受 application/json，传统表单无法直接伪造。

Cookie： 浏览器自动携带目标域的 Cookie。这是 CSRF 攻击的核心——浏览器不区分请求是用户主动发起的还是被第三方页面诱导发出的，只要目标域有 Cookie 就自动带上。

Cookie: session_id=abc123; csrf_token=xxx

如果 Cookie 没有设置 SameSite 属性，跨站请求也会携带。如果设置了 HttpOnly，JavaScript 无法读取（降低 XSS 窃取 Cookie 的风险）。如果设置了 Secure，只通过 HTTPS 传输。

Origin / Referer： 标识请求来源。

Origin: https://attacker.com
Referer: https://attacker.com/page?id=1

Origin 只在跨域 POST 中发送，格式为 scheme://host:port（不含路径）。Referer 在所有请求中发送，包含完整 URL。服务端可以用它们校验请求来源是否合法，但这两个头也可能被隐私插件剥离。

CORS 机制中，浏览器发送的 Origin 头和服务端返回的 Access-Control-Allow-Origin 响应头共同决定了跨域请求是否被允许。如果服务端动态反射 Origin（把请求的 Origin 原样返回），等于对所有域开放 CORS。

自定义安全头：

X-Requested-With: XMLHttpRequest
X-CSRF-Token: rAnd0mV4lu3

服务端可以用自定义头做 CSRF 校验——HTML 表单和 <img> 标签无法设置自定义头，所以要求必须有自定义头就能挡住传统 CSRF 手段。但这只挡住了不会 JS 的攻击者，fetch 可以设置任意自定义头，此时需要配合 CORS 策略兜底。

1.3 请求体

请求体是请求的实际数据载荷。根据 Content-Type 不同，格式不同：

表单编码（application/x-www-form-urlencoded）：

username=admin&password=123&redirect=%2Fdashboard

键值对用 & 分隔，特殊字符做 URL 编码。这是最传统的请求体格式，也是 CSRF 表单攻击的标准格式。

JSON（application/json）：

{"username": "admin", "password": "123", "role": "user"}

现代 API 的标准格式。JSON 格式对 CSRF 有一定天然防护（表单无法直接发送 JSON），但如果 CORS 配置错误，fetch 可以绕过。

Multipart（multipart/form-data）：

------WebKitFormBoundary
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: application/x-php

<?php phpinfo(); ?>
------WebKitFormBoundary--

文件上传的专用格式。filename 和每部分的 Content-Type 完全由客户端控制。攻击面包括：文件名注入（路径穿越、SQL 注入、命令注入）、文件类型伪造（扩展名、MIME、Magic Number）、文件内容（WebShell、图片马、SVG XSS）。

1.4 底层连接

HTTP 运行在 TCP/TLS 之上。TLS 保证传输加密，但如果证书校验不严（如客户端禁用证书校验），中间人可以截获和篡改请求内容。

二、HTTP 响应的完整结构

服务端处理完请求后，返回一个 HTTP 响应。响应也由三部分组成：状态行、响应头、响应体。

2.1 状态行

HTTP/1.1 200 OK
│          │    │
│          │    └── 状态描述
│          └── 状态码
└── 协议版本

状态码本身一般不直接构成攻击面，但某些状态码与安全问题相关：302 重定向可能被利用做开放重定向（Open Redirect），403/404 页面的信息泄露可能暴露系统版本和路径。

2.2 响应头

响应头是服务端告诉浏览器”如何处理这个响应”的指令。以下是与安全直接相关的关键响应头：

Content-Type： 告诉浏览器响应的 MIME 类型。

Content-Type: text/html; charset=utf-8
Content-Type: application/json
Content-Type: image/jpeg

如果服务端返回 JSON 数据但 Content-Type 错误设置为 text/html，浏览器会把 JSON 当 HTML 解析。如果 JSON 中包含用户可控数据（如用户名），其中的 <script> 标签会被执行。这就是为什么 API 必须正确设置 Content-Type: application/json。

Content-Disposition： 告诉浏览器是内联显示还是作为附件下载。

Content-Disposition: inline                          ← 浏览器直接渲染
Content-Disposition: attachment; filename="file.jpg" ← 强制下载

对于用户上传的文件，设置 Content-Disposition: attachment 可以阻止 SVG/HTML 文件的 XSS 执行——浏览器会下载而不是渲染它。

X-Content-Type-Options: nosniff： 阻止浏览器 MIME 嗅探。如果 Content-Type 设置错误，浏览器通常会”智能”检测实际内容类型并据此处理。nosniff 让浏览器严格按照声明的 Content-Type 处理，防止 JSON 被当 HTML 解析。

Content-Security-Policy（CSP）： 告诉浏览器哪些来源的脚本可以执行。

Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-xxx'; object-src 'none'

CSP 是 XSS 防御的最后一道防线。即使页面中存在 XSS 注入点，CSP 禁止内联脚本后，大多数 payload 无法执行。

Set-Cookie： 服务端设置 Cookie。

Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/

HttpOnly 阻止 JS 读取 Cookie（防 XSS 窃取会话）。Secure 要求 HTTPS 传输（防中间人）。SameSite 控制跨站请求是否携带（防 CSRF）。这三个标志分别对应不同的攻击类型。

Access-Control-Allow-Origin / Allow-Credentials / Allow-Headers： CORS 响应头，控制哪些域可以跨域访问本资源。

Access-Control-Allow-Origin: https://mysite.com     ← 白名单（安全）
Access-Control-Allow-Origin: *                       ← 所有域（危险）
Access-Control-Allow-Credentials: true               ← 允许携带 Cookie
Access-Control-Allow-Headers: X-CSRF-Token           ← 允许跨域带自定义头

如果 Allow-Origin 动态反射请求的 Origin，等于对所有域开放。配合 Allow-Credentials: true，攻击者可以在自己的页面上用 fetch 携带用户 Cookie 读取敏感数据，或绕过 CSRF Token。

X-Frame-Options: DENY： 阻止页面被 <iframe> 嵌入，防御点击劫持。

2.3 响应体

响应体是服务端返回的实际内容——HTML 页面、JSON 数据、图片、文件等。

HTML 响应体 是 XSS 的主战场。服务端将用户数据拼入 HTML 时，如果没有做输出编码，<script>、onerror、javascript: 等可执行内容会被浏览器解析执行。

JSON 响应体 如果 Content-Type 设置错误（text/html），或者被嵌入到 HTML 页面的 <script> 标签中（var data = {{ user_data | safe }}），也可能触发 XSS。

文件下载响应体 如果是用户上传的文件（图片、文档），可能包含恶意内容（图片马、SVG XSS）。

三、三种攻击在请求响应链路中的映射

现在把 XSS、CSRF、文件上传三种攻击映射到这条链路上，看它们各自攻击的是哪个环节。

3.1 XSS：攻击响应体中的 HTML 渲染

XSS 的核心环节是响应体。攻击者将恶意数据注入到服务端的响应中，浏览器解析响应体时执行恶意脚本。

请求阶段                          响应阶段
┌─────────────────────┐          ┌─────────────────────────────────┐
│ GET /search?q=<script>│ ──→    │ HTML: <p>搜索结果：<script>...</p>│
│                      │         │                                  │
│ 注入点在请求的查询参数 │         │ 恶意数据被拼入响应体的 HTML 中    │
└─────────────────────┘          │                                  │
                                 │ 浏览器解析响应体 → 执行 <script>  │
                                 └─────────────────────────────────┘

攻击的完整链路：

请求阶段：攻击者构造恶意 URL，将 payload 放在查询参数中（?q=<script>...）。

服务端处理：服务端从查询参数中取出值，未经转义拼入 HTML 模板。

响应阶段：响应体中包含未转义的 <script> 标签。

浏览器渲染：浏览器解析 HTML，遇到 <script> 执行其中的 JS。

XSS 的关键防御点在响应阶段： 输出编码（在响应体中将 < 转为 &lt;）和 CSP 响应头（告诉浏览器不要执行内联脚本）。

三种 XSS 在链路上的差异：

反射型：恶意数据在请求参数中 → 服务端回显到响应体 → 浏览器执行。数据经过服务端。

存储型：恶意数据先通过一个 POST 请求写入数据库 → 后续 GET 请求时服务端从数据库取出 → 拼入响应体 → 浏览器执行。数据经过服务端两次（写入和读出）。

DOM 型：恶意数据在 URL hash 中 → 前端 JS 从 location.hash 读取 → 写入 innerHTML → 浏览器执行。数据不经过服务端，完全在客户端流转。

3.2 CSRF：攻击请求阶段中的 Cookie 自动携带

CSRF 的核心环节是请求阶段。攻击者利用浏览器自动携带 Cookie 的行为，以用户身份发出伪造请求。

请求阶段                              响应阶段
┌──────────────────────────┐         ┌──────────────────┐
│ attacker.com 页面中的表单  │ ──→     │ bank.com 处理转账  │
│ <form action=bank.com>    │         │ Cookie 有效，执行  │
│                           │         │                  │
│ 浏览器自动携带 bank.com    │         │ 服务端无法区分     │
│ 的 Cookie 发出跨站请求     │         │ 请求是主动还是伪造 │
└──────────────────────────┘         └──────────────────┘

攻击的完整链路：

请求阶段（攻击者侧）：攻击者在自己的页面上放置 <form> 或 <img>，指向目标站的操作接口。

请求阶段（浏览器侧）：用户访问攻击页面，浏览器加载 <form> 或 <img>，自动携带目标站的 Cookie 发出请求。

服务端处理：服务端收到请求，看到有效的 Cookie，认为是用户本人操作，执行请求中的操作。

响应阶段：服务端返回操作结果（攻击者不关心响应内容）。

CSRF 的关键防御点在请求阶段： SameSite Cookie（阻止跨站携带 Cookie）、CSRF Token（在请求中携带服务端校验的令牌）、自定义请求头（利用表单无法设置自定义头的限制）。

CSRF 不关心响应阶段。 攻击者不需要读取服务端的响应，只需要请求发出去、操作被执行就够了。这与 XSS 形成鲜明对比——XSS 需要在响应体中注入内容，CSRF 只关心请求是否被发出。

3.3 文件上传：攻击请求体中的 multipart 解析

文件上传的核心环节是请求体。攻击者通过 multipart/form-data 格式将恶意文件发送到服务端，服务端解析请求体、提取文件、存储到文件系统。

请求阶段                                响应阶段
┌────────────────────────────┐        ┌────────────────────────┐
│ POST /upload               │ ──→    │ 文件被写入服务器文件系统 │
│ Content-Type: multipart/   │        │                        │
│   form-data; boundary=xxx  │        │ 如果上传目录可执行脚本   │
│                            │        │ → 攻击者访问文件 → RCE  │
│ filename: shell.php        │        │ 如果配合 LFI           │
│ Content-Type: image/jpeg   │        │ → 通过 include() 执行   │
│ 内容: <?php phpinfo(); ?>  │        │ 如果文件名有路径穿越     │
│                            │        │ → 文件写到任意位置       │
│ 请求体中携带恶意文件内容    │        └────────────────────────┘
│ 和伪造的文件名/MIME类型    │
└────────────────────────────┘

攻击的完整链路：

请求阶段：攻击者构造 multipart/form-data 请求，在 filename 中注入路径穿越序列，在文件内容中放入 WebShell，在 Content-Type 中伪造合法 MIME。

服务端处理：解析 multipart 结构，校验文件名和类型（可能被绕过），将文件写入文件系统。

后续请求：攻击者访问上传的文件 URL，如果上传目录可执行脚本，WebShell 被执行。

文件上传的关键防御点横跨请求和服务端两个阶段： 请求阶段校验文件名和类型（白名单、Magic Number），服务端阶段限制上传目录的执行权限、使用随机文件名、隔离存储域名。

四、三种攻击的关联与对比

4.1 攻击位置对比

                    请求阶段                          响应阶段
            ┌──────────────────────┐          ┌──────────────────────┐
            │ 请求行 │ 请求头 │ 请求体 │          │ 响应头 │ 响应体 │
            └──────────────────────┘          └──────────────────────┘
XSS         注入点    ─       ─                CSP     ★ 主战场
            (URL参数)                          (兜底)   (HTML渲染)

CSRF        ─        ★ 主战场  ─                ─       ─
                     (Cookie                   (不关心
                      自动携带)                  响应内容)

文件上传    ─        ─       ★ 主战场           安全响应头  后续访问
                            (multipart          (Content-  (执行恶意
                             文件内容)            Disposition) 文件)

XSS 的主战场在响应体——恶意数据被渲染为可执行代码。CSRF 的主战场在请求头中的 Cookie——浏览器自动携带凭证。文件上传的主战场在请求体中的 multipart 数据——恶意文件被写入服务端。

4.2 攻击者需要什么

XSS 攻击者需要： 找到一个用户输入被回显到 HTML 中且未编码的位置。攻击者需要理解服务端的 HTML 渲染逻辑，找到注入点。

CSRF 攻击者需要： 用户已登录目标站 + 目标站缺乏 CSRF 防御。攻击者不需要理解目标站的内部逻辑，只需要知道操作接口的 URL 和参数格式（通过抓包分析）。

文件上传攻击者需要： 一个文件上传接口 + 上传目录可执行脚本（或配合 LFI）。攻击者需要理解服务端的文件处理逻辑（校验了什么、没校验什么）。

4.3 三者之间的连锁关系

三种攻击不是孤立的，它们经常组合使用：

XSS 绕过 CSRF 防御： 如果目标站有 CSRF Token 但存在 XSS，攻击者可以通过 XSS 读取页面中的 CSRF Token，然后以用户身份发起带有效 Token 的请求。此时 CSRF Token 形同虚设——因为攻击者通过 XSS 获得了和目标站 JS 相同的权限。

// XSS 注入的 JS：读取 CSRF Token，发起伪造请求
const token = document.querySelector('input[name=csrf_token]').value;
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'X-CSRF-Token': token },
  credentials: 'include',
  body: JSON.stringify({ to: 'attacker', amount: 10000 })
});

文件上传 → XSS： 上传 SVG 文件（内含 JavaScript），如果上传目录没有做域名隔离或 Content-Disposition 限制，其他用户访问该 SVG 时触发 XSS。这是文件上传和 XSS 的交叉点。

文件上传 → CSRF： 上传 .htaccess 文件修改服务器解析规则，让 .jpg 被当作 PHP 执行。这本身不是 CSRF，但上传操作如果缺乏 CSRF 防护，攻击者可以以管理员身份通过 CSRF 在管理后台上传恶意文件。

XSS + CSRF 组合： XSS 注入的 JS 可以发起跨域请求（因为同源策略不阻止发送请求，只阻止读取响应）。如果配合 CORS 配置错误，XSS 可以读取其他域的敏感数据，将 XSS 的影响从一个域扩展到多个域。

4.4 防御侧重对比

            XSS                    CSRF                   文件上传
            ─────────────────     ─────────────────      ─────────────────
核心风险    数据被当作代码执行      请求被以用户身份发出     恶意文件被写入可执行环境

主战场     响应体（HTML渲染）      请求头（Cookie携带）     请求体（multipart解析）

最关键防御  输出编码                SameSite Cookie         上传目录禁执行
           （按上下文选编码函数）   （阻断跨站携带Cookie）   （最后一道防线）

兜底防御   CSP响应头               CSRF Token              独立域名/对象存储
           （禁止内联脚本）        （服务端校验请求合法性）  （隔离执行环境）

辅助防御   输入验证                自定义请求头              文件名随机化
           模板引擎默认转义         Origin校验               Magic Number校验
           框架默认转义             二次验证                 防病毒扫描

三种攻击的防御逻辑有一个共同点：纵深防御，不依赖任何单一手段。

XSS 的纵深：输出编码 → 模板引擎默认转义 → CSP → 输入验证。

CSRF 的纵深：SameSite Cookie → CSRF Token → CORS → 自定义头 → 二次验证。

文件上传的纵深：上传目录禁执行 → 文件名随机化 → 扩展名白名单 → Magic Number → 独立域名隔离 → 防病毒扫描。

每一层都可能被绕过，但组合使用可以大幅提高攻击成本。

4.5 一个统一的视角

从 HTTP 协议的角度看，三种攻击的本质可以统一为：

XSS = 响应体中的数据被浏览器当作代码执行。 防御核心是确保数据始终是数据——输出编码、CSP。

CSRF = 请求中的身份凭证被浏览器自动携带。 防御核心是确保请求确实是用户主动发出的——SameSite、Token。

文件上传 = 请求体中的恶意内容被服务端写入可执行环境。 防御核心是确保写入的内容不可执行——目录权限、存储隔离。

三者的共同根源是：系统在处理用户可控数据时，没有正确区分”数据”和”指令”的边界。 XSS 混淆了 HTML 数据和 JS 代码，CSRF 混淆了用户请求和伪造请求，文件上传混淆了普通文件和可执行脚本。

理解了这一点，再看任何新的 Web 漏洞，都可以问同一个问题：在这个漏洞中，数据和指令的边界在哪里被混淆了？
